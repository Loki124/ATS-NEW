## 一、背景与目标

### 1.1 背景
当前「设置」侧边栏**没有**独立的「组织管理」分组。原 `SettingsLayout.s14` 菜单文案为「组织管理」，但实际指向的是 `/settings/department` 部门页（且页面 H1 `DepartmentManagement.s1` 也是「组织管理」）——即「组织管理」名称被部门页占用，语义错位。

兵哥要求将原「组织管理」功能**降级为「部门」**，并以「组织管理」作为**新的父分组**，在其下挂载三个二级子菜单：**部门 / 职务 / 职级**。其中职务、职级的页面交互对标 Moka：职务含职位族三级联动与职责说明富文本；职级含类别、职等、序列类型等管理。

### 1.2 产品目标（3 个正交目标）
1. **结构归位（G1）**：建立「组织管理」父分组，将部门/职务/职级三类组织基础数据归拢到统一入口，消除名称语义错位。
2. **补齐职务与职级（G2）**：提供职务、职级的完整 CRUD + 启停 + 导出能力，使组织基础数据可配置、可维护，支撑招聘需求/岗位/候选人等下游业务。
3. **架构一致（G3）**：新模块严格复用既有范式（dictionary 数据字典承载枚举、V2Permission 权限、软删、CSV BOM 导出、统一分页），不引入新的工程债。

### 1.3 约束（来自代码现状探查，PRD 必须对齐）
- 两级父分组模式已有先例：`g-company` / `g-user` / `g-permission`（`SettingsLayout.vue` 95–247 行）。
- 后端新 CRUD 范本 = `dictionary` app（`FullAuditModel`+`UUIDModel`、软删、`V2Permission`、`test_crud.py`）；前端范本 = `DepartmentManagement.vue`（搜索/状态筛选/启停/CSV 导出 `utf-8-sig`）。
- 权限三处登记：① 前端 `utils/permissionMenu.ts` `MENU_PERMISSION_RULES` 加 `{prefix,code}`；② 后端 `seed_v2_init.py` `RESOURCES` 加 `menu:view` + 动作码；③ 路由 `config/urls.py`。
- i18n：zh / en 两域键集合必须对称（`npm run locale:audit` 门禁），页内 key 用 `命名空间+sN`。
- 项目硬规则：CSV 导出 BOM `utf-8-sig`；分页唯一真源 `useTablePagination`（`pageSizes=[10,20,50,100]`，默认 20）；文案优先中文；系统内置值走「系统内置」语义；禁止 stub 返 501 假成功。
- **在途改动禁区（本期不许触碰）**：`demand/`、`field_acl/`、`data_permission/`、`candidate/`、`application/`、`add_candidate/`、`DemandList.vue`、`CandidateDetail.vue`。

## 二、用户故事

- **US1**（HRIS/HR 管理员）：作为组织管理员，我希望在「组织管理」下统一看到部门、职务、职级三个入口，以便在一处维护全部组织基础数据。

- **US5**（HR 管理员）：作为组织管理员，我希望将职务/职级列表导出为 Excel 友好的 CSV（带 BOM），以便离线盘点与汇报。

## 三、功能需求（按模块）

### 3.1 模块一：菜单重组

| 项 | 裁决 / 说明 |

| 文案调整 | `SettingsLayout.s14`（原「组织管理」菜单标题）→ 改为「部门」；`DepartmentManagement.s1`（页面 H1，原「组织管理」）→ 改为「部门管理」。新父分组「组织管理」使用新增 i18n key（建议 `SettingsLayout.s62`，zh/en 对称补「组织管理 / Organization」）。 |

### 3.2 模块二：职务（Job Title）

#### 3.2.1 列表页（对标 Moka 职务列表）
- 顶部：搜索框「搜索职务名称」 + 状态筛选（启用中 / 停用 / 全部）+ 右侧「添加」「导出」按钮。
- 表格列：`职务 | 在职员工数 | 关键职务(是/否) | 操作(编辑/停用)`。
- 分页：复用 `useTablePagination`（默认 20 条/页，可切 10/20/50/100）。
- 「在职员工数」列：本期**隐藏**（见 §3.2.4 与 Q3）。

#### 3.2.2 编辑/新增弹窗字段
| 字段 | 必填 | 控件 | 数据来源（裁决见 Q2） |
|---|---|---|---|
| 职务 | 是 | 文本 | 用户输入 |
| 职位族 | 是 | 下拉 | 数据字典 `job_family`（新增字典类型） |
| 职位类 | 否 | 下拉 | 数据字典 `job_category`，建议级联依赖「职位族」 |
| 职位子类 | 否 | 下拉 | 数据字典 `job_subcategory`，建议级联依赖「职位类」 |
| 关键职务 | 是 | 下拉（是/否） | 系统内置枚举 |
| 职责说明 | 否 | 富文本（B/I/U/列表/链接） | 复用既有 `RichEditor` 组件（`components.RichEditor`） |
| 是否为管理岗 | 否 | 下拉 | 系统内置枚举（是/否） |
| 岗位层级 | 否 | 下拉 | 数据字典或系统内置枚举（建议字典化，P1） |
| 底部 | — | 取消 / 确定 | — |

#### 3.2.3 启停
- 列表行「停用」操作：置 `is_enabled=false`（软停，不物理删除）。再次进入可「启用」。
- 停用对引用方约束：本期仅**提示**被引用情况（若有），**不硬阻止**（避免触碰 `candidate/`、`demand/`、`position/` 等在途禁区）；硬阻止留 P2（见 Q5）。

#### 3.2.4 在职员工数
- 本系统无员工表，仅候选人/用户。本期**不计算、不展示**该列（出 P0，进 P1/P2）。若后续需落地，候选方案：从「已入职」状态的 candidate 按职务/职级关联计数（见 Q3）。

### 3.3 模块三：职级（Job Level）

#### 3.3.1 职级管理页
- 标题「职级管理」。顶部：状态筛选（启用中/停用/全部）+ 右侧按钮组：`添加职级` / `导入` / `类别管理` / `职等管理` / `职级序列管理`。
- 表格列：`职级名称 | 类别 | 职等(数字) | 顺序 | 在职员工数 | 备注 | 操作(编辑/停用)`。
- 分页：复用 `useTablePagination`。「在职员工数」列同 §3.2.4 本期隐藏。

#### 3.3.2 职级模型边界（裁决）
| 实体 | 字段 | 说明 |
|---|---|---|
| 职级 JobLevel | name、category(FK 类别)、grade(职等,数字)、sort_order(顺序)、remark(备注)、is_enabled | 核心实体 |
| 类别 JobLevelCategory | name、sort_order | 「类别管理」弹窗维护；示例：1/助理、2/专员、3/主管、14/专家 |
| 职等上限 JobLevelGradeSetting | max_grade(默认 40，范围 1–999) | 全局单例设置，「职等管理」弹窗维护；提示「可设置等级上限 1–999」 |
| 序列类型 JobLevelSequence | 专业序列(系统内置固定，不可更改/停用) + 管理序列(开关) | 「职级序列管理」弹窗维护；专业序列置灰必选 |

#### 3.3.3 弹窗功能
- **类别管理弹窗**：类别列表（每行 = 类别名称输入框 + 「包含 N 个职级」+ 停用链接）；底部「+ 添加类别」；取消/保存。
- **职等管理弹窗**：字段 `等级上限`(数字，默认 40)，提示「可设置等级上限 1–999」；取消/确定。
- **职级序列管理弹窗**：序列类型复选——专业序列（置灰必选，说明「系统默认职级均为专业序列，不可更改、停用」）；管理序列（说明「支持员工确定双职级，并在各相关业务场景可维护管理职级字段」）；取消/确定。
- **导入按钮**：本期**不实现**具体导入逻辑（进 P1）；按钮可保留但点击提示「即将上线」或直接隐藏——建议按 Q4 拍板，推荐 P1 实现。

#### 3.3.4 启停
- 职级 / 类别用 `is_enabled`（与 dictionary 惯例对齐，见 Q5）。停用仅软停，不物理删除；类别停用后其下职级仍可查看但不可新关联。
