# 统一背调供应商接口标准规范

> 文档版本：v1.0.0 ｜ 编制角色：产品经理（许清楚）｜ 审批：交付总监（齐活林）
> 适用范围：ATS-NEW 招聘系统背调模块 · 所有背调供应商统一接入
> 配套代码：现行 3 个接口（创建订单 / 订单回调 / 取消订单）

---

## 0. 文档说明

### 0.1 文档目的
当前背调模块已接入**一家**供应商，接口字段散落在各供应商对接脚本中，缺乏统一约定。为支持**多家供应商并行接入、统一调度、可替换**，特制定本规范，作为供应商技术对接合同附件与联调验收依据。新供应商**必须**完全遵循本规范，方可通过接入评审。

### 0.2 适用范围
- 我方（ATS-NEW）与背调供应商之间的**所有** RESTful 接口交互。
- 涵盖：订单创建、订单取消、状态异步回调三大核心链路，以及供应商能力声明、健康检查等接入支撑链路。
- 供应商侧的报告查看、附件下载等如涉及，参照本规范的「认证 / 签名 / 安全」统一约束。

### 0.3 术语表

| 术语 | 说明 |
|------|------|
| 我方 / 平台 | ATS-NEW 招聘系统（调用方） |
| 供应商 / SP | 背调服务供应商（被调用方） |
| 候选人 | 被背调的求职者 |
| 委托人 / 经办人 | 发起背调的 HR / 招聘方联系人（operator* 字段） |
| 合作凭证 | appId + appKey，供应商分配给我方的身份标识 |
| 签名 sign | 用于校验请求/回调来源与完整性的 HMAC 值 |
| 订单号 number | 我方生成的背调订单唯一编号（贯穿全链路） |

| 版本 | 日期 | 说明 |

## 1. 接口协议与认证方式

### 1.1 传输协议
- **强制 HTTPS**，TLS 版本 ≥ 1.2，禁止明文 HTTP。
- 数据格式：**`application/json; charset=utf-8`**，UTF-8 编码。
- 字符集：请求与响应均使用 **camelCase** 字段命名（与前端全局约定一致）。

### 1.2 接口风格与版本
- 风格：RESTful，资源面向「订单 / 回调 / 能力」建模。
- **版本前缀强制**：所有路径以 `/api/v{n}/` 开头，例如 `/api/v1/background-check/orders`。
- 旧供应商未带版本号的接口，接入网关统一 301 重定向至 `/api/v1/`，供应商无需改造存量路径。

### 1.3 环境隔离
每家供应商提供两套 Base URL，通过合作凭证区分，**禁止**用同一凭证混用环境：

| 环境 | 用途 | 数据 |
|------|------|------|
| 沙箱 Sandbox | 联调、回归、流水线 | 全为虚构测试数据 |
| 生产 Production | 真实业务 | 真实 PII |

### 1.4 认证方式（双重）
本规范采用「**凭证 + 签名**」双重认证，分别覆盖同步请求与异步回调。

#### 1.4.1 同步请求认证（appId + appKey）
- 我方在请求头携带：
  - `X-App-Id: {appId}`
  - `X-App-Sign: {签名}`
  - `X-Timestamp: {毫秒时间戳}`
- `appId` / `appKey` 为供应商分配的合作凭证（对应现行 `appId` / `appKey` 字段）。
- `appKey` **仅用于签名计算，绝不出现在请求体或 URL 中**。

#### 1.4.2 异步回调认证（sign 验签）
- 供应商回推状态通知时，须在请求体携带 `sign` 字段（对应现行回调接口的 `sign`）。
- 我方收到后按 §5.2 规则验签，验签失败一律拒绝并计入安全审计。

#### 1.4.3 签名算法（统一 HMAC-SHA256）
```
待签字符串 = 排序后的业务参数(key=value&连接) + "&timestamp=" + X-Timestamp
签名       = HMAC-SHA256(待签字符串, appKey)  // 输出十六进制小写
```
- 业务参数指请求体 JSON 的**业务字段**（不含 `sign`、不含 `X-*` 头）。
- `null` / 空字符串字段**不参与签名**。
- 时间戳允许误差 ±5 分钟，超出视为重放攻击拒绝。

## 2. 字段命名与数据结构定义

### 2.1 命名与类型约定
- 字段名：**camelCase**（与现行 Java 字段一致，如 `candidateName`、`operatorPhone`）。
- 时间字段：
  - 时间戳类（如 `completionTime`）→ **Unix 毫秒 Long**，与现行 `Long completionTime` 保持一致。
  - 日期类（如 `expectEntryTime`）→ **`yyyy-MM-dd` 字符串**，便于人读与校验。
- 枚举类统一用 **Integer**（与现行 `status` / `riskLevel` / `authWay` 一致）。
- 文件类统一用 **`List<String>`**，元素为**已上传文件的 URL 或文件标识**（现行 `authFiles` 等即如此）。

### 2.2 统一数据字典

| appKey | String | 是（仅签名用，不传体） | 合作 key |
| requestId | String | 是 | 我方生成的幂等请求号（UUID），用于去重 |

| 3 | 高风险 |
| 4 | 无风险 |

**授权方式 authWay（供应商可声明支持子集）**

| 值 | 名称 |
|----|------|

## 3. 请求与响应格式

### 3.1 统一请求信封
写接口请求体 = 业务字段（§2.2）+ 公共头（§1.4.1）。示例（创建订单）：

```json
POST /api/v1/background-check/orders
Headers:
  X-App-Id: sp_abc123
  X-Timestamp: 1724563200000
  X-App-Sign: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
Content-Type: application/json

{
  "requestId": "req-7f3a9c2e",
  "productToken": "pkg_edu_001",
  "candidateName": "张三",
  "phone": "13800001111",
  "operatorName": "李四",
  "operatorPhone": "13900002222",
  "authWay": 1,
  "callbackUrl": "https://ats.example.com/api/v1/background-check/callback"
}
```

### 3.2 统一响应信封（**新增，现行接口无 wrapper**）
所有接口响应统一结构，便于错误处理与追踪：

```json
{
  "code": 0,                 // 业务码：0=成功，非0=失败（见 §4）
  "message": "success",      // 人类可读描述
  "data": { "number": "BG202608250001" },
  "requestId": "req-7f3a9c2e",
  "timestamp": 1724563200123 // 响应生成毫秒时间戳
}
```

- 成功：`code=0`，`data` 承载业务数据（创建订单 `data.number`；取消订单 `data={number, cancelled:true}`）。
- 失败：`code≠0`，`data` 可为空，`message` 描述原因。
- HTTP 状态码见 §4.1，业务码见 §4.2。

### 3.3 分页（列表类接口预留）
列表查询（如订单列表）统一分页参数与返回：

```
Query: page=1&pageSize=20
返回 data: { "list": [...], "pagination": { "page":1, "pageSize":20, "total":135 } }
```

## 4. 状态码与错误处理机制

### 4.1 HTTP 状态码
| HTTP | 含义 | 处理 |
|------|------|------|
| 200 | 请求已处理（业务结果看 `code`） | 读取 `code` |
| 400 | 参数校验失败 | 返回 `code=400xx`，修正后重试 |
| 401 | 认证失败（appId/appKey/sign 错） | 检查凭证与签名 |
| 403 | 无权限（套餐不匹配/环境错） | 联系平台 |
| 404 | 资源/接口不存在 | 检查路径与版本 |
| 409 | 冲突（订单已存在/已取消） | 幂等处理 |
| 429 | 限流 | 按 `Retry-After` 退避重试 |
| 500 | 供应商内部错误 | 平台侧告警，可重试 |
| 503 | 服务不可用/维护 | 进入降级，稍后重试 |

### 4.2 业务错误码（code）
| code | 含义 |
|------|------|
| 0 | 成功 |
| 40001 | 缺少必填字段 |
| 40002 | 字段格式非法（手机号/身份证校验失败） |
| 40003 | 套餐不存在或无权限 |
| 40101 | appId 无效 |
| 40102 | 签名校验失败 |
| 40103 | 时间戳超时（重放） |
| 40401 | 订单号不存在 |
| 40901 | 订单状态不允许该操作（如已取消再取消） |
| 50001 | 供应商内部异常 |

### 4.3 错误处理原则
- **fail-fast + 明确**：参数错误立即返回 4xx + 具体 `code`，不静默。
- **不吞异常**：供应商侧 5xx 必须返回明确 `message`，平台侧记入错误日志与告警，**禁止**返回"成功"掩盖失败。
- **幂等安全**：重复请求（同 `requestId`）返回首次结果，不产生副作用。

## 5. 回调与异步通知规范

### 5.1 回调触发与投递
- 供应商在订单状态变更时，**主动 POST** 至我方 `callbackUrl`（请求中指定）或平台默认回调地址。
- 回调为**异步、至少一次投递（at-least-once）**，我方须按 §5.3 做幂等。
- 每次状态变更均推送（含阶段报告 status=7），我方按 `status` 驱动订单机。

### 5.2 回调签名校验（强制）
```
待签串  = "number=" + number + "&status=" + status + "&timestamp=" + ts
sign    = HMAC-SHA256(待签串, appKey)   // 十六进制小写
```
- 我方收到后用 `appKey` 重新计算并比对 `sign`，不一致 → **拒绝（401）并审计**。
- `timestamp` 纳入待签并校验 ±5 分钟防重放。

### 5.3 幂等与重试
- 以 `(number, status, completionTime)` 组合做幂等键；重复推送返回 200 不重复处理。
- 供应商侧：我方返回 **2xx 视为成功**；非 2xx 按**指数退避**重试（建议 1s/5s/30s/5m，最多 6 次）。
- 重试期间供应商须保留通知，避免丢失。

### 5.4 超时与降级
- 我方回调接口 P99 < 1s；超时供应商按重试策略处理。
- 若回调长期失败，供应商在订单详情接口仍可提供最新状态（供平台**主动轮询兜底**）。

## 6. 数据安全性要求

### 6.1 传输安全
- 全链路 **HTTPS TLS≥1.2**，HSTS 开启。
- 签名防篡改、防重放（§1.4 / §5.2）。

### 6.2 PII 与敏感字段
- 身份证 `idCard`、手机号 `phone` 属 PII，**传输加密 + 存储加密（AES-256）**。
- 数据库存储 PII 字段须**脱敏存储**（如身份证展示 `110***********1234`）。
- 日志、监控、链路追踪中**禁止打印明文 PII**；确需排查用令牌化 ID 代替。

### 6.3 存储与留存
- 报告、授权书等文件须加密存储，访问需鉴权，设置留存期限（默认 ≤ 法定/合同期限）。
- 候选人撤回授权（status=8）后，须按约定删除/封存相关 PII 与报告。

### 6.4 权限与审计
- 合作凭证按供应商隔离，最小权限；`appKey` 定期轮换（建议 90 天）。
- 所有订单创建、取消、回调、报告访问**留审计日志**（谁/何时/什么操作/结果）。
- 供应商仅可访问本合作账号下的数据，跨租户隔离。

### 6.5 合规
- 满足《个人信息保护法》与候选人**授权前置**要求；无授权（status=2 未解决）不得开展实质背调。
- 候选人有权查询、更正、删除其背调数据。

## 7. 供应商接入的适配与扩展约定

### 7.1 架构模式：统一抽象 + 适配器（Adapter）
- 平台定义**统一背调接口契约**（即本规范），对上游业务只暴露统一方法：`createOrder / cancelOrder / handleCallback / queryOrder`。
- 每家供应商实现一个 **Adapter**，负责：
  1. 平台标准字段 ⇄ 供应商私有字段的**映射**（字段名/枚举值差异在此消化）；
  2. 供应商私有认证/签名细节；
  3. 供应商特有能力的封装。
- 新增供应商 = 新增一个 Adapter，**业务代码零改动**即可接入。

### 7.2 供应商能力声明（Capability Negotiation）
供应商接入时提交能力清单，平台据此路由与校验：

| 能力项 | 说明 |
|--------|------|
| 支持套餐 productToken 列表 | 决定可下单范围 |
| 支持授权方式 authWay 子集 | 决定授权流程分支 |
| 是否支持主动回调 | 否则平台走轮询兜底 |
| 支持字段子集 | 如不支持 `educationFiles` 则下单时忽略 |
| 报告格式 | PDF / JSON / 在线地址 |

- 能力声明以**配置文件/元数据**形式登记，平台启动时加载，避免硬编码。

### 7.3 版本管理
- 路径版本 `/api/v1/`；破坏性变更升 `v2`，旧版本给**不少于 90 天**过渡期。
- 枚举新增取值（如新增 status）须向后兼容，旧版供应商忽略未知值。

### 7.4 环境与联调
- 必须提供沙箱环境，沙箱数据全虚构，可自由触发各 status 回调用于联调。
- 联调通过**自动化用例**覆盖：创建→各状态回调→取消→幂等→签名失败→超时重试。

### 7.5 健康检查
- 供应商提供 `GET /api/v1/health`，返回 `{ "status": "up", "timestamp": ... }`。
- 平台定时探活，异常自动降级（暂停新单下发、保留存量处理）。

### 7.6 新供应商接入 Checklist（落地交付物）
1. [ ] 签署数据与安全合规附录（§6）
2. [ ] 分配 `appId` / `appKey`，配置沙箱 + 生产 Base URL
3. [ ] 提交能力声明清单（§7.2）
4. [ ] 实现 Adapter：字段映射 + 签名 + 回调
5. [ ] 沙箱联调通过自动化用例（创建/回调/取消/幂等/安全）
6. [ ] 提供 `health` 端点并接入探活
7. [ ] 安全评审：PII 加密、日志脱敏、审计、密钥轮换
8. [ ] 平台侧灰度 1 个真实订单验证 → 全量
