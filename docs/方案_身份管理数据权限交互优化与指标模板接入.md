# 身份管理数据权限交互优化 × 指标模板接入方案

> 文档类型：现状调研 + 优化方案（未实施）
> 调研日期：2026-10-14　　代码基线：`main` @ `2d3aeb6d`
> 范围：查看权限（数据可见范围、字段级可见性）、操作权限（增删改导入导出审批）的交互流程与配置逻辑；并将「指标模板」能力融入权限规则配置
> 证据标注：`文件:行号` 为代码事实；标「推断」处为分析判断，附验证方式

## 0. 结论摘要

| # | 结论 | 性质 |
|---|---|---|
| 1 | **操作权限（写范围）保存后被抹除** —— 前端序列化漏 `write`，后端「先删后建」把 WRITE 行删掉不重建，UI 却提示保存成功 | 已复核的 P0 缺陷 |
| 2 | **字段级可见性是只读死页** —— 后端模型、序列化裁剪、审计日志全在，前端无任何配置入口，`upsertAclRule/deleteAclRule` 全仓零调用 | 已复核的 P0 缺失 |
| 3 | **三套权限模型并存**（`permission_resources` / `data_permission_rules` / `field_acl`），粒度重叠、无统一入口、无冲突裁决 | 架构级问题 |
| 4 | **权限叠加语义是"并集"，但前后端均无任何呈现**；且生产数据 84 条授权全部是「每人恰好 1 角色」，并集路径从未被真实流量验证 | 已用 SQL 核实 |
| 5 | **「用指标配权限」后端能力完备（已验证），但前端入口在 2026-10-13 被主动下线**；模板侧三类「值约束」（`value_domain`/`param_config`/实体值域）**从未进入任何条件目录** | 关键发现，直接决定方案取向 |
| 6 | 建议走 **B 方案**：以指标模板为权限条件的**唯一来源**，新建 `metric` 条件类型；复活已下线的「属性条件」词汇会造成第三套并行概念 | 建议，待决策 |

**一句话**：权限系统当前是「三套模型 + 两个数据范围 + 一个不生效的写范围 + 一个写不了的字段 ACL」；要接入指标模板，**必须先决定走哪条技术路线**（复活 attribute vs 新建 metric 条件类型），本文档给出推荐路线与完整改动清单。

```

  → ViewSet.permission_classes = [V2Permission]（core/permissions_v2.py:61）
  → get_queryset() → ScopeQuerysetMixin → scope_filter_q()（core/scope_resolver.py:487，唯一真相源）
  → get_object() 之后 → ensure_writable()（data_permission/enforcement.py:338）
  → to_representation → FieldAclSerializerMixin（field_acl/mixins.py:49）列级裁剪
```

叠加语义：**并集**。`has_perm` 用 `role_code__in`（`core/permission_check.py:20-33`）；数据范围多角色 `set()` 合并（`scope_resolver.py:110-111`）；任一角色 ALL → 全量（`enforcement.py:180-205`）。列级例外：取**最严** `most_restrictive()`（`enforcement.py:34,45-51`）。

### 1.5 指标模板接入现状（决定方案取向的关键）

**链路 A：指标模板 → 阶段规则（entry_condition）＝已完整打通**

## 2. 问题分析

### P0 级（阻断性，必须先修）

#### P0-1　写范围保存被抹除（前后端契约断裂）

- **证据**：前端 `submit()` 序列化 payload 时无 `write` 字段（`useRoleDataPerm.ts:684-693`）；后端 `upsert_modules()` 是「先删后建」（`role_scope_api.py:256-267`），且 `write` 缺失即 `w_mode='none' → continue`（`:289-292`）→ WRITE 行被删且不重建
- **表现**：管理员配好操作权限 → 校验通过 → 脏检查为 true → 提示"保存成功" → **重新打开配置全部消失**
- **加剧因素**：前端脏检查（`:441-448`）与校验（`:564-579`）都**包含 write**，形成"看起来生效了"的假象；后端返回体不含 write（`:125-127` 注释说明未配置时 mode='none'），前端无法察觉丢失
- **复现**：身份管理 → 编辑角色 → 数据权限 → 展开写范围 → 选「全部可写」+ 勾动作 → 保存 → 重新打开
- **附注**：DB 现存 11 条规则无一条 WRITE，与"从未成功保存过"一致

#### P0-2　字段级可见性无配置入口

- **证据**：`FieldAclSettings.vue` 只读；`upsertAclRule/deleteAclRule`（`api/field-acl.ts:53,56`）零调用；空状态引导指向不存在的配置区
- **影响**：敏感字段（薪资/身份证/手机号）无法按角色配 VIEW/MASK/HIDE；`maskPattern` 脱敏规则前端完全触达不到
- **连带**：ACL 仅接入 4 个序列化器（`candidate/serializers.py:29,69`、`talent_pool/serializers.py:16,43`），`application`/`interview`/`onboarding`/`demand` 裸奔

#### P0-3　授权数据完整性失控

- **证据**：`user_roles` 76/84 指向不存在的用户；`role_permission` 存在孤儿角色 `test`（21 条关联）
- **根因**：`user_id`/`role_code` 均为裸字段无 FK（`models_permission_v2.py:116,220`）
- **风险**：一旦给不存在的用户或 `test` 角色建立授权即刻放行；角色/用户删除不清授权

### P1 级（架构性）

#### P1-1　三套权限模型并存，无统一入口与裁决规则

| 模型 | 承载 | 维度 | 粒度 |
|---|---|---|---|
| `permission_resources` | 功能权限 | 全局（可下推双系统） | 菜单 / 按钮 |
| `data_permission_rules` | 数据与操作权限 | ROLE / DEPARTMENT / USER | 行 / 列 |
| `field_acl` | 字段可见性 | **仅 ROLE** | 列 |

管理员需在三处分别配置，冲突时无裁决规则；`priority` 字段（`models.py:138`，注释"大者优先"）**在 enforcement 中从未被读取**——管理员配的优先级被静默忽略。

#### P1-2　权限叠加语义对用户完全不可见

并集是后端事实，但前端零呈现（`并集|交集|叠加|冲突|优先级|继承` 全仓零命中）。用户给同一用户配两个角色后，**无法得知最终可见范围**；叠加预览器不存在。

#### P1-3　操作路径冗长

- 配一个模块的数据范围：**7 次点击 + 2 层弹窗嵌套**，布尔表达式需手写（`useRoleDataPerm.ts:202-286` 自研递归下降校验器）
- 新建角色**必须两轮**（`RoleEditModal.vue:149-150` 空态 + `:714` 的 `if (form.id && ...)` 跳过新建）
- 中文摘要 `previewOf()` 只在关闭规则弹窗后才可见（`ModulePermCard.vue:68-77`）

#### P1-4　关键能力不可发现 / 操作类动作配置缺失

- 写范围默认折叠（`ModulePermCard.vue:98,107`），未激活 mode 时完全收起
- 动作无分组；`category==='read'` 被过滤（`:232-237`）→ 导出类动作若归为 read 则**无法在写范围配置**
- 动作字典 15 个仅 6 个接线（`ensure_writable` 实际只用 edit/transition/claim/talent_pool_add/delete）；`import`/`export`/`merge`/`eliminate` 等**无守卫调用点** → 批量导入不受写范围约束（`candidate/views.py:541-555` 无 scope 判定）
- `approve_l1/approve_l2` 权限码**零消费**（仅 seed + 模板授予），多级审批权限隔离形同虚设

### P2 级（体验与一致性）

| # | 问题 | 证据 |
|---|---|---|
| P2-1 | 两套"数据范围"语义冲突无说明（`defaultDataScopeType` vs `module.mode`） | `RoleEditModal.vue:26-33` / `ModulePermCard.vue:45-54` |
| P2-2 | 权限资源树未启用（`parent_code` DB 全空），批量授权只能靠字符串前缀解析 | `models_permission_v2.py:40` |

### 问题归因到用户提的四个维度

| 维度 | 核心问题 |
|---|---|
| **操作路径** | 7 步 2 层弹窗；新建角色两轮；表达式手写；摘要延迟可见（P1-3、P0-2） |
| **层级关系** | 角色 → 功能/数据权限仅靠三个平级页签，无递进；"数据范围"有两套互不相关的层级（A 角色级 / B 模块级）；权限资源树未启用（P2-1、P2-2） |

## 3. 优化后的交互流程

### 3.1 设计取向

- **渐进披露取代平铺**：角色编辑从「三个平级页签」改为 **两段式**：第一段"身份与功能"（信息 + 功能权限），第二段"数据与操作权限"（读/写/字段三合一）
- **一处配置一条权限**：读范围、写范围、字段可见性统一到同一张「模块权限卡」内，用三个并列分区表达，取代"读在卡上、写藏在折叠里、字段在另一个只读页"
- **语义显式化**：任何叠加/继承/冲突都在 UI 上用「生效预览」讲清楚，而不是让用户去猜
- **新建一次配完**：新建角色允许直接配权限，首个保存请求携带权限草稿

### 3.2 目标态操作流程

**流程 A：新建角色并配权限（1 轮完成）**

```
身份管理 → 新建身份
  ├─ Step1 基础信息：名称 / 编码 / 默认数据范围（保留，但标注"仅对未单独配置的模块生效"）
  ├─ Step2 功能权限：模块分组 → 子模块 → 操作码勾选（保持现状，补全父选联动）
  └─ Step3 数据权限：模块卡 × N（读/写/字段三分区）
        └─ 保存（单次请求：角色 + 功能权限 + 数据权限）
```

**流程 B：配置模块读范围（抽屉替代三层弹窗）**

```
模块权限卡 · 读范围分区
  ├─ 模式三选一：无权限 / 全部 / 指定范围
  ├─ 选「指定范围」→ 就地展开条件组编辑器（抽屉，非弹窗套弹窗）
  │    ├─ 条件组编辑器提供三种条件源：
  │    │    ① 关系维度（保持现状：本人/本部门/用人经理/HRBP…）
  │    │    ② 指标条件（新增，见第 4 章）
  │    │    ③ 权限模板（保持现状，一键引用快照）
```

## 4. 指标模板配置设计要点

### 4.1 决策：走 B 方案（新建 metric 条件类型），不复活 attribute

| 维度 | A 方案：复活 `kind='attribute'` | **B 方案：新建 `kind='metric'`（推荐）** |
|---|---|---|
| 词汇 | 与"关系维度"并列的第三套词汇（正是 2026-10-13 下线的原因） | 复用阶段规则已定稿的「指标模板」词汇，用户已在阶段规则中熟悉 |
| 值约束 | 仍无 `value_domain`（需另建通路） | 模板的值域/实体候选/白名单天然接入 |
| 存储 | `field=source_path`（原子指标驱动） | `field=模板 id` + 版本快照，与阶段规则一致 |
| 失效语义 | 沿用 attribute 现状 | 可显式定义为 fail-closed（见 4.5） |
| 存量数据 | 当前 DB 中 `kind='attribute'` 条件 **0 条**（`plan-attribute-condition-offline.md:41-45` 已核实）→ 无迁移负担 | 同 |
| 后端成本 | 复活前端 + 改造 attribute_fields | 新增 metric 条件分支，复用 `evaluate_metric_condition` 与 `operator_matrix` |

**推荐 B 方案**。attribute 分支保留只读兼容（存量 0 条，仅防历史数据），新配置一律走 metric。

### 4.2 指标模板与原有权限规则的关系

```
权限规则（DataPermissionRule.scope_payload）
  └─ 条件组 groups[]
       └─ 条件 conditions[]
            ├─ kind='relationship'  关系维度（本人/部门/HRBP…）—— 保持现状
            ├─ kind='metric'        🆕 指标模板条件 —— 本方案新增
            │    ├─ templateId      引用 MetricTemplate（存 id，不存外键以免级联）
            │    ├─ templateVersion 引用时的版本号（快照）
            │    ├─ operator        必须 ∈ 模板 operators 白名单
            │    └─ value           形态由模板驱动（见 4.4）
            └─ kind='templateRef'   权限模板快照引用 —— 保持现状
```

**职责边界**：
- **指标模板**回答"用什么指标、可以怎么比、能填什么值"（配置能力）
- **权限规则**回答"在什么条件下、对哪个模块、谁能读/能做什么"（授权决策）
- 指标模板**不直接持有权限语义**，权限语义只在规则侧表达 → 同一模板可被多个角色/模块复用

### 4.3 选择入口（三处，缺一不可）

| 入口 | 位置 | 作用 |
|---|---|---|
| **E1 权限侧主入口** | 模块权限卡 → 写/读范围 → 条件组 → 「+ 指标条件」 | 配置权限时按指标挑模板 |
| **E2 指标侧反查入口** | 指标模板列表 → 「被引用」列 + 影响面分析 | 改模板前看清影响哪些权限规则（复用 `template_impact.py`，需扩到 data_permission） |
| **E3 批量入口** | 指标模板 → 「应用到权限」批量选择模块/角色 | 常用模板一次铺开到多个模块 |

**E2 是当前完全缺失的一环**：现在改模板只能看到 entry_condition / stage_rule / metric_rule 三处影响，看不到权限。

### 4.4 参数映射（补齐断掉的三类值约束）

**A. 目录装配**（扩 `_build_metric_template_catalog` 的权限变体）

| 模板字段 | → 权限条件字段 | 用途 |
|---|---|---|
| `tpl.id` | `templateId` | 条件存储引用 |
| `version` | `templateVersion` | 快照锚点 |

| `tpl.operators` | `operators` | 算子白名单（唯一来源，与阶段规则一致） |

### 4.5 生效优先级与冲突处理

**优先级链（自上而下，先命中先生效）**

| 层 | 规则 | 说明 |
|---|---|---|
| 1 | 硬分区 `recruit_type` | 对所有用户含超管生效，不可覆盖（`scope_resolver.py:513`） |
| 2 | 超管 bypass | 无条件放行 |
| 3 | **模块级规则**（`module.mode=scope` 时的条件组） | 🆕 高于角色默认范围 |
| 4 | 角色默认范围 `defaultDataScope_type` | 仅当模块未配置（=兜底） |
| 5 | 租户默认 `GLOBAL_DEFAULT_DATA_SCOPE` | 最后兜底，当前 `SELF` |

**同一模块多规则并存时的裁决**

| 场景 | 裁决 | 现状 | 方案 |
|---|---|---|---|
| 多角色读范围 | **并集**（任一 ALL → 全量） | 已实现，无 UI 呈现 | 保留语义 + 加预览 |
| 多角色列权限 | **从严**（HIDE>MASK>VIEW） | 已实现（`most_restrictive`） | 保留 + 冲突可见 |
| 功能权限 vs 写范围动作 | **从严**（功能权限勾了但写范围没勾 → 不可操作） | 隐性 | 显式提示（流程 C） |
| `priority` 字段 | 当前**从不生效** | 定义但不读 | 二选一：①实现为「规则命中优先级」②下掉字段并加迁移。**建议先下掉**（避免造出第二套叠加语义） |
| 条件值越界 | **保存拦截**（新） | 当前不校验 | 🔴 值必须落在模板 `value_domain` 内，否则拒绝保存并给出行内错误 |
| 算子不在白名单 | **保存拦截** | 求值时报错 | 前端算子下拉只给白名单；后端保存二次校验 |
| 模板停用/删除/改版 | **fail-closed，整组 `_deny_all()`** | attribute 链路已是此语义 | 🔴 明确采用**权限侧更严语义**（区别于阶段规则的条件级 FAIL） |
| 模板版本落后 | **漂移标记 + 显式升级**（不自动跟随） | `drift_of()` 已有范式 | 复用 `scope_templates.py:202-252` |

**🔴 铁律：指标模板不得成为运行时外链**。权限规则引用模板时**必须快照**（存 templateVersion + 当时的候选值集合），否则「管理员改一次模板，所有在用权限规则静默漂移」＝事故级缺陷。这条沿用权限模板已确立的原则（`scope_templates.py:3-15`）。

### 4.6 权限叠加的呈现设计

```
生效预览（用户视角）
┌──────────────────────────────────────────────┐
│ 用户：张三（3 个角色）                          │
├ 功能权限  并集 · 命中 78 项                     │
│   导出候选人 ✓  ← HR / HRBP（任一授予即生效）    │
│   删除候选人 ✗  ← 无人授予                      │
├ 数据范围  并集                                 │
│   候选人管理：全部 ← SUPER_ADMIN（范围最大）      │
│   招聘流程：本部门及下属 ← HIRING_MANAGER        │
├ 列权限    从严                                 │
│   薪资：MASK ← offer 模块默认（HR 无更严规则）   │
│   身份证：HIDE ← AUDITOR（最严）                 │
└──────────────────────────────────────────────┘
```

每个结论**可展开到来源角色**，让"叠加"从黑盒变成可解释。
