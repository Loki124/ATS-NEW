### F1 实际落地

- **每日看板快照幂等**：`ReportSnapshot` 增 `snapshot_key`（唯一、可空 —— MySQL 唯一索引允许多个 NULL，
  不影响其他快照）；任务改 `update_or_create(snapshot_key='DASHBOARD:YYYY-MM-DD')` →
  同一天重跑/并发跑都只更新同一条，不再出现重复快照。迁移 `analytics/0007`。
- **提醒任务改「先标记后发」**：`NotificationLog` 增 `sending_at`（抢占位）；任务在真正发信前
  用**条件 UPDATE** 抢占本行（`sending_at` 由 NULL 置 now），抢到才发；抢不到跳过；
  抢占超 5 分钟视为上一轮崩溃 → 允许重新抢占（既不重复发也不漏发）。迁移 `notification/0004`。
  修的是「外部通道已收到、但落 `sent_at` 前进程崩溃 → 下一轮重发」的重复通知窗口。
- 新增用例 `tests/test_f1_f2_celery_idempotency.py`（17 条）。

### F2 实际落地

- **只加 `max_retries` 不会自动重试** —— 必须配 `autoretry_for(瞬时异常)`，且异常要真正**逃出任务体**
  才会被重跑。故给 10 个任务统一加
  `max_retries=3, default_retry_delay=5, autoretry_for=(OperationalError,)`：
  选 `django.db.OperationalError`（DB 抖动/死锁/连接断开）—— 它是 `DatabaseError` 子类但
  **不含** `IntegrityError`/`ProgrammingError`（非瞬时，重试无意义）。
- 新增**静态守卫**用例（参数化 10 个任务）：断言每个任务都有 `max_retries` + `autoretry_for`，
  防止后续改动把重试配置回退（这是「配了等于没配」的常见退化点）。

### F3 实际落地（通知链路）

**前提核实**：外部调用确实在请求路径上 —— `NotificationService.send_notification` 此前**同步** dispatch，
而它被 Offer 审批（`apps/offer/services.py:233`）、面试安排（`apps/interview/services.py:136`）、
公告推送（`apps/announcement/views.py:225`）、自动化规则执行（`apps/automation/services.py:456`）调用
→ 外部通道慢，**API 请求就跟着卡住**（各通道 `timeout=10`）。

**改法**：

1. 落库后 `transaction.on_commit(...)` **入队**由 Celery 任务投递，请求立即返回。
   用 `on_commit` 是必须的：不等事务提交就入队，worker 会抢在提交前读不到这一行。
2. **兜底 1**：broker 不可用（开发机没起 worker）→ 同步投递，**不丢通知**
   （异常集刻意收窄：kombu / redis / socket，**不新增宽捕获**，盲 except 基线仍是 147）。
3. **兜底 2**：每小时 `send_pending_reminders` 会捡走仍未送达的日志。
4. 投递逻辑抽成 `NotificationDispatcher.deliver_log()`（抢占 → 发送 → 落状态），
   即时任务与每小时重试任务**共用** → 两条路径不会对同一条通知重复发送。

**关于 worker 依赖**：本改动让通知投递也依赖 Celery worker，但这**不是新假设** ——
部署脚本本就起 `celery -A celery_app worker -Q celery,time_limit,automation,notification,...` + beat，
且每小时提醒重试 / 每日看板快照 / GDPR 保留期清理本来就是 Celery 定时任务，worker 不起时它们同样不跑。

**返回值语义变更**：`send_notification` 的 `sent` 从「已发送」变为「**已受理(已入队待投递)**」，
另加 `queued: True`。唯一依赖该字段的生产调用方是公告推送
（`apps/announcement/views.py:235` 用 `result.get('sent')` 决定是否记录 log_id）→ 语义等价
（log 一定存在，发送失败会落 `failed_reason`）。

**未改的外部调用点**：`integration/services.py` 的阿里云短信 / 企微 / moka 同步调用、
`suppliers/hmac_adapter.py`、`ssrf.py` —— 它们要么已在 Celery 任务里（不在请求路径），
要么是集成自检端点（故意同步，「测试短信」/「测试消息」），要么是供应商同步批处理（后台任务）。
真正留在请求路径上的只有通知链路这一类 → 本轮已收口。

**新增用例**：`tests/test_f3_notification_async.py`（4 条）——
请求路径**不得**同步调外部通道、任务路径才真正发送、每小时任务是兜底、已送达的不被重发。

### F4 实际落地

- `DictionaryTypeViewSet.submit` 处理「已存在项」时，原先每条 2 次查询
  （`objects.get(id=...)` + `_has_children_final` 内的 `filter(parent=item)`）→ N 条 = **2N 次**。
- 改为**批量预取**：一次取全部已存在项 + 一次取子级映射（`{parent_id: [child_id]}`），
  循环内零查询；`_has_children_final` 增可选 `live_children` 参数，不传时退回单查（其他调用方不受影响）。
- 业务语义保持不变：找不到的 `item_id` 仍由外层 `except DictionaryItem.DoesNotExist` → 400。
- 新增用例 `tests/test_f4_dictionary_nplus1.py`（4 条）：**用「3 条 vs 9 条的 SELECT 次数对比」**
  而不是写死魔法数字（数字会随无关改动漂移，对比法不会），另锁「值确实被更新」「缺失项仍 400」
  「有子级不可停用」三条语义。

### 卡 H1｜整跑 flaky 根因治理 ✅ 已完成（2026-10-21）

**问题**（4 个根因，全部实测复现）：

1. **补种打到了开发库** —— `pytest_runtest_setup(tryfirst)` 跑在 `item.setup()` 之前，
   而 pytest-django 在 session 级 `django_db_setup` 里才把库名切成测试库
   → 补种写进 `ats_test`（实测 552 行 `role_permission`）→ 开发库迁移只到 `core.0040`
   → `(1054, Unknown column 'permission_resources.sub_module')` → 被静默吞掉
   → **测试库的种子一次都没补回来** → 下游批量 403。
2. **瞬时数据库错误被吞** —— 三处 `except Exception: pass` 把 MySQL 1213 死锁 / 1205 锁等待超时
   这类**可重试**的错误一并吞掉 → 补种静默失效。
3. **没有守卫** —— 模块级 `pytestmark = pytest.mark.django_db(transaction=True)` 的文件，
   **每个**用例 teardown 都 flush 整库 → 污染面是整个文件。
4. **共享测试库被并发改动** —— `--reuse-db` 下多进程共用一个 test 库
   → 死锁 / `(1060, Duplicate column)` / 失败集合逐轮不同。

**改法**：
- `tests/fixtures_common.py` 加 `in_test_database()` 闸门（用模块导入时的 `_BASE_DB_NAME` 比对）
  → 不在测试库时**直接跳过补种**；该窗口由 session 级 `_ensure_v2_schema` 覆盖。
- 三个新原语替代裸 `except Exception`：
  `_is_transient_db_error()`（只把 `OperationalError`/`InterfaceError` 算瞬时）、
  `_run_with_retry()`（退避重试 3 次）、
  `_record_repair_failure()`（失败**记入 `_SEED_REPAIR_FAILURES` + 打 warning**，不再静默），
  并由 `seed_repair_failures()` 对外暴露。
- 新增扫描器 `apps/django/scripts_scan_module_level_transaction.py`（**AST 静态判定**，
  方法级装饰器不算违规）+ `KNOWN_EXCEPTIONS` 登记机制 + **CI 硬门禁**
  + 本地整跑用例 `tests/test_module_level_transaction_guard.py`。
- 新增 `apps/django/scripts_run_isolated_tests.py`：用**独立库名**跑整跑（与共享库零交集），
  启动前做权限预检，不可用时打印需要 DBA 执行的授权 SQL。
- 附带：`pytest.ini` 写死的 `--basetemp` 改为由根 `conftest.py` 的 `pytest_configure`
  提供**每轮唯一**目录（pytest 对已存在的 basetemp 会 `rm_rf` → 沙箱拦删 → 12 例 setup error）。

**验证**：新增 20 条用例（补种可靠性 15 + 守卫 5）全绿；
隔离库整跑 **3293 passed / 12 skipped / 0 failed / 0 errors**（78.6s，且不需手动指定 `--basetemp`）；
共享库整跑对照 **3289 passed / 0 failed / 0 errors**（78.5s）；
整跑日志里的 `[seed-repair]` 告警只剩 2 条且都是单测刻意触发 → **真实补种失败为 0**。

### 卡 H2｜前端 localStorage 兜底 ✅ 已完成（2026-10-21）
