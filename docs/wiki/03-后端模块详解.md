## 一、核心支撑层（8 个）

### 3.1 core — 用户 / 组织 / 认证 / 权限 / 健康

**职责**：系统基石。用户与部门组织架构、JWT 认证、V1+V2 双权限体系、健康检查、WebSocket 通道。

**关键模型**（`apps/core/models.py`）：

| 模型 | 表名 | 说明 |
|---|---|---|
| `User` | `auth_user`（默认） | 继承 `AbstractUser`，扩展：工号 `employee_id`、手机号、部门 FK、上级 FK、职务/职级、VP、摩卡用户 ID 等 |
| `Department` | `departments` | 树形结构（`parent`/`path`/`sort_order`），含负责人、VP、HRBP |
| V2 权限模型（`models_permission_v2.py`） | `roles` 等 9 表 | 见下表 |

**V2 权限 9 表**（`apps/core/models_permission_v2.py`，T01.1 真实建表）：

`roles` / `user_roles` / `permission_resources` / `permission_templates` / `role_permission` / `management_units` / `tenant_configs` + V1 备份 `roles_v1_backup` / `user_roles_v1_backup` / `permissions_v1_backup` / `role_permissions_v1_backup`。

**关键类与函数**：

| 符号 | 文件 | 说明 |
|---|---|---|
| `LoginView` | `views_auth.py` | 支持 username/工号/邮箱/手机号登录，签发 `RefreshToken`，返回用户+部门+角色 |
| `has_perm(user, resource_code)` | `permission_check.py` | V2 核心判断：UserRoleV2 → RolePermissionV2 匹配资源码；超管 bypass；schema 缺失保守返回 False |
| `resolve_scope(user)` | `scope_resolver.py` | L1-L4 数据范围堆栈：L1 用户级 `management_unit_ids` → L2 角色级 `default_data_scope_type` → L3 租户全局配置 → L4 兜底 SELF |
| `V2Permission` | `permissions_v2.py` | DRF permission 类，调 `has_perm()` |
| `ScopeQuerysetMixin` | `permissions_v2.py` | 按 `department_ids` / `management_unit_ids` 过滤 queryset（IDOR 防护） |
| `ConditionalCsrfMiddleware` | `middleware.py` | API 路径豁免 CSRF，admin 路径保留 |
| `RequestIdMiddleware` | `middleware.py` | 注入 X-Request-ID |
| `NotificationConsumer` / `ApplicationUpdateConsumer` | `consumers.py` | WS 消费者 |
| `push_to_user()` / `push_to_application()` | `routing.py` | 服务层同步推送入口 |
| `bootstrap.py` | | 启动引导（权限资源同步等） |

**URL 前缀**：`auth/`（`urls_auth.py`）、`users|departments|roles|permissions`（`urls.py`）、`permissions/resources|templates|...` 9 端点（`urls_permission_v2.py`）、`/health/`（`urls_health.py`）。

**管理命令**：`init_demo_data`、`migrate_v2_data`、`seed_v2_init`。

### 3.2 field_acl — 字段级 ACL

**职责**：按角色控制 API 返回字段的可见性（隐藏/脱敏），R2 接入。

**关键**：`FieldAclService`（`services.py`）——在序列化期对字段做过滤/掩码；`mixins.py` 提供 ViewSet 接入混入；`signals.py` 保持缓存一致。表：`field_acls`。

**URL**：`field-acl/`。

### 3.3 audit — 审计日志

**职责**：全站写操作与错误响应审计。

**关键**：

| 符号 | 文件 | 说明 |
|---|---|---|
| `AuditMiddleware` | `middleware.py` | 记录非 GET 写操作 + 错误响应；失败计数、日志降级、熔断保护（审计故障不阻断业务） |
| `AuditLog` | `models.py` | 表 `audit_logs`（含索引优化迁移 0002） |
| `AuditService` | `services.py` | 信号驱动的显式审计（BUG-6：需显式传 operator） |

**URL**：`audit-logs/`。

### 3.4 dictionary — 数据字典

**职责**：枚举值 single source of truth（如阶段类型 `recruitment_stage_type`），供前后端统一引用。

**关键**：`DictionaryType` / `DictionaryItem` 模型；`registry.py`（注册表）；`seed_context.py`（种子上下文）；管理命令初始化。

**URL**：`dictionary-items/?type_code=xxx`、`dictionary-types/`（挂在 api/v1 根下）。

### 3.5 notification — 通知中心

**职责**：通知模板管理 + 四渠道分发。

**关键**：`NotificationDispatcher.dispatch()`（`services.py`）按 channel 路由：

| 渠道 | 实现 |
|---|---|
| `IN_APP` | 站内信（配合 WS 推送） |
| `EMAIL` | Django email backend |
| `SMS` | SMS provider（env 配置，默认 mock） |
| `WECOM` | 企业微信（CORPID/SECRET/AGENTID） |

模型：通知模板、通知日志；`tasks.py` 异步发送。

**URL**：`notifications/`。

### 3.6 gdpr — 数据合规

**职责**：数据主体请求（访问/删除/匿名化）、验证码核验、留存清理。

**关键**（`services.py`）：

| 函数 | 说明 |
|---|---|
| 请求提交服务 | 创建 `GDPRRequest`，验证码存 hash、返回明文 code 供邮件/SMS 发送 |
| 验证码校验服务 | 检查状态/过期/锁定/尝试次数，timing-safe hash 比对 |
| 匿名化/留存清理 | 软删 + 匿名化 + 定期清理（Celery） |

**URL**：`gdpr/`。

### 3.7 integration — 外部集成

**职责**：第三方系统（Moka 等）配置与同步，敏感凭证加密存储。

**关键**（`crypto.py`）：`_fernet()` 读取 `INTEGRATION_FERNET_KEY`；`encrypt_secret` / `decrypt_secret` / `encrypt_secret_dict` / `decrypt_secret_dict`（AES-128-CBC + HMAC-SHA256）。模型：集成配置 + 同步日志。

**URL**：`integrations/`。

### 3.8 common — 公共基座

**职责**：所有 app 共用的模型基类、工具、异常、分页。

| 符号 | 文件 | 说明 |
|---|---|---|
| `FullAuditModel` | `models.py` | 审计字段基类（created_at/updated_by 等），业务模型统一继承 |
| `BaseAppConfig` | `base.py` | app 配置基类（BigAutoField + signal 钩子） |
| `EncryptedCharField` | `encryption.py` | Fernet PII 字段加密（明确不引入 django-cryptography，理由见文件头注释） |
| `custom_exception_handler` | `exceptions.py` | DRF 全局异常处理 |
| `StandardResultsSetPagination` | `pagination.py` | 标准分页 |
| `retryable_scheduled_task` | `celery_utils.py` | 调度任务统一重试/计数/告警装饰器 |
| `masking.py` / `filters.py` / `mixins.py` / `utils.py` | | 脱敏、过滤器、混入、杂项工具 |

## 二、流程域（4 个）

### 3.9 process — 招聘流程（核心）

**职责**：可版本化的招聘流程定义：阶段、流程、流程-阶段连线、模板、阶段规则。

**关键模型**（`apps/process/models.py`，10 个模型）：

| 模型 | 表名 | 说明 |
|---|---|---|
| `RecruitmentStage` | `recruitment_stages` | 阶段：code/name/type/status、builtin/start/end 标记 |
| `RecruitmentProcess` | `recruitment_processes` | 流程：编号/名称/当前版本/适用范围/模板/启用/归档 |
| `ProcessStageLink` | `process_stage_links` | 流程↔阶段连线（有向图） |
| `ProcessTemplate` | `process_templates` | 流程模板 |
| `StageRule` | `stage_rules` | 阶段规则 |
| 其他 | | 进入条件/表达式等相关模型 |

**关键 ViewSet**（`views.py`）：`RecruitmentStageViewSet`（`disable/enable/references`）、`RecruitmentProcessViewSet`（`archive/clone-version/list-versions/batch-screen/batch-recommend`）。**版本化设计**：申请单冻结创建时版本（`workflow_version`），流程升级后存量申请走旧版本完成。

**URL**：`stages/`、`processes/`（旧别名 `recruitment-processes/`）、`process-stage-links/`、`stage-rules/`、`expressions/`。

### 3.10 entry_condition — 进入条件

**职责**：定义候选人/申请进入某阶段的条件规则。表：`entry_condition_rules`。

**URL**：`recruitment-rules/entry-conditions/`（别名 `entry-condition-rules/`）。

### 3.11 time_limit — 阶段限时

**职责**：阶段停留时长规则 + 超时巡检。Celery Beat `check-stage-time-limit` 定时扫描超时申请触发归档/提醒。表：`stage_time_limit_rules`。

**URL**：`time-limit-rules/`。

### 3.12 automation — 自动化规则引擎

**职责**：事件驱动的规则执行。

**执行管线**（`services.py`）：

```
触发事件 → 加载规则 → 按优先级评估 → 执行动作 → 记录日志 → 失败率/熔断
```

**关键类**：`AutomationEngine`——动作类型 `AUTO_ADVANCE`（自动推进）/ `SKIP_TO`（跳转阶段）/ `REMIND`（提醒）/ `REJECT_TO_POOL`（拒入人才库）。表：`automation_rules` / `automation_logs`。`signals.py` 监听业务事件触发。

**URL**：`automation-rules/`。

## 三、业务域（17 个）

### 3.13 candidate — 候选人主档

**职责**：候选人主数据 + 9 态 FSM。

**关键**：

| 符号 | 说明 |
|---|---|
| `Candidate`（表 `candidates`） | 主模型；`current_state = FSMField(protected=True)`；`id_card_hash` 不可逆哈希查重（BUG-1 修复） |
| `CandidateState` | 9 态：APPLIED/IN_PROCESS/OFFER_SENT/PENDING_ONBOARDING/ONBOARDED/PROCESS_FAILED/WITHDRAWN/TALENT_POOL/PROCESS_PAUSED |
| `@transition` 方法 | `enter_process`/`send_offer`/`move_to_pool`/`mark_onboarded`/`withdraw`/`mark_process_failed`/`pause_process` 等（BUG-5 补齐 5 个缺失 transition） |
| `CandidateService`（`services.py`） | 业务编排（撤回等被 application 服务调用） |
| `CandidateViewSet`（`views.py`） | 含 `/transition` action（`CandidateStateTransitionSerializer`） |
| `CandidateTag` / `CandidateHistory` | 标签 / 历史表 |

**URL**：`candidates/`。

### 3.14 add_candidate — V2 新建候选人

**职责**：新版「上传简历 → 解析 → 查重 → 评分 → 批量建档」流程。

**关键**：

| 符号 | 文件 | 说明 |
|---|---|---|
| `ParseJob` | `models.py` | 解析任务：状态/阶段/进度/文件/解析结果/查重结果，表 `add_candidate_parsejob` |
| `UploadAndParseView` | `views.py` | 校验文件数量/大小/类型，建 ParseJob，异步触发 `parse_resume_task` |
| `BulkCreateView` | `views.py` | 批量建档入口 |
| SSE 评分流 | `views.py` + `sse.py` | `scoring/stream/` 返回 `text/event-stream` |
| `BulkCreateService.create_batch(drafts, actor)` | `services/bulk_create.py` | 事务原子执行，任一失败全量回滚 |
| `DuplicateCheckService.find()` | `services/duplicate_check.py` | 按 phone/email/id_card/moka_id 查重，判定 `clean/unocc/occupied` |
| `ResumeParserService.parse()` | `services/resume_parser.py` | 封装 Affinda SDK（认证/超时/配额/HTTP 错误处理） |
| `ScoringService.score()` | `services/scoring.py` | 四维规则引擎：技术匹配/经验匹配/学历匹配/综合素质 → 总分+及格线 |

**URL**：`candidates/add-candidate/`。

### 3.15 application — 申请单（业务枢纽）

**职责**：候选人 × 职位 的申请实例，阶段流转、抢单、软拒、流程升级。

**关键模型**（`models.py`）：

| 模型 | 说明 |
|---|---|
| `Application`（表 `applications`） | `state = FSMField`（9 态）；`workflow_version` 冻结流程版本；抢单字段 `is_grabbed/grabbed_by/grabbed_at` |
| `ApplicationStageRecord` | 阶段记录，内嵌 `StageState` 10 态（NOT_STARTED/PENDING/TO_BE_SCHEDULED/PROCESSING/PASSED/FAILED/SKIPPED/REJECTED/TIMEOUT/ARCHIVED） |
| `ApplicationHistory` | 流转历史 |

**关键服务**（`services/`）：

| 符号 | 文件 | 说明 |
|---|---|---|
| `GrabService.get_pool() / grab()` | `grab.py` | 抢单池 + 认领：`select_for_update()` 防并发、状态校验、写 ApplicationHistory |
| 软拒服务 | `soft_reject.py` | 统计软拒次数（跨阶段/跨申请），达阈值自动移入人才库 |
| `resolve_stage_mapping()` | `stage_mapping.py` | 升版本/换流程时解析下一阶段落点（共享核心） |
| `ApplicationService` | `__init__.py` | 申请编排：`upgrade_workflow_version()` 等；FSM protected 字段强制走 @transition |

**URL**：`applications/`、`grab-pool/`（独立 URLconf，避免与 ApplicationViewSet 路由冲突）。

### 3.16 demand — 招聘需求

**职责**：用人部门提需求 → 审批 → 招聘。`Demand`（表 `demands`）FSM 8 态（DRAFT→PENDING→APPROVED→RECRUITING→COMPLETED，旁路 REJECTED/PAUSED/CANCELLED）。`DemandApproval` 审批记录、`DemandSetting` 设置。`DemandConfigView` 提供全局配置端点 `system/config/demand`。

**URL**：`demands/`。

### 3.17 position — 职位

**职责**：职位发布与管理。`Position`（表 `positions`）FSM（DRAFT→PENDING_PUBLISH→PUBLISHED→RECRUITING→…，含 PAUSED/CLOSED 等），含 headcount（计划/已招）、流程版本。

**URL**：`positions/`。

### 3.18 offer — Offer 管理

**职责**：Offer 审批、发放、谈判、接受/拒绝、PDF 生成（reportlab）。`Offer`（表 `offers`）FSM 11 态（详见 [04-数据模型与状态机](./04-数据模型与状态机.md)）。

**URL**：`offers/`。

### 3.19 onboarding — 入职

**职责**：入职流程与待办。`Onboarding`（表 `onboardings`）FSM 7 态；`todo_list`/`todo_completed` JSON 字段管理待办清单。

**URL**：`onboardings/`。

### 3.20 invitation — 面试邀约

**职责**：邀约状态跟踪。`Invitation`（表 `invitations`）FSM 5 态（PENDING→INVITING→SUCCESS/FAILED/TIMEOUT）；`tasks.py` 超时异步处理。

**URL**：`invitations/`。

### 3.21 interview — 面试

**职责**：面试安排与评价反馈（`InterviewFeedbackForm` 对应后端）。表：`interviews`。

**URL**：`interviews/`。

### 3.22 referral — 内推

**职责**：内推码、内推记录、奖励。**特殊**：`urls_stubs.py` 寄放了 22 个全局 stub 端点（auth/register、candidates/batch/*、search 等，历史兼容层）；`urls_single.py` 提供单数 `/referral/` 别名路由。

**URL**：`referrals/` + `referral/`（别名）+ `''`（stubs）。

### 3.23 search — 全局统一搜索

**职责**：Plan P 统一搜索端点（跨候选人/职位/申请等聚合检索）。无 model，仅 APIView。

**URL**：`search/`（**必须注册在 stubs 之前**，否则被 stub 抢路由——见 `config/urls.py` 注释）。

### 3.24 resume_flow — 履历审批流

**职责**：Phase 2 T06 独立的审批流 app（特殊简历审批）。

**URL**：`resumes/approval-flows/`。

### 3.25 talent_pool — 人才库

**职责**：公共人才库（沉淀未通过/超时候选人）+ 推荐。表：`talent_pool_entries` / `talent_pool_tags`；`tasks.py` 异步任务（队列 `talent_pool`）。

**URL**：`talent-pool/`。

### 3.26 channel — 招聘渠道

**职责**：渠道管理（猎头/内推/网站等）与成本核算。表：`channels` / `channel_costs`。

**URL**：`channels/`。

### 3.27 analytics — 数据中心

**职责**：报表、快照、导出任务、KPI 看板、数据订阅。表：`reports` / `report_snapshots` / `export_tasks` + KPI/订阅模型；`tasks.py`（队列 `analytics`）；`models_data.py` + `urls_data.py` 提供数据中心 KPI（`/data/kpi`）与订阅（`/data/subscriptions`）。

**URL**：`analytics/`、`data/`。

### 3.28 mou — MOU 大客户协议

**职责**：大客户协议（协议、容器、互斥组）。4 个 ViewSet + audit-logs stub，挂 `permissions-v2/` 前缀（历史原因）。表：`mou_agreements` / `mou_containers` / `mou_mutual_exclusion_groups`。

**URL**：`permissions-v2/`。

### 3.29 announcement — 制度公告

**职责**：招聘专家查看 / HR 及以上维护的制度公告。

**URL**：`announcements/`。

### 3.30 campus_control — 校招管控

**职责**：校招人员比例管控系统：规则 / 人员 / 看板 / 规划 / 校验。

**关键**：`calc.py`（比例计算算法，配套测试 `test_calc.py`）、`io_xlsx.py`（Excel 导入导出，openpyxl）、`constants.py`、`sample_data.py`。

**URL**：`campus/`。
