## A. 一页结论

**整体质量评级：良（Good，含必改项）**

**一句话总评**：结构扎实、自我诚实，是当前三份文档中最新最准的一份；但权限描述与代码不符、P0-6「回写候选人」数据契约缺失、active 接口 `recruit_type` 参数名写错——这三处不修，文档无法作为 P0-6 的权威规格。

**最关键的纠偏（先说结论，免得被带偏）**：
> 主理人怀疑的「权限模型大概率未真正实现」——**经核对代码，这个怀疑是错的**。权限门禁确实已实现（`SceneRuleViewSet` 组合了 `IsAuthenticatedReadOnly` + `SystemOrAdminPermission` 做三档判定）。真正的问题是：① PRD §2.2 把「系统预置仅超管可改」写死了，但代码已**放宽为 HR 及以上可改**；② 架构文档却只写了 `IsAuthenticatedReadOnly`（暗示无角色门禁）。三份文档对同一个安全关键事实说法互相打架，这才是要修的。

## B. 需要更新的条目清单（按严重度排序）

### 阻断级 / 必须修（影响文档可信度与 P0-6 落地）

#### B-1【权限模型：文档与代码不符】——经代码核实，非假设
- **位置**：PRD §2.2 角色矩阵（第 96–108 行「编辑系统预置标签/规则 ✅仅超管」）、§13.1（「未接入 V2 权限码」）、§12.2 错误码 40300/40301/40310；架构文档第 37 行（`permissions.py # IsAuthenticatedReadOnly（写方法需登录）`）。
- **问题（已读代码确认）**：
  1. 架构文档第 37 行只写 `IsAuthenticatedReadOnly`，但该类的设计语义是「只校验登录，写权限交给同 view 的其它 permission_classes」。`SceneRuleViewSet` 实际是 `permission_classes = [IsAuthenticatedReadOnly, SystemOrAdminPermission]`（`rule_view.py:84`），后者对非安全方法按 `_is_admin_user`（超管 OR HR 及以上）门禁。**角色门禁是真实存在的**，架构文档那行描述会让人误以为「只有登录校验」。
  2. PRD §2.2 矩阵写「系统预置标签/规则 仅超管可改」，但 `SystemOrAdminPermission.has_object_permission` 对 system/custom 一律返回 `_is_admin_user`（`permissions.py:88-99`），且 `rule_view.py:165-171` 注释明示「Item2：系统预置规则由'仅超管可改'放宽为'HR 及以上可改'」。**代码已放宽，PRD 未同步。**
  3. 好消息：系统预置「不可停用」确有兜底——`partial_update` 强制 `data['enabled'] = True`（`rule_view.py:171`）；「不可删除」`destroy()` 对 system 规则直接 40310（`rule_view.py:216-221`，注释「即使超管」）。这两项 BR-7 是**真落实**的。
  4. §13.1「未接入 V2 权限码」字面为真（确实没用未来那套 V2 体系），但**容易读作『无任何权限校验』**，而实际已有本地三档判定。属表述误导。
- **为什么是问题**：安全关键事实三份文档互相矛盾，PM 据以做排期/安全评审会得出相反结论。
- **具体修订建议（可直接抄）**：
  - PRD §2.2 矩阵「编辑系统预置标签/规则」一行改为：`✅ 超管 / HR 及以上（已放宽，见 §13.1 注）`；并在矩阵下方加注：
    > 注：系统预置资源的写权限当前由 reason-library 本地三档判定实现（超管 / HR 及以上 / 普通用户只读），**非**未来 V2 权限码体系。系统预置规则「不可停用、不可删除」由写路径强制兜底，不依赖角色勾选。
  - PRD §13.1 改写为：`原因库当前使用本地三档权限判定（apps.core.permissions 的 is_super_admin / is_hr_or_above），已覆盖写操作门禁；尚未接入项目规划的 V2 权限码体系，待其落地后需同步改造。`
  - 架构文档第 37 行改为：`permissions.py # 本地三档判定：IsAuthenticatedReadOnly(登录) + SystemOrAdminPermission(对象级：system→超管/HR+，custom→HR+；system 规则 enabled 强制 True、不可删)`
- **需先确认**：请 PM（兵哥）拍板——「系统预置 HR 及以上可改」是**有意的放宽**还是 **PRD 未同步**？若是后者，代码需收紧回超管；若是前者，上面 §2.2 改写即可。（这是产品决策，我不能替你定。）

#### B-2【P0-6 回写契约完全缺失】——需架构/研发定义，我不能凭空写
- **位置**：PRD §6.3 路线图④「归因数据回写候选人记录 + BI 消费」；§11.7 接口清单（无候选人写回端点）。
- **问题**：reason-library 是**纯配置模块**——它只提供 `GET /active/` 让业务端**读取**归因选项（`getActiveRule()`）。业务页面把选中的 `reason_tag_id` 列表**写回候选人**走的是 ATS 候选人模块，三份文档**完全没有定义**：哪个接口、落到候选人哪张表的哪个字段、是否进入 `CandidateHistory` 审计链、BI 消费的是哪张宽表/哪个字段。
- **为什么是问题**：P0-6 被你自己定性为「缺失则价值为零」的最高优先级，而它的**闭环最后一步（数据落库+审计+BI）没有契约**，等于验收标准 AC-14 缺了后半段，无法判定"完成"。
- **具体修订建议（框架，需架构/研发填实）**：
  - 在 PRD 新增 §11.8「业务端归因回写数据契约」，明确：① 业务页调用 `GET /active/?scene=X&recruitType=Y` 取选项；② 选中后调用 `PATCH /candidates/{id}/` 或专属 `POST /candidates/{id}/reasons/` 写入 `reason_tag_ids` + `scene` + `recruit_type` + 操作人；③ 该写操作**必须**进 `CandidateHistory`（可审计、可回溯）；④ BI 消费字段口径（与 §13.2「停用规则不计入生效归因」对齐）。
  - AC-14 拆为「六场景各一条 + 回写一条」共 7 条验收，回写那条明确校验"写入后可在 CandidateHistory 查到且 BI 口径一致"。
- **需先确认**：此契约必须由**架构/研发**定义（涉及候选人域与审计链），我不能凭空编接口。列为 P0-6 的硬前置。

#### B-3【active 接口 recruit_type 缺失且参数名写错】——经代码核实
- **位置**：PRD §11.7（第 650 行 `GET .../active/?scene=X`）、§5.7（第 337 行 `?scene=&recruit_type=`）、架构文档 §5（第 106 行 `GET /active/?scene=X`）。
- **问题（已读代码确认）**：
  1. 实际参数名是 **`recruitType`**（camelCase）——`active_view.py:39` 只读 `request.query_params.get('recruitType')`。PRD §5.7 写的 `recruit_type`（snake）**对不上**，业务端照抄会拿不到类型维度。
  2. §11.7 与架构 §5 的示例**根本没带招聘类型**，但 BR-1/§3.3/US-1 把「场景×招聘类型」二维作为核心卖点。
  3. 更要命：`active_view.py:37-38` 与 `active_query_service.py:48-49` 注释明示——**前端当前没真正传 recruitType**，不传时退化为纯按场景兜底。也就是说，二维能力后端支持、前端没接。
- **为什么是问题**：若 P0-6 接入不强制业务端传 `recruitType`，则「校园招聘的简历筛选单独配置」(US-1) 等二维承诺会**静默失效**，所有人看到的是场景级兜底。这是 P0-6 验收的隐形地雷。
- **具体修订建议（可直接抄）**：
  - §11.7 改为：`GET /api/v1/reason-library/active/?scene=筛选不通过&recruitType=social   # recruitType 业务端接入时必传，不传退化为场景级兜底`
  - §5.7 同改参数名为 `recruitType`。
  - 架构 §5 同改，并补一句：`recruitType 参数名 camelCase；不传时按场景兜底（历史兼容），业务端接入须传以启用二维。`
  - 在 AC-14（或 P0-6 验收）增加一条：**业务端六个场景接入时必须携带 recruitType 并按 (场景,类型) 命中规则，否则视为未达标。**
- **注**：以上为「示例/参数名」修正，已核实代码；"前端是否已接"需前端研发在 P0-6 排期时确认。

2. **结构完整且对齐工程现实**：用户角色、User Story、MoSCoW 优先级、Given/When/Then 式 AC、数据字段、错误码、决策记录（§14.2）一应俱全，且 AC 能对应到测试函数名，说明 PRD 与研发是真对齐写的。
3. **业务规则凝练**：BR-1~BR-11 把"优先级/唯一归属/兜底/只增不删/单一默认规则"等核心不变量讲清楚，且多数被代码落实（如 UNIQUE(scene,recruit_type)、single preset default、delete→disable）。

### Gaps（还缺什么）
1. **P0-6 闭环契约为零**：最大优先级项的"数据怎么落库、怎么进审计、BI 怎么吃"完全空白（B-2）。

3. **路线图不可执行**：P0-6 无 owner/时间/逐场景 AC（I-5）。

6. **QA 报告失真**：日期/计数/规则数陈旧且前后矛盾（I-1）。

### Risks（承诺若不实会反噬）
1. **i18n "100% 对齐 + 自动化审计"无证据**（I-4）：一旦被要求演示审计脚本或抽查未翻译文案，立即破功。属典型"假绿"，最该先排雷。
2. **权限"仅超管可改系统预置"与代码(HR+)冲突 + 架构"仅登录"误导**（B-1）：安全评审或 audit 抽查时，会发现普通 HR 也能改系统词表——若文档承诺了"仅超管"，就是合规层面的反噬。
3. **AC-3 绿灯误导**（I-8）：把"仅超管可改"标绿，实际 HR 可改，验收时被挑战会被动。
4. **二维能力"静默失效"风险**（B-3）：前端不传 recruitType，US-1 的"校招单独配置"卖点实际交付不了，却没人察觉——直到业务方问"为什么校招和社招选项一样"。
5. **文档新鲜度混乱**：PRD(10-10) > 架构(10-08 但体陈旧) > QA(09-20 但被补丁)——拿任何一份当"最新真相"都会踩坑。

**关于"真实可靠、不弄虚作假"的总判断**：这份 PRD 在**大面上诚实**（主动暴露 P0-6 缺口、承认权限未接 V2 码），值得肯定；但在**三处具体承诺上踩了"假绿"边缘**——i18n 审计（无脚本）、AC-3（测试只覆盖 DELETE 且字面与代码冲突）、权限矩阵（与代码/架构互不一致）。这三类不是"恶意造假"，而是"写了理想态/旧状态却没回填现实"，但在安全与验收语境下同样危险，必须修。
