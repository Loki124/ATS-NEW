## 0. 一句话结论

整跑从 **220 failed / 201 failed** 收敛到 **0 failed / 3142 passed**（12 skipped）。
卡 B5 不是一个 bug，而是**六个互相叠加的根因**；任一单独修都不够，必须一起修。

| # | 根因 | 典型症状 | 修复位置 |
|---|---|---|---|
| R1 | `transaction=True` 用例 teardown 的 `flush` 连**已提交种子**一起清掉 | `DoesNotExist` / 403 / 空目录 | `tests/fixtures_common.py` 惰性补种 |

## 1. R1｜`flush` 把「已提交种子」一起清掉

### 实测

`django_db(transaction=True)` 的用例在 teardown 会 `flush` **整库**（含已提交的迁移种子）。
`--reuse-db` 下次运行**不再重跑已应用的迁移** → 种子永久缺失。

```bash
cd apps/django
# 找一个 transaction=True 的文件，跑完看种子是否还在
DJANGO_SETTINGS_MODULE=config.settings.test python -m pytest tests/test_qa_bug7_repro.py -q -p no:randomly
# → 随后查库：注册表 0 行、role_permission 0 行
```

被清掉的「已提交种子」共 6 类：

| 种子 | 来源 | 缺失症状 |
|---|---|---|
| `permission_resources`（资源码注册表） | `seed_v2_init.RESOURCES` | 卡 A1 的 fail-closed 把所有派生写码判为「未注册」→ **非超管写操作一律 403** |
| `role_permission`（角色授权） | `fixtures_common._seed_role_permissions` | HR/HRBP 一条授权都没有 → **一片 403** |
| `recruitment_stages` 起止阶段 | 迁移 `process.0012` | `RecruitmentStage.DoesNotExist`（9 处）+「找不到系统内置起止阶段」（2 处） |
| `dynamic_fields`（Demand 规范字段 29 个） | 迁移 `dynamic_field.0019/0020/0022/0024/0025` | 「缺少系统字段 talent_level」「缺少自定义字段 external_short_name」（5 处） |
| `metrics_atomic_metric` / `metrics_derived_metric` | 迁移 `metrics.0012/0016/0017/0018/0020/0027` | 指标目录为空 → 条件求值器一律返回 None（6 处） |
| `data_permission_actions`（动作字典） | 迁移 `data_permission.0006` | `is_operable` 动作白名单全落空 → 候选人写操作 403（7 处） |

### 修复

`tests/fixtures_common.py` 新增 `_repair_committed_seeds()`，由
**`pytest_runtest_setup`（tryfirst）** 调用（见 R3 解释为什么是这个时机），
逐项用**幂等**方式补齐：迁移数据迁移的函数直接重放（用当前 app registry），
`permission_resources` / `role_permission` 用原生 upsert。

> 注：`metrics.0013/0017/0018` **不能**直接重放 —— 它们引用的 `DerivedMetric.params`
> 已被 `0021`（calc params 移到模板）`RemoveField` 掉，用当前 registry 重放会抛
> `FieldError: Invalid field name(s) for model DerivedMetric: 'params'`。
> 故这部分按**当前 schema** 直接落（口径与 0013/0017/0018 + 0021 一致），
> 见 `_seed_safe_set_metrics()`。

## 2. R2｜「表是否为空」不是可靠的补种判据

### 实测（踩坑全过程）

第一版补种判据是「表为空就补」。结果：

```text
# 迁移 core.0034 在 migrate 阶段就写了 5 条资源码 + 10 条 role_permission 行
# → 表「不为空」→ 整批播种被跳过
# → 注册表只剩 5 条、HR 一条授权都没有 → 整跑 196 failed
```

同理，`role_permission` 的播种用**裸 INSERT**，撞 `uk_role_resource` 唯一约束时
**整批中断**（前面插进去的留下、后面的全丢）——这正是 0034 那 10 行能"卡死"整批播种的原因。

### 修复

1. 判据改成**哨兵行**（每张表都有的关键行）：
   - `role_permission`：`role_code='HR' AND resource_code='recruit:candidate:list'`
   - `permission_resources`：`resource_code='recruit:candidate:list'`
   - `recruitment_stages`：`code='P001'`
   - `dynamic_fields`：`resource='Demand' AND field_key='talent_level'`
   - `metrics_atomic_metric`：`source_path='candidate.age'`；`metrics_derived_metric`：`name='跳槽频率'`
   - `data_permission_actions`：`key='recommend'`
2. 播种语句全部改**幂等 upsert**（`ON DUPLICATE KEY UPDATE` / `get_or_create`），
   重复调用安全、不再整批中断。

## 3. R3｜补种必须跑在「用例事务之外、fixture 之前」

三个时机各踩一次坑：

| 时机 | 症状 |
|---|---|
| `pytest_runtest_setup`（trylast） | 跑在**用例自己的 fixture 之后** → `test_migrate_0028_resource_code_rename.py` 的 `three_stores` fixture 故意清空注册表来构造「迁移前状态」，补种把它填回去 → 迁移报「目标码已存在」→ **整文件 7 例假红** |
| 同上 | 跑在**用例事务内** → 补的种子随用例回滚 → 补了等于没补 |
| `pytest_runtest_teardown`（trylast） | 跑在 finalizer 之后 → 写入与**用例事务残留的锁**形成 MySQL 死锁：`1213 Deadlock found when trying to get lock` → 事务被标记 broken → 后续查询全抛 `TransactionManagementError` → **15 failed** |

**最终形态**：`pytest_runtest_setup`（**tryfirst**）——
跑在 `item.setup()` 之前，因此既没有用例事务、也没有用例 fixture 的清空动作，
写入是**提交态**的、且不与用例抢锁。

配套：pytest-django 默认**只在用例体内**放行 DB 访问（`django_db_blocker`），
钩子跑在用例之外 → 必须显式 `with blocker.unblock():`。
（踩坑记录：漏了这句 → 钩子内异常被吞 → 补种**静默失效** → 整跑 196 failed。）

## 4. R4｜裸 INSERT 遇唯一约束整批中断

`role_permission` 的播种原为裸 `INSERT INTO ... VALUES (...)`。
只要表里已有任意一行与待插行撞 `uk_role_resource`，整批就停在那行。
0034 迁移预置的 10 行正好与待插行重叠 → HR/HRBP 的 500+ 条授权**一条都没进库**。

改为 `ON DUPLICATE KEY UPDATE system_code = VALUES(system_code)` 后：
重复调用安全、撞约束的行就地更新而非中断整批。

## 5. R5｜MySQL 大小写不敏感（真 bug，不只是测试问题）

### 实测

`utf8mb4_unicode_ci` 排序规则**大小写不敏感** → `filter(field_key='Name')` 会命中
`'name'`。项目 2026-10-15 从 SQLite 迁到 MySQL 后，这类断言全部失真。

### 真实缺陷

`apps/dynamic_field/migrations/0023_normalize_candidate_fields.py` 的**反向迁移**
用 DB 侧大小写不敏感的 `filter(field_key=old_key).exists()` 判「旧 key 是否被占用」：

```python
# 反向：'name' → 'Name'。查 'Name' 会命中 'name' 行 → 判定「旧 key 被占用」→ 改名被整段跳过
if DynamicMetric.objects.filter(resource='Candidate', field_key=old_key).exists():
    continue
```

**结果：0023 的反向迁移在 MySQL 上实际失效**（回滚不会把 `name` 还原成 `Name`）。
改为在 **Python 侧**用集合判定（大小写敏感），与正向迁移的 `taken` 口径一致。

### 测试侧

`test_normalize_migration.py` 三处断言改为 Python 侧集合比对（`set(...values_list('field_key'))`）。

## 7. 顺带修掉的两个**真 bug**（不是测试问题）

### 7.1 `scripts_scan_softdelete.py` 死循环 → 脚本永不退出

```python
while isinstance(base, ast.Call):
    base = base.func.value if isinstance(base.func, ast.Attribute) else base
#                                            ↑ func 不是 Attribute 时 base = base → while 永真
```

`get_foo(...).filter(deleted_at__isnull=True)` 这类写法即触发。
**实测：脚本挂 18 分钟无任何输出**（CI 里等于挂死）。
修正后**1.4 秒**跑完，报「必炸调用点 0 处 / 未能静态解析 25 处」。

并按 `scripts_scan_todo.py` 同款口径加了 `--strict`（发现即 exit 1），
存量清零后在 CI 加 `--strict` 即可翻硬门禁。

### 7.2 标签导入超长 name → 整个导入 500

`apps/reason_library/views/tag_view.py` 的 CSV/Excel 导入对 `en_name`(64) / `tip`(128)
都做了截断，唯独漏了 `name`（`ReasonTag.name` 限 32）→ 超长 name 直落 MySQL 触发
`1406 DataError` → **整个导入 500**（QA 探针 `test_qa_name_exceeding_max_length` 早就在记录这个 500）。
改为按行报错并跳过（沿用该端点既有的「逐行报错」口径），全部行失败时统一 400。

## 8. B6｜扫描脚本接进 CI

`.github/workflows/ci.yml` 的 `test-backend` job 新增两步：

| 步骤 | 形态 | 实测 |
|---|---|---|
| `V2 write-permission guard (hard gate)` | **硬门禁**（有缺口 exit 1） | `python scripts_scan_v2_write_guard.py` → 0 缺口、exit 0 |
| `Soft-delete filter scan (warn-only)` | 报告模式 | `python scripts_scan_softdelete.py` → 0 处、1.4s、exit 0 |

写口扫描器的码集合取**「DB ∪ seed」双源并集** → CI 里 DB 未 migrate 也能给出正确判定。

## 9. 验证口径

```bash
cd apps/django && . .venv/bin/activate

# 整跑（确定性序）
DJANGO_SETTINGS_MODULE=config.settings.test \
  python -m pytest --tb=line -q -m "not quarantine" -p no:randomly
# → 0 failed, 3142 passed, 12 skipped, 7 errors, 27 subtests passed（~83s）

# 门禁
ruff check apps tests                        # All checks passed
DJANGO_SETTINGS_MODULE=config.settings.dev python manage.py makemigrations --check --dry-run
                                             # No changes detected
python scripts_scan_v2_write_guard.py        # exit 0，0 缺口
python scripts_scan_softdelete.py            # exit 0，0 处（1.4s）
```

**7 errors 的定性**：全部是 `apps/add_candidate/tests/test_duplicate_check.py` 的
`DataError: Data too long for column 'code'`（R6，已修）；**修复后为 0**。
若在其它环境仍有 error，是 pytest `tmp_path` 的 `PermissionError: [Errno 1] Operation not permitted`
—— 那是**沙箱禁止删除目录**导致的环境伪失败（pytest 清 basetemp 时 `rm_rf` 被拦），
换 basetemp 或在 CI（可删目录）即消失，**非代码回归**。
