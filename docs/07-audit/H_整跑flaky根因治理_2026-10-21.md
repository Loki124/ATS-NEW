# H — 整跑 flaky 根因治理 + 前端测试环境兜底（2026-10-21）

> 起因：整改卡 **C4**（手机号/邮箱落库加密）验收时，连续三轮整跑出现
> **失败集合逐轮不同**的异常（20 errors → 18 failed+11 errors → 8 failed+16 errors）。
> C4 本身是绿的（隔离库整跑 3269 passed / 0 failed），但排查过程暴露出
> **测试基础设施层面的 4 个真问题** —— 它们会让「整跑结果不可信」，
> 也就无法判断任何一次失败算不算自己的。
>
> 本批把这些问题逐个钉死。**新增卡 H1 / H2 / H3**（见整改计划卡 §11）。

## 1. H1｜整跑 flaky 根因治理

### 1.1 现象

同一份代码连跑多轮：

| 轮次 | 结果 |
|---|---|
| 第 1 轮（隔离库） | 3269 passed / 6 skipped / **0 failed / 0 errors** |
| 第 2 轮（共享库） | 20 errors（setup 阶段） |
| 第 3 轮（共享库） | 18 failed + 11 errors |
| 第 4 轮（共享库） | 8 failed + 16 errors |

失败在「403 权限失败」与「MySQL 1213 死锁」之间游走，**失败集合逐轮不重叠**。

### 1.2 根因一：补种打到了**开发库**（最隐蔽的一个）

`tests/fixtures_common.py` 的补种挂在 `pytest_runtest_setup(tryfirst)` 上
—— 选 tryfirst 是为了避开三个坑（用例 fixture 之后补会破坏「故意清空表」的用例、
用例事务内补会随回滚失效、teardown 补会与用例残留锁形成 1213 死锁）。

**但 tryfirst 跑在 `item.setup()` 之前**，而 pytest-django 是在 session 级
`django_db_setup` fixture 里才把库名从 `ats_test` 切成 `test_ats_test`
→ **在第一个需要 DB 的用例之前，hook 里的补种连的是开发库**。

实测后果（全部复现）：

1. **污染开发库**：往 `ats_test` 写了 **552 行 `role_permission`**；
2. **补种失败**：开发库的迁移只到 `core.0040`，没有 `permission_resources.sub_module` 列
   → 补种 INSERT 报 `(1054, "Unknown column 'permission_resources.sub_module' in 'field list'")`；
3. **失败被静默吞掉**（`except Exception: pass`）
   → **测试库的种子其实一次都没被补回来**
   → flush 清掉的种子永远缺失 → 下游用例批量 403。

> 这条是整跑 flaky 的**主因**：不是「偶发」，而是**补种机制从未真正生效过**。

**修法**：加闸门 —— `tests/fixtures_common.py: in_test_database()`
（用模块导入时记下的 `_BASE_DB_NAME` 与当前库名比对），
不在测试库时**直接跳过补种**（既不污染开发库，也不产生误导性的缺列报错）。
该窗口的补种需求由 session 级 `_ensure_v2_schema` 覆盖（它跑在 `django_db_setup` 之后 → 库名已切换）。

### 1.3 根因二：瞬时数据库错误被当成「不重要的异常」吞掉

三处 `except Exception: pass` / `except Exception: continue`：

| 位置 | 吞掉的是什么 |
|---|---|
| `fixtures_common.py::_repair_committed_seeds` → `_reseed` | MySQL **1213 死锁** / 1205 锁等待超时（瞬时，可重试） |
| `fixtures_common.py::_seed_action_dictionary` | 同上 → 动作字典没补回来 → 候选人写操作（转发/推荐/关注）一律 403 |
| `fixtures_common.py::_seed_demand_dynamic_fields` | 单个种子失败 → Demand 字段集永远缺一块 |

**修法**（三个原语，异常集收窄 + 退避重试 + 失败可见）：

- `_is_transient_db_error(exc)`：只有 `OperationalError` / `InterfaceError` 算瞬时
  （1213 / 1205 / 2006 / 2013）；`IntegrityError`（唯一约束冲突）、`ProgrammingError`（SQL 写错）
  **不重试** —— 重试没有意义，只会掩盖真因；
- `_run_with_retry(fn, label, max_attempts=3)`：瞬时错误退避重试（0.2s / 0.4s）；
- `_record_repair_failure(label, exc)`：重试用尽 → **记入 `_SEED_REPAIR_FAILURES` + 打 `RuntimeWarning`**，
  并由 `seed_repair_failures()` 对外暴露 —— 排查时先看它，而不是从下游 403 往回猜。

> **收窄异常集时踩到的第二个坑**：旧代码的 `except Exception: return True` 实际兜住了两类
> **不是失败**的语境 —— ① pytest-django 的 DB 阻断（`RuntimeError: Database access not allowed`）；
> ② `django.test.testcases.DatabaseOperationForbidden`（**继承的是 `AssertionError`，不是 `RuntimeError`**！
> 收窄时按 `RuntimeError` 接会漏掉它）→ 纯单测 / `SimpleTestCase` 子类每次都会刷一条假告警。
> 修法：新增 `_is_no_db_context(exc)` 显式识别这两类 → **静默跳过，不记为失败**。
> 这也是为什么「收窄异常集」必须配套一条「补齐被吞掉的非失败语境」的用例。

> 这条改动的价值立刻兑现：闸门修好后第一次跑，就打印出了此前被吞掉的
> `(1054, Unknown column ...)` —— **静默失效变成了可见信号**。

### 1.4 根因三：没有守卫阻止「模块级 `transaction=True`」

`django_db(transaction=True)` 的用例在 teardown 会 `flush` **整库**。
写成**模块级**（`pytestmark = pytest.mark.django_db(transaction=True)`）时，
该文件里的**每一个**用例都触发一次全库 flush → 污染面是「整个文件」。

仓库里已有 1 处：`apps/campus_control/tests/test_rule_config.py:40`
—— 其注释写明是**刻意**的（大量依赖 `save()` 内的 `select_for_update` 自动补号，
savepoint 模式下会逃逸回滚 → 编号断言不确定），已评估过代价 → **保留并登记**。

**修法**：

- 新增扫描器 `apps/django/scripts_scan_module_level_transaction.py`
  （**AST 静态判定**，不执行测试）：顶层 `pytestmark = ...` 且其值含
  `pytest.mark.django_db(transaction=True)` → 违规；
  **方法级装饰器不算违规**（只影响那一个用例）；
- 已登记的例外写在脚本的 `KNOWN_EXCEPTIONS` 里，**必须写明理由**（防「例外」变「盲区」）；
- 接进 **CI 硬门禁**（`.github/workflows/ci.yml`：`Module-level transaction marker scan (hard gate)`）；
- 另配本地整跑用例 `tests/test_module_level_transaction_guard.py`（含「扫描器能抓到造出来的违规」的自检）。

实测：**违规 0 处**（1 处已登记例外）。

### 1.5 根因四：共享测试库被并发改动

`--reuse-db` 下所有 pytest 进程共用同一个 test 库。第二个进程（另一个会话 / 另一个 agent /
另一个分支的 CI）一旦同时往这个库上应用迁移或跑用例，就会撞出：

- `(1213, 'Deadlock found when trying to get lock')` 死锁；
- `(1060, "Duplicate column name 'version'")` 同一迁移被两个进程同时应用；
- 失败集合逐轮不同。

**修法**：新增 `apps/django/scripts_run_isolated_tests.py` —— 用**另一个库名**跑整跑，
与共享库零交集；启动前做**权限预检**，不可用时直接打印需要 DBA 执行的授权 SQL：

```bash
python scripts_run_isolated_tests.py --db-name ats_t03_ci -- --tb=line -q -m "not quarantine"
python scripts_run_isolated_tests.py --db-name ats_t03_ci --precheck-only
```

> 本地 MySQL 没有 root（`ats_dev` 只有 `CREATE, DROP ON *.*`），
> **新建库只拿到默认权限、ALTER 被拒**（`1142 ALTER command denied ... django_content_type`）
> → 必须复用**已授权**的库：`ats_test` / `test_ats_test` / `ats_t03_ci` / `test_ats_t03_ci` /
> `ats_drift_repro` / `ats_0030_probe`。脚本的预检会明确告诉你缺什么。

### 1.6 附带修掉：写死的 `--basetemp` 是个坑

`pytest.ini` 原来写死 `--basetemp=/tmp/ats_pytest_bt`。pytest 的
`_ensure_relative_to_basetemp` 对**已存在**的 basetemp 会先 `rm_rf` 再 `mkdir`
→ 沙箱拦删除 → `PermissionError: [Errno 1] Operation not permitted`
→ 所有用 `tmp_path` 的用例在 **setup 阶段**整片 error（实测一次整跑 12 例）。

**修法**：改为由根 `conftest.py` 的 `pytest_configure` 提供**每轮唯一**的 `/tmp` 子目录
（`/tmp/ats_pytest_bt_<pid>_<ts>`）：只需新建、不需删旧，并发的两轮整跑也互不覆盖；
命令行显式传 `--basetemp` 时尊重调用方。

## 2. H2｜前端 localStorage 兜底（本地假红 9 个用例）

**现象**：本地 `npm test` 有 9 个用例红（`src/utils/__tests__/request.test.ts` 8 个 +
`src/api/__tests__/addCandidate.test.ts` 1 个），报错 `localStorage.getItem/clear is not a function`；
**CI 是绿的**（CI 用 Node 20，本地用 Node v25）。

**根因**（实测，非推测）：

1. Node ≥ 22 内置了一个**空的** `globalThis.localStorage`
   （原型只有 `Object.prototype`，`getItem`/`clear` 全是 `undefined`）；
2. vitest 的 happy-dom 环境**不会覆盖已经存在的全局**
   → 于是测试拿到的是 Node 的空壳，而不是 happy-dom 的可用 `Storage`。

用 `NODE_OPTIONS=--no-experimental-webstorage` 跑同样两个文件 → **15 passed / 0 failed**，
直接证明了这个因果链。

**修法**：`web/app/src/__tests__/setup.ts` 增加 `ensureLocalStorage()` ——
**只在 localStorage 不可用时**注入一个 DOM Storage 接口齐全的内存实现
（`getItem/setItem/removeItem/clear/key/length`），可用时保持原样，
不改变 happy-dom / Node 自带实现的行为。

> 仓库里其实早有同源记录：`src/router/__tests__/router.test.ts` 顶部注释写着
> 「happy-dom 测试环境可能不提供 localStorage … 直接调 `localStorage.getItem` 会抛
> "not a function"」—— 当时只在那一个文件里做了 stub 兜底，其余文件没兜。
> 这次是**一次性在 setup 层兜住**，不再逐个文件打补丁。

## 5. 未验证 / 遗留

- **未验证**：本地 MySQL 无 root，无法为新库名授权 → 隔离验证**只能复用已授权的库**
  （`ats_t03_ci` 等）。多会话并行时若各用不同库名，需要 DBA 预先授权。
- **未验证**：CI 的 backend job 本来就是独立 MySQL 容器（天然隔离），
  故 1.5 的隔离入口**只解决本地/多会话场景**，CI 侧收益有限。
- **遗留**：`apps/campus_control/tests/test_rule_config.py` 的模块级 `transaction=True`
  仍然存在（刻意保留，已登记）→ 它每次整跑仍会 flush 整库一次。
  彻底消除需要改写该文件的用例语义（依赖 `select_for_update` 的编号断言），
  属独立任务，**不建议顺手改**。
- **遗留**：本批只治了「补种不可靠」这条链。共享测试库被并发改动（根因四）
  **仍然存在** —— 隔离入口是「绕开」而非「消除」。
  根治需要 CI/本地都用「每工作区一个库名」的约定。
