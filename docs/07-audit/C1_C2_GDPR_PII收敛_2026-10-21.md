## 1. 为什么要做

诊断报告 `PROJECT_DIAGNOSTIC_2026-10-21.md` 列出的两个 P0：

| 编号 | 缺陷 | 后果 |
|---|---|---|
| **P0-7** | `apps/gdpr/services.py:288` `req.result = f'导出数据：{export_data}'`，而 `export_data` 含 name/phone/email/id_card_no 明文 | 候选人 PII **明文落库**，且 `result` 在 `GDPRRequestSerializer.fields` 里 → **API 原样吐回** |

两条都是「清一半」：明文清了、**能反查的那把钥匙留着**。

## 2. C2｜匿名化连盲索引 hash 列一起清

**改动**：`apps/gdpr/services.py` → `approve_and_forget`

```python
candidate.phone_hash = ''
candidate.email_hash = ''
candidate.id_card_hash = ''
candidate.save(update_fields=[
    'name', 'phone', 'email', 'id_card_no',
    'phone_hash', 'email_hash', 'id_card_hash',
    'updated_at',
])
```

**要点**：

1. **必须进 `update_fields` 白名单** —— `save(update_fields=[...])` 只写列出的列，漏掉哪个哪个就不落库。这是本卡最容易踩的坑（原代码已有 `update_fields` 白名单的先例）。
2. **为什么必须清**：`phone_hash` 是 salt 前置 SHA-256；手机号空间仅 ~10^10，且 `LEGACY_HASH_SALT='ats-pii'`（`apps/common/encryption.py:137`）历史上硬编码在公开源码里 → 拿到 hash 就能离线预计算反查。`apps/common/encryption.py:143` 的 `HASH_V2_REQUIRED_MAX_LENGTH=80` 说明 v2 已支持外部 salt，但**存量 v1 hash 仍可反查**。
3. **无业务副作用**：查重走 hash 列，但被遗忘权执行后该候选人本就不该再参与查重。

**验证**（两条，缺一不可）：

| 用例 | 断言 |
|---|---|
| `test_anonymize_clears_hash_columns` | ORM 层：3 个 hash 列 == `''` |
| `test_hash_columns_cleared_in_db` | **DB 层直查** `SELECT phone_hash, email_hash, id_card_hash FROM candidates WHERE id=%s` → `('', '', '')` |

第二条专门防「ORM 读到了内存值但 DB 没落库」这种假绿。

## 3. C1｜PII 明文不再落 `result` 列

### 3.1 改造后的数据流

```
approve_and_export
  ├─ 明文 export_data 组装（只在函数栈内存活）
  ├─ Fernet 加密 → gdpr_export_artifacts.payload
  ├─ req.result ← 只写摘要（无 PII）
  └─ 响应体 ← 只给一次性下载链接（含 token）
                    ↓
GET /api/v1/gdpr/{id}/export/?token=…
  ├─ 校验：超管登录 + token 未用过 + 未过期
  ├─ 解密 → 返回明文
  ├─ 擦除 payload（密文落空）+ 落 downloaded_at / download_count
  └─ 写审计 AuditLog(action=EXPORT, 只记 id 不记 PII)
```

### 3.2 新表 `gdpr_export_artifacts`

`apps/gdpr/models.py` → `GDPRExportArtifact`（迁移 `apps/gdpr/migrations/0005_gdprexportartifact.py`）

| 字段 | 作用 |
|---|---|
| `payload` | **Fernet 密文**（与 `id_card_no` 同一套密钥体系，密钥轮换时行为一致：MultiFernet 双读） |
| `token` | 一次性下载 token（`secrets.token_urlsafe(32)`，unique + db_index） |
| `expires_at` | 有效期，默认 30 分钟（`EXPORT_TOKEN_TTL_MINUTES`） |
| `downloaded_at` / `download_count` | 下载留痕 |
| `created_by` | 谁发起的导出 |

### 3.3 访问控制：三重叠加

| 层 | 手段 | 防的是 |
|---|---|---|
| 授权 | ViewSet 默认 `IsSuperAdmin` | 链接被转发给外人 |
| 一次性 | token 下载后即失效 + **密文擦除** | 链接被二次使用；DB 事后被导出时已无明文 |
| 时效 | `expires_at` 30 分钟 | 链接长期挂着被捡漏 |

> 为什么下载端点仍要求超管登录、而不是「持 token 即得」：token 只解决「一次性」，不解决「谁有资格拿」。签名 URL 一旦外泄，无鉴权端点等于裸奔。

### 3.4 `result` 列现在长什么样

```
已导出候选人 C00000001 的 4 项个人信息；导出件为一次性下载（30 分钟内有效），下载动作已留审计记录
```

**不含**姓名/手机号/邮箱/身份证号任一明文。

### 3.5 序列化器暴露面同步收窄

`apps/gdpr/serializers.py`：

- `result` 保留在 `fields`（现在是摘要，安全）。
- `submitted_email` **仍可写**（create/update 行为不变，避免静默改产品行为），但**读**时改为输出 `submitted_email_masked`（`g***@example.com`，复用 `apps/common/masking.py:mask_email`），原字段不出响应体。
  - 依据：卡 C1 的验收口径是「`GET /gdpr/requests/{id}/` 响应中不含手机号/**邮箱**/身份证号明文」——`submitted_email` 本身就是邮箱明文，不收窄则验收不过。

### 3.6 配套：超期导出件擦除

`GdprService.cleanup_expired_exports()` —— 超期未下载的导出件**保留行、擦掉密文**（下载痕迹要留）。已挂进 `apps/gdpr/tasks.py:run_retention_cleanup`（每日 beat）。

**明确高危的 2 张**（直接存候选人 PII 原文）：

- `scraped_resume.ScrapedResume` —— `raw_content` / `parsed_content` 是**整份简历原文**（含姓名、电话、邮箱、地址），`source_url` 可能带 utm/标识可回溯。
- `candidate.CandidateFieldValue` —— 动态字段值，字段键由运营配置，**内容不可静态枚举**（可能存"期望薪资"这类，也可能存"身份证号"）。

**需要兵哥拍板的 3 件事**：

1. **动态字段值（`candidate_field_values`）怎么处理？** 建议：按 `field_key` 白名单只清「身份证号/手机号/邮箱/家庭住址」等个人敏感项，其余（学历/期望薪资/意向城市）保留为业务事实。
2. **简历正文（`scraped_resumes.raw_content` / `parsed_content`）清还是脱敏？** 建议：保留解析后的结构化字段（学历/技能/经历）作为招聘事实，`raw_content` 原文整段清空。
3. **面评/推荐理由/备注类文本（`comment` / `note` / `reason` / `rejection_reason`）算 PII 还是业务事实？** 建议：这些是**招聘方写的评价**，属业务事实保留；但若文本里常被写入候选人联系方式则需正则脱敏。

> 卡 C3 的 `PROTECT` FK **不改**（改 CASCADE 会误删业务数据），改为「显式清 PII 字段」，与计划卡一致。
