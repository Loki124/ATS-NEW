## 2. 盘点补漏：FK 盘点漏了一张表

原盘点（按 `candidate` 外键找）得到 17 张表 —— 但 **`dynamic_field_values` 不在这 17 张里**：

```python
# apps/dynamic_field/models.py:408
class DynamicFieldValue(TimestampedModel):
    resource = models.CharField(...)      # 'Candidate'
    entity_id = models.CharField(...)      # 候选人 id
```

它用**泛型 `(resource, entity_id)`** 引用业务实体，**不是真 FK** → 按外键盘点必然漏掉。
而它存的正是候选人动态字段的录入值（电话/邮箱/身份证/住址都在里面）。

> 这就是「PII 有几份副本」盘点最容易被骗的地方：**只按外键找 = 只看得到有关系约束的那部分**。
> 本卡把 `resource='Candidate'` 的行也纳入了清理。

最终覆盖 **18 处存储点**（17 张 FK 表 + 1 张泛型表）。

## 4. 审计链：冲突与解法

### 4.1 冲突

`candidate_histories` 是**哈希链 + 禁改删**的不可篡改审计表：

```
row_hash = sha256(candidate_id | seq | action | detail | created_by | prev_hash)
```

`detail` 在哈希输入里 → **改 detail 必然让 row_hash 失配** → 触发
`GET /candidates/{id}/histories/verify` 的篡改检测（`apps/candidate/views.py:427-445`）。

而 `detail` 里确实存着 PII：`record_info_update` 落的 `changes[].old/new` 含
`email` / `resume_text` 的**原值**（`apps/candidate/audit.py:81`）。

→ **被遗忘权要求清 PII，不可篡改审计要求不能改行**。两者正面冲突。

### 4.2 解法（两条一起做）

**① 存量行：脱敏 + 整链重算 + 留痕**

- 改第 N 行的 detail → 第 N 行 hash 变 → 第 N+1 行的 `prev_hash` 也要跟着变 → **必须整条链重算**
  （`seq` 不变，`prev_hash`/`row_hash` 逐行重算）
- 重算后链**仍然自洽** —— 校验端点的判定逻辑（seq 连续 + prev_hash 链接 + row_hash 重算）依旧通过
- 链尾追加一条 `GDPR_PII_PURGED` 标记行（`detail` 只记清理了多少行，无 PII）→
  **「这次清理发生过」本身留在链上**。被遗忘权要的是**不可见**，不是无痕。

**② 写入端治本（关键，否则是打地鼠）**

`apps/candidate/audit.py:diff_fields` 现在落库前一律脱敏：

- 手机号/邮箱/身份证 → 掩码；姓名/简历正文/简历文件 URL → 整体隐去
- **比对仍用原值**，只有落库值脱敏 —— 否则 `'ab@x.com' → 'ac@x.com'` 脱敏后两边相同，
  会把真实变更误判成「无变化」而漏记（有专门用例守住）

> 不做这一条，C3 就是打地鼠：候选人每改一次简历，审计链里就再落一份 PII 原值。
> `record_forward` 的附言（`note`）也一并脱敏。

### 4.3 一个诚实的限制

被遗忘权执行后候选人已软删，而 `histories/verify` 端点用 `get_object()`（默认 manager 过滤 `deleted_at`）
→ **无法再通过 HTTP 校验该候选人的链**。用例改为按端点**同一套判定逻辑**在 Python 侧直接校验
（`tests/test_gdpr_purge.py::test_chain_recomputed_and_still_valid`）。

## 5. 批量回填

整改前已执行过被遗忘权的候选人（主表清了、关联表没清）需要补跑：

```bash
# 预演（不改库）
python manage.py purge_candidate_pii --dry-run

# 正式回填（默认只处理已软删的候选人）
python manage.py purge_candidate_pii

# 单个候选人排障
python manage.py purge_candidate_pii --candidate-id cand-xxxx

# 跳过审计链重算（先观察其他表的清理效果）
python manage.py purge_candidate_pii --skip-audit-chain
```

> 默认**不**加 `--include-active` —— 对在招候选人跑这个命令等于毁简历。

**归因结论：轮次 ① 的 3 个失败与本次改动无关**（三条同时成立）：

1. 这 3 个用例**单独跑全部通过**（`3 passed in 1.47s`）→ 排除确定性缺陷；
2. **完全相同的代码第二轮、第三轮整跑均 0 failed** → 排除真回归；
3. **基线（stash 掉本次改动）那轮也出现 1 个 error**，且**每次失败的用例都不同**
   （① 是 `test_field_acl` / `test_grabpool_context_and_reassign` / `test_audit_fake_upgrades`，
   基线是 `test_application_grabpool_nonempty_regression`）→ 排除"改动只是改变了执行顺序"。

> 即：仓内存在**跨用例状态敏感**的非确定性失败（`-p no:randomly` 只固定了顺序，并未消除
> `PYTHONHASHSEED` 随机化带来的集合/字典迭代序差异）。这与 B5 已治的「跨用例状态污染」是同类问题，
> 建议单独立卡治理（当前已在 B5 记录，Phase 6 可纳入）。
> 本轮**未**去动这批 flaky 用例 —— 它们与 C3 无关，且改动用户在途代码的风险高于收益。

- **遗留｜动态字段定义**：白名单按 `field_key` 精确匹配。若运营把敏感字段配成 `phone_number_backup`
  这类非标准 key，会漏清 → 建议后续加一条守卫：新建 `DynamicField` 时若 `field_type` ∈ PII 类型，
  自动登记进敏感 key 集合。
- **遗留｜C4**：phone/email 落库加密 —— 独立 PR + 独立发布，前置已满足（C1/C2/C3 均完成）。
- **遗留｜其他泛型引用表**：本卡只处理了 `dynamic_field_values` 一张泛型引用表；
  若后续新增同类泛型表，需纳入同一清理口径。
