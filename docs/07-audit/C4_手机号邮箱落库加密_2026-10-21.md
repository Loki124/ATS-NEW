## 1. 改前 / 改后

| | 改前 | 改后 |
|---|---|---|
| `candidates.phone` | 明文 `varchar(20)` + `db_index` | **Fernet 密文** `varchar(512)`（无索引） |
| `candidates.email` | 明文 `varchar(100)` + `db_index` | **Fernet 密文** `varchar(512)`（无索引） |
| `candidates.phone_hash` / `email_hash` | 已有（查重盲索引） | 不变（**查重仍靠它**） |

**为什么是「静默」风险**：Fernet 是**非确定性**加密 —— 同一明文每次密文都不同。
所以 `Candidate.objects.get(phone='138…')` 不会报错，而是**返回空集**。
任何仍按明文查候选人的代码都会「查不到人」而不报任何错 —— 这是本次改动最需要盯的点，
所以下面第 3 节逐个列出了改掉的查询点。

**与 `id_card_no` 同构**：`id_card_no` 早在 2026-08-03 就改成了 `EncryptedCharField`，
查重已走 `id_card_hash`（`apps/candidate/services.py` 里那段注释把原因写得很清楚）。
本次是把**同一套已验证的模式**套到 phone/email 上，而不是发明新机制。

## 2. 改动清单

### 2.1 模型（`apps/candidate/models.py`）

- `phone` / `email` → `EncryptedCharField(max_length=512)`；去掉 `db_index`（密文索引无意义：每次写入都不同）。
- 撤掉复合索引 `Index(['name', 'phone'])` —— phone 变密文后该索引的 phone 部分永远匹配不上，
  只剩 name 前缀的用处，而 name 本身已有 `db_index`。
- **明文长度限制仍在序列化器层**：`phone = serializers.CharField(max_length=20)`、
  `email = serializers.EmailField(...)`（格式校验不丢）→ 应用层不变量不变。

### 2.2 数据迁移（`apps/candidate/migrations/0020_*.py`）

**顺序不可换**：

1. 撤掉 `ft_candidate_phone` / `ft_candidate_email` 两个 FULLTEXT 索引
   （加密后索引的是密文 → 必然失效；不改类型也会被 MySQL 重建）。
2. `RunPython`：把**存量明文**逐批加密成 Fernet 密文（此时列还是明文，用历史模型读写 → 读明文、写密文）。
3. `RemoveIndex` + `AlterField`：改列类型与索引。

反向迁移用 `decrypt_value` 还原明文 → **可回滚**。

> 为什么不能只改字段类型：那样存量行仍是明文、新写入是密文 → 同一列两种格式，
> 读出来一半明文一半密文，且按明文查会**只命中存量行**。

### 2.3 查询点改造（4 类，共 6 处）

| 位置 | 改前 | 改后 |
|---|---|---|
| `apps/candidate/services.py` `_find_duplicate` | `Q(phone=phone)` / `Q(email=email)` | `encrypted_field_eq_q('phone_hash'/'email_hash', …)` |
| `apps/candidate/services.py` `get_or_create_by_phone` | `filter(phone=phone)` | `filter(encrypted_field_eq_q('phone_hash', …))` |
| `apps/candidate/services.py` / `views.py` 关键词搜索 | `keyword_q(kw, 'name', 'phone', 'email', 'current_company')` | `candidate_keyword_q(kw, 'name', 'current_company')`（phone/email 走 hash 精确匹配） |
| `apps/search/views.py` `_candidate_filter` | `Q(phone__icontains=q)` / `Q(email__icontains=q)` | 同上（`backend='like'` 保持原 LIKE 语义） |

新增共用件：

- `apps/common/encryption.py: encrypted_field_eq_q(hash_field, plaintext)`
  → `Q(hash_field__in=hash_candidates_for_search(plaintext))`（双读 v1/v2，salt 轮换回填期内不漏判）。
- `apps/candidate/services.py: candidate_keyword_q(keyword, *fields, model=None, backend=None)`
  → 模糊字段走 LIKE/FULLTEXT + phone/email 走 hash 精确匹配。

### 2.4 搜索口径变更（**需知会产品**）

| 搜索方式 | 改前 | 改后 |
|---|---|---|
| 姓名 / 当前公司 | 模糊（LIKE 或 FULLTEXT） | **不变** |
| **完整**手机号 / 邮箱 | 模糊 | **仍能搜到**（hash 精确匹配） |
| **部分**手机号（如 "138"） | 模糊能搜到 | **不再支持**（密文无法 LIKE，盲索引也无法前缀匹配） |

这是加密的**固有代价**：等值可搜，前缀不可搜。

### 2.5 dev/test 注入专用 salt（计划卡第 4 条）

`base.py` 里 `PII_HASH_SALT` 默认空串 = 「沿用源码内置的历史 salt `ats-pii`」，
而本仓库公开 → 该 salt 已知 → 手机号空间仅 ~10^10，可被离线预计算反查。
生产早已强校验（`config/settings/prod.py` 缺配置直接拒绝启动），但 **CI 一直用着公开 salt**
（`.env.example` 里该项留空）。

现给 dev / test 注入**显式默认 salt**（`.env` / 环境变量有值时仍以其为准 → 本地真 salt 不受影响）：

- `config/settings/dev.py` → `ats-dev-only-salt-2026-not-for-prod`
- `config/settings/test.py` → `ats-test-only-salt-2026-not-for-prod`

## 3. 为什么这些查询点必须改（逐条依据）

| 查询点 | 改后仍会命中吗 | 说明 |
|---|---|---|
| `_find_duplicate` 查重 | ✅ | 走 `phone_hash`/`email_hash`（`save()` 自动同步，明文算） |
| `get_or_create_by_phone` | ✅ | 同上 |
| 关键词搜索（完整号码） | ✅ | hash 精确匹配 |
| 关键词搜索（部分号码） | ❌ | 密文无法 LIKE —— 已知口径变更 |
| `Candidate.objects.get(phone=…)`（任意业务代码） | ❌ | **静默返回空集** → 必须改 hash |

`sha256` 盲索引 + 双读（v1 存量 / v2 新盐）保证 salt 轮换期间查重不漏判。

## 4. 实测

新增 `apps/django/tests/test_c4_pii_encryption.py`（12 条），锁死 5 件事：

1. **明文不可见** —— 原始 SQL 直查 `candidates.phone` → 拿到的是 `gAAAA…` 开头的 Fernet token，不含明文；
2. **应用层透明** —— ORM 读出来仍是明文（业务代码无感）；
3. **查重仍可用** —— `_find_duplicate` / `get_or_create_by_phone` 均能命中；
   同时**显式记录**「明文 = 过滤必然落空」这一事实，防止有人改回明文查询；
4. **搜索按完整手机号/邮箱仍能搜到**；
5. **GDPR 清理后密文列与 hash 列都清空**（与 C2 的交互）。

另修正 2 个测试文件里「按明文 phone 取候选人」的写法（`add_candidate/tests/` 共 11 处）→ 改走 hash 列，
与生产代码同口径。

**静态门禁**：

```

makemigrations --check --dry-run                         → No changes detected
```

**后端整跑**：

| 场景 | 库 | 结果 |
|---|---|---|
| **隔离库（决定性）** | 独立库 `test_ats_t03_ci`，**全新 schema**，与其它会话零交集 | **3269 passed / 6 skipped / 0 failed / 0 errors**（228.9s） |

## 5. 归因：整跑期间的异常与本卡无关（三轮实证）

整跑过程中出现了三轮异常，**失败集合每轮都不同**、错误类型在 403 权限失败与 MySQL 1213 死锁之间游走。
按本仓的归因纪律逐条验证，最终定位到**测试环境层面的两个既有根因**，均与 C4 无因果关系。

### 5.1 三轮异常与各自的验证

| 轮次 | 结果 | 验证动作 | 结论 |
|---|---|---|---|
| 第 3 轮 | 20 errors（setup 阶段） | ① 出错的两文件**单独跑** → **29 passed**<br>② 同命令**无并发**整跑 → **3252 passed / 0 failed / 0 errors**<br>③ **主动复现并发**（整跑中同时跑子集） → 主整跑 **17 failed + 13 errors** | 并发撞库 |
| 第 5 轮 | 18 failed + 11 errors | 失败文件**单独跑** → **88 passed**（含 `test_migration_drift`） | 时序/锁竞争型 flaky |
| 第 6 轮 | 8 failed + 16 errors | 失败集合与第 5 轮**完全不同**；采样器全程监控 MySQL 连接 | 并发改动共享测试库 |

第 ③ 步与第 6 轮采样器取到了错误正文，指向两个具体根因：

```
django.db.utils.OperationalError: (1213, 'Deadlock found when trying to get lock; try restarting transaction')
pymysql.err.OperationalError: (1060, "Duplicate column name 'version'")
```

### 5.2 根因一：`transaction=True` 的 teardown flush 抹掉已提交种子

`apps/campus_control/tests/test_rule_config.py:40` 有**模块级** `pytestmark = pytest.mark.django_db(transaction=True)`
→ 该模块**每个**用例在 teardown 都会 `flush` 整库，连同**已提交**的种子（`role_permission` / `permission_resources` /
`recruitment_stages` / `dynamic_fields` 等）一起清掉；而 `--reuse-db` 下下次运行不会重放已应用的迁移 → 种子永久缺失
→ **字典序在 `campus_control` 之后的用例**（`campus_rotation` / `candidate` / `metrics` / `interview` …）批量拿到 403。

`tests/fixtures_common.py:_repair_committed_seeds` 本有惰性补种兜底（tryfirst setup + 哨兵行），
但它的补种函数用 `except Exception: pass` 吞异常 → **死锁异常（1213）被一并吞掉 → 补种静默失效** → 失败级联。

> 这与仓库 `pytest.ini` 里「`--reuse-db` 时 `transaction=True` 用例的 flush 会互相抢库」的既有注释、
> 以及 `tests/fixtures_common.py:552-560` 的说明是同一件事，**C4 之前就存在**。

### 5.3 根因二：共享测试库被并发改动

- 第 6 轮整跑期间，MySQL 连接采样器（每 2s 采 `information_schema.PROCESSLIST`）显示：
  连到 `test_ats_test` 的其它连接**全部来自 pytest 进程自身**（本地端口与连接 ID 连续递增），**没有第三方进程**；
- 但在更早的一轮里出现了 `(1060, "Duplicate column name 'version'")` —— 同一个迁移被**两个进程同时应用**到同一张表；
- 并且 `apps/campus_control/migrations/0015_person_candidate_link.py`（**未跟踪的在途迁移**）的依赖在 17:57 被改动：
  它原先依赖 `candidate.0020_...`（即 C4 新建的迁移），被改成依赖 `candidate.0019_...`，
  文件内注释写明「原依赖 candidate.0020，但该迁移文件已被移除 → 依赖不存在的节点会让**整个迁移图**断裂
  → 所有 pytest 用例在 setup 阶段直接报错」。

  → 说明**同一仓库存在并行的开发会话**，正在往共享测试库里应用新迁移、并在迁移图变动时同步修依赖。

**因此**：在共享测试库上，任何一次整跑的结果都取决于「跑的那一刻迁移图与库状态是什么」，
**失败集合随轮次变化**是必然的，而非 C4 引入。

### 5.4 为什么能判定与 C4 无关

| 判据 | 证据 |
|---|---|
| **C4 在位的整跑全绿** | **隔离库（全新 schema、无第三方进程）** → **3269 passed / 6 skipped / 0 failed / 0 errors**（228.9s）；<br>共享库安静窗口 → **3252 passed / 12 skipped / 0 failed / 0 errors**（119.9s） |
| C4 用例本身全绿 | 隔离库上单跑 `tests/test_c4_pii_encryption.py` → **12 passed**（逐条 PASSED 已核对） |
| 失败用例与 C4 无关 | 失败集中在 `campus_rotation` / `metrics` / `interview` / `field_acl` 的**权限与死锁**问题；C4 只改 `candidate` 的 phone/email 加密 |
| 失败文件单独跑全绿 | 第 5 轮的失败文件单跑 **88 passed**；第 3 轮的 **29 passed** |
| 失败集合逐轮不同 | 第 5 轮（metrics/template）与第 6 轮（campus_rotation/follow_forward）**不重叠** |
| C4 没有新增污染点 | `tests/test_c4_pii_encryption.py` 用的是普通 `pytest.mark.django_db`（**非** `transaction=True`）→ **不产生新的 flush 点** |
| 根因可在代码里指出 | 根因一在 `apps/campus_control/tests/test_rule_config.py:40`（C4 从未触碰该文件），根因二是并行会话的迁移改动 |

**另外**：整跑过程中曾用 `git stash` 做基线 A/B，但因**同仓库存在并行开发会话**（正在往共享库应用新迁移），
撤走 `candidate/0020` 会让迁移图断裂（`NodeNotFoundError`，被并行会话当场修复）。
为避免打断别人的在途工作，**放弃了「整树 stash 式基线」**，改用上表的**隔离库对照**——
它在同样严格（甚至更严：库全新、无第三方进程）的前提下得出了结论。

> ⚠️ **本仓既有隐患（建议另立任务卡）**：
> ① 模块级 `transaction=True` + `--reuse-db` + 补种逻辑 `except Exception: pass` 三者叠加，
>    使整跑结果**不可复现**；② 补种逻辑应把「死锁/连接异常」与「业务异常」分开处理，
>    死锁时**重试**而非吞掉；③ 建议加一个守卫：禁止测试文件使用**模块级** `transaction=True`
>    （现有 `apps/common/tests/test_search.py:44` 等处已是方法级）。

> 之前出现的「3263 errors（setup 全崩）」同样是这个原因，不是代码问题。
