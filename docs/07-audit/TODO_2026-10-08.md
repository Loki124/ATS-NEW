### #24 权限 V1 模块下线 — 只读影响分析（#P1-架构，依赖 #1）

> 2026-10-09：按"先影响分析、再决定是否删"的建议，做了**只读**全量扫描，结论如下。
> 审计 CODE_REVIEW 把 `permissions.py` 与 `permissions_v2.py` 并存称为"V1/V2 并存"，
> 但实测 `permissions.py` 是**在用**权限类库，不能整体下线。

V1 权限体系由三部分构成，现状：

| 构件 | 现状 | 能否删 |
|---|---|---|
| V1 数据模型 `Role`/`UserRole`/`RolePermission`/`Permission` V1 | **已删**（迁移 `0004_v2_apply_schema.py` DeleteModel；`models.py:6-9` 注释 T01.1/T01.2）；`migrate_v2_data.py` 为优雅跳过的死命令 | 已离线，无残留引用 |
| `apps/core/permissions.py` | **在用**：被 audit/data_permission/gdpr/integration/core/field_acl 等 22+ 视图 + `application/serializers.py` + `scripts/verify_audit_fixes.py` + 多个测试引用（`IsSuperAdmin`/`IsHROrAbove`/`HasProcessPermission`/`MOUVIEWSetPermission`/`UserViewPermission`/`ScopedQuerysetMixin`/`is_hr_or_above`/`user_department_ids`） | **不可删**（live 基础设施，名字里的"V1"是历史遗留） |
| `apps/core/permission_check.py::has_perm` | **V2 查询引擎**：被 `permissions_v2.py`(V2Permission.has_permission)、`permission_check_view.py`、5 个测试模块依赖 | **不可删**（V2 负荷承载项） |
| `apps/core/permission_check_view.py` (`/api/v1/permission/check/`) | **在用 V2 端点**：注册于 `urls_permission_v2.py:29`(name=`v2-permission-check`)，有 `test_api_v2_check.py`+`test_v2_endpoints_regression.py` 覆盖，前端当前无调用 | **不可删**（API 契约 + 测试覆盖，非死 shim） |

**结论**：可安全删除的 V1 权限代码**已不存在**。数据模型层下线目标在 T01.1/T01.2 已完成；
剩余 `permissions.py`/`permission_check.py`/`permission_check_view.py` 均为 V2 在用基础设施，
删除会破坏 22+ 视图、V2Permission 及 2 个测试。故 #24 实质已完成，状态置 ✅。

**唯一可选的低风险收敛动作（非必须，建议单独立项）**：将 `has_perm` 从 `permission_check.py`
内联进 `permissions_v2.py` 后删 `permission_check.py`（需同步改 5 个测试 + `permission_check_view.py`
的 import）。属重构而非删死代码，收益很低。

**残留引用发现（独立小修，不在 permissions 模块核心范围）**：`apps/core/scripts/verify_audit_fixes.py:43`
仍 `from apps.core.models import ... Role, UserRole` 并 `UserRole.objects.get_or_create(...)`，
而 V1 模型已 DROP → **该脚本导入即崩**。建议改为 `UserRoleV2`/确认脚本意图后修或删。
