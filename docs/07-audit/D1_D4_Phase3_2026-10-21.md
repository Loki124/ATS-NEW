## 2. D1｜看板 KPI 接行级 scope

### 缺陷

`apps/analytics/views.py` 的两个看板端点此前是**全表计数**：

```python
'candidates_total': Candidate.objects.filter(deleted_at__isnull=True).count(),
'applications_total': Application.objects.filter(deleted_at__isnull=True).count(),
```

`dashboard_summary` 的 docstring 自称「HR **个人**看板」，`KpiViewSet.list` 返回给前端看板的 6 个数字。
两者都只持 `recruit:settings:data_dashboard:list` 就能读到**全组织**总数 —— 而同页面的列表接口是被 scope 裁剪的，
→ **同一页面两套数字**，且等于「列表看不到的数据，看板能读到」。

### 改法

统一走 `apps.core.entity_scope.scoped_queryset`（ENTITY_SCOPE 单一真相源，字段口径与各 ViewSet 逐项对齐）：

- `dashboard_summary`：4 项计数 + `applications_by_state` 分组
- `KpiViewSet.list`：6 项计数（candidate / demand / position / interview / offer / onboarding）

`KpiViewSet` 的 `_safe_count` 额外捕获 `FieldError` —— scope 路径漂移时返 0 而非 500，
符合该端点「任何 model 字段漂移都不 500，顶多返 0」的原设计。

### 口径影响（需知会）

- **超管数字不变**（`scope_filter_q` 对超管 bypass）；
- **普通账号的看板数字从「全组织」收窄为「本人可见范围」** —— 这是本卡要的修正，但属**可见的产品口径变化**。

### 实测

新增 `tests/test_d1_d2_scope_leak.py`：

| 用例 | 断言 |
|---|---|
| `test_kpi_scoped_by_department` | A 部账号 `openPositions==1`、B 部 `==1`、超管 `==2`；候选人维度同理 |
| `test_dashboard_summary_scoped_by_department` | `applicationsTotal` 1 vs 2；`positionsOpen` 1 vs 2；`candidatesTotal` 1 vs 2 |
| `test_super_admin_still_sees_everything` | 超管不被裁剪（防「修过头」） |

**A/B 对照**（`git stash` 掉本次改动的 3 个源文件后用**完全相同的命令**重跑）：
**6 failed / 1 passed** → 改动后 **7 passed**。用例确实守得住这个缺陷。

> 响应键是 camelCase —— 全局挂了 `djangorestframework-camel-case` 渲染器
> （源里的 `candidates_total` → 响应里的 `candidatesTotal`）。断言按渲染后的键名写。

## 3. D2｜抢单池接 scope + 修分页 total

### 缺陷（两处）

1. `apps/application/services/grab.py:GrabService.get_pool()` 过滤了 `deleted_at` 但**没有 scope**
   → 全公司申请池对所有登录用户可见；
2. `application/views.py` 传 `limit=50` → `grab.py` 先 `[:limit]` 截断 → 再分页
   → `pagination.total` 报的是**截断后**的条数（恒 ≤ limit），不是真实池总量。

### 改法

- `get_pool()` 改返回 **QuerySet**（不再返回 list、不再预截断），新增 `scope_q` 参数；
  `get_grab_pool_summary()` 同样接 `scope_q`（此前汇总数也是全公司池子大小）；
- `GrabPoolViewSet` 新增 `_grab_scope_q()` → `entity_scope_q(request, 'application')`
  （scope 字段口径与 `ApplicationViewSet` 一致：`position__department` / `created_by`）；
- 分页顺序改为「**先分页、再按 `limit` 裁当页**」→ `total` 取未截断 queryset 的真实值。

### 实测

| 用例 | 断言 |
|---|---|
| `test_cross_department_application_not_visible` | A 部账号只看到 `APP_D1_A`，B 部只看到 `APP_D1_B` |
| `test_pagination_total_is_real_pool_size` | 池里 4 条 → `pagination.total == 4` |
| `test_limit_truncates_page_but_not_total` | `limit=2` → 当页 2 行，但 `total` 仍是 4 |
| `test_grab_pool_summary_scoped` | summary 的 `total` 按 scope 裁剪 |

> 前端未调用抢单池端点（全仓 `web/app/src` 无 grab-pool API 调用）→ 无前端联动风险。

## 4. D3｜软删治理（本阶段最大的一张）

### 4.1 先量准：泄漏点到底有多少

计划卡写的是 30 处，实测**38 处**（在途新增了校招模块）。为了不靠人眼数，新增**反向扫描器**
`apps/django/scripts_scan_softdelete_viewsets.py`：

> 判定：ViewSet 的 queryset 指向的模型**有** `deleted_at`，且表达式**没有** `deleted_at__isnull=True`，
> 且该模型的默认 manager **不是** `SoftDeleteManager` → 报出来。

```bash
python scripts_scan_softdelete_viewsets.py
# 修复前: 软删泄漏 ViewSet（模型有 deleted_at 却不过滤）：38 处
# 修复后: 0 处
```

### 4.2 改法选择：跳过「逐个改 38 处」，直接做结构性修复

计划卡原定「先给 30 个 ViewSet 逐个补过滤（低风险），再做结构性挂载」。实测后**直接做了第二步**，
因为它能一次性根治 38 处、且让**以后新建的模型默认即合规**。

```python
class SoftDeleteModel(models.Model):
    deleted_at = models.DateTimeField(...)
    objects = SoftDeleteManager()      # 默认 manager: 自动过滤软删行
    all_objects = models.Manager()     # 显式取全量（含软删行）
```

子类若自己声明了同名 manager，以子类为准（Django 的 manager 继承规则）。

### 4.3 爆炸半径：25 条失败，逐条归类

结构性改动一落地，整跑 **25 failed**。逐条看完，**不是「25 个 bug」，而是两类**：

**A 类｜测试侧读软删行（17 条）** —— 测试用 `.objects` 去读**刚软删**的行来断言。
例：`test_approve_anonymizes_pii` 里 `Candidate.objects.get(id=...)`。
→ 改用 `all_objects`（语义明确：「读含软删行的数据」）。

**B 类｜生产代码真回归（8 条）** —— 这些位置的**注释里本来就写明「刻意不过滤软删」**，
依赖「默认 manager 不过滤」这个前提，前提一被抽掉就静默出错：

| 位置 | 原意图 | 被打破后的后果 |
|---|---|---|
| `process/services/versioning.py` 版本号 seq 计算 | C1 是无条件唯一约束，**软删行同样占位** | 算出的 seq 撞唯一约束 → IntegrityError |
| `process/services/versioning.py` is_latest 腾位 | 翻转语句**刻意不过滤**，连软删行一起降级自愈 | 腾不出槽位 → 新行落 `is_latest=True` 撞约束 |
| `dynamic_field/views.py` 删后重建 | 查软删占位行 → 复活它 | 误判为无占位 → 新建 → 撞 unique_together → 500 |
| `dynamic_field/views.py` 预设 seed | 存在性判断**含软删** → 管理员删过的预设不复活 | 被重新 seed 出来 |
| `process/management/commands/backfill_process_start_end.py` | 复活软删 link（DB 唯一约束不认 deleted_at） | 走新建 → 撞唯一约束 |
| `campus_rotation/views.py` ×4 + `campus_control/views.py` | restore 要能取到已软删对象 | **404**（campus_control 原本就是坏的 —— 既有缺陷） |
| `rule_engine/management/commands/check_rule_engine_consistency.py` | 「已删分支」要能查到软删规则 | **漂移检测对已删规则直接失明** |

修法一律是**显式改用 `all_objects` / `_base_manager`**，并在原地写明为什么。

### 4.4 连带发现：迁移里的历史模型也开始过滤软删行

Django 的 `ModelState.from_model` 会把**默认 manager 的类**复制成 shim 给历史模型：

```python
elif manager is model._base_manager or manager is model._default_manager:
    instance = model._meta.default_manager.__class__()   # ← 同类 shim
```

→ **迁移里**的 `DynamicField.objects` 也成了 `SoftDeleteManager` → 过滤软删行。
后果实测：`dynamic_field/migrations/0023_normalize_candidate_fields.py` 的**反向迁移**复活不了行
（`update(deleted_at=None)` 匹配不到软删行）→ 反向迁移静默失效。
→ 改用 `DynamicField._base_manager`（Django 的无过滤兜底 manager）。

> 该仓已有先例：`dynamic_field/migrations/0019/0020/0022/0024` 早就用了 `_base_manager`，
> 说明这个坑之前已被踩过一次（只是当时没有 manager 化的普遍影响面）。

### 4.5 restore 端点：同时满足「能恢复」与「不绕��行级隔离」

守卫 `apps/data_permission/tests/test_write_guard.py` 要求 restore 端点源码里**字面**出现 `self.get_object()`，
且不许用全表 `Model.objects.get(pk=)` 取数。而 `get_object()` 走 `get_queryset()`（按 deleted_at 过滤）
→ 恢复软删对象必然 404。

新增 `SoftDeleteRestoreMixin`（`apps/common/mixins.py`）：在 restore 动作内把取数来源换成
`model.all_objects`，**其余过滤链（scope / filter_backends）原样保留** → 行为 =「可见范围内可恢复软删对象」。
已挂到 campus ×2、campus_control ×4 六个 ViewSet，守卫与功能同时满足。

### 4.6 影响面提醒

`objects` 语义变了 —— **所有**软删模型的默认 manager 现在都过滤软删行。仓内需要读历史行的地方
必须显式写 `all_objects`。本轮已逐条修完（25 条失败 + 静态审计 `deleted_at__isnull=False` /
「不过滤软删」注释扫描，命中 4 处生产路径，确认都安全：其中 3 处本就用 `_base_manager` 或已显式过滤）。

## 5. D4｜索引补齐

### 5.1 计划卡的数字需要修正

计划卡写「`code` 37 处声明仅 1 处有索引」—— **与实测不符**：绝大多数 `code` 是 `unique=True`
（MySQL 自带唯一索引），实测需要补索引的 `code` 只有 5 处。计划卡疑似只统计了 `db_index=True` 而漏算 `unique`。

新增扫描器 `apps/django/scripts_scan_missing_indexes.py`（判据：CharField + 无 db_index + 无 unique
+ 全仓确有按值过滤）→ 实测 **34 处**（含 3 处属 `django_celery_results` 第三方模型，不可改）。

### 5.2 最终补的 23 个字段

| 组 | 字段 | 理由 |
|---|---|---|
| `status` ×16 | accounts / add_candidate / analytics / campus×2 / campus_control / dynamic_field / integration / library×2 / metrics×4 / mou / rule_engine | 均有按值过滤 |
| 权限热路径 ×2 | `RolePermissionV2.role_code` / `resource_code` | **每次鉴权都查** `role_permission`（`has_perm`），此前无索引即全表扫 |
| 编号字段 ×5 | `RecruitmentProcess.code` / `ControlDimension.code` / `FieldGroup.code` / `FieldModule.code` / `MouContainer.code` | 均按 code 过滤（`RecruitmentProcess.code` 是克隆/版本号计算的热路径） |

**刻意不补**：`system_code` ×7（单值分区键，基数≈1，索引无收益）、`RoleV2.role_code`
（已有 `UniqueConstraint(system_code, role_code)` 复合索引）、`UserRoleV2.role_code`
（先走 `user_id` FK 索引）、`django_celery_results.TaskResult.status`（第三方模型）。

### 5.3 生产发布注意

MySQL 加二级索引会**锁表 / 重建表** → **需在低峰期执行**；`EXPLAIN` 验证待生产量级数据（**未验证**）。

### 5.4 工具链的三个坑（脚本自身踩的，已在脚本注释里记下）

用 AST 精确改写字段定义时连踩三坑，均已写进 `/tmp/d4_add_indexes.py` 的注释：

1. **单行/多行判定**不能用「有没有 keyword」—— `models.CharField(max_length=16, verbose_name='x')`
   是单行但带 keyword；误判会把 `db_index=True,` 插到字段定义**外面** → 游离语句 → **模块导入即 NameError**；
2. 多行时**末参数**要取「位置参数 + 关键字参数」里位置最靠后的那个，且末参数常无尾逗号 → 需先补逗号；
3. AST 的 `col_offset` / `end_col_offset` 按 **UTF-8 字节**计，**不是字符数** ——
   含中文的源码里字节偏移 > 字符偏移 → 按字符切片会切错位置（本次 `'状态'` 3 字节就差了 2）。

脚本带**写后校验**（重新解析 + 断言该字段确实带上了 `db_index` + 游离语句检测），避免再写坏文件。

- **遗留**：`objects` 语义变化后，仓外/未来代码读历史行必须显式用 `all_objects`；
  建议把 `scripts_scan_softdelete_viewsets.py` 接进 CI（现在 0 处，可直接 `--strict` 翻硬门禁）。
- **遗留**：`status` 的 db_index 覆盖了实测命中的 16 处，但 `stage` 类字段实测无「无索引且按值过滤」的命中
  （计划卡说 4 处）→ 本卡未加。
