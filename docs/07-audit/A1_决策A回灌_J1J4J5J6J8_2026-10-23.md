# A1 — 决策 A 回灌：J1 / J4 / J5 / J6 / J8 在 Django（真源）侧的修复（2026-10-23）

> 背景：后端正从 Django 迁到 Java（`ATS-Java`）。迁移过程中在 Java 侧发现了一批缺陷（J1~J9），
> 其中若干**在 Django 真源侧同样成立** —— 真源有缺陷 ⇒ 两边一起坏 ⇒ 那才是"真源口径"。
> **决策 A = 把这些缺陷回灌到 Django 侧修掉**（不是"迁就 Java"，是"把真源修对"）。
>
> 本轮对应条目：**J4-Django**（工具在读阶段就崩）、**J1**（序列化器静默丢字段）、
> **J5**（盲索引单形态漏判）、**J6**（审计链哈希列宽零余量）、**J8**（角色/授权悬空引用）。
> **J2** 经核查**命题在 Django 侧不成立** ⇒ 不改（详见 §5）。
>
> 配套记录在 `ATS-Java/docs/06-Django缺陷对照.md` §十二 / §十三 与 `ATS-Java/docs/04-进度跟踪.md` **M20-34**。

## 1. 一览

| 条目 | 改前 | 改后 |
|---|---|---|
| `CandidateHistory.prev_hash` / `row_hash` | `max_length=64`（= sha256 hex 长度，**零余量**） | **`max_length=80`**（+ 迁移 `0021` + 常量 + 防漂移测试） |

## 2. 逐条改动

### 2.1 J6：审计链哈希列宽 64 → 80

**为什么零余量是缺陷**：`apps/candidate/audit.py::compute_row_hash` 用 `hashlib.sha256(...).hexdigest()`
⇒ 输出**恰好 64 字符**；而列宽也是 64 ⇒ 没有任何缓冲。
- "加版本前缀"**不是假设**：PII 盲索引列已经因为外部 salt 改成 `v2_` 前缀（67 字符）
  ⇒ "哈希类字段可版本化"在本仓是**已发生的事实**；
- 审计链比 PII 哈希更**不能想改就改**：`prev_hash` 串起全链 ⇒ 改一列 = **整条链**失效，
  `histories/verify` 端点会立刻报 `broken_at`。

**改动**：

| 文件 | 改动 |
|---|---|
| `apps/candidate/audit.py` | 新增 `AUDIT_HASH_REQUIRED_MAX_LENGTH = 80`（列宽下限的唯一真源） |
| `apps/candidate/models.py` | `prev_hash` / `row_hash` 的 `max_length` 64 → **80** |
| `apps/candidate/migrations/0021_widen_audit_hash_columns.py` | **新增**：纯 `AlterField` 加宽（**零行为变化**，不改数据、不动 id） |
| `apps/candidate/tests/test_audit.py` | 新增 `test_audit_hash_columns_fit_prefix_margin`：把**模型列宽与常量绑在一起**，任何一方回退到 64 都会被拦下 |

> 迁移**只加宽、不收窄** ⇒ 不存在数据被截断的风险；Django 侧 `makemigrations --check` 已确认**无未生成的迁移**。

### 2.2 J1：`DynamicFieldSerializer` 静默丢 `created_at` / `updated_at`

`Meta.fields` 里只列了业务字段，而 `created_at` / `updated_at` 仅出现在 `read_only_fields`
⇒ DRF **静默丢弃**（不报错、不告警）⇒ 前端拿不到这两个键。
**改动**：补进 `Meta.fields`。**验收**：运行时键数 **30 → 32**，两个键均在。

> **通用纪律**：**`read_only_fields` ≠ 「会被序列化」** —— 字段必须同时出现在 `fields` 里。

### 2.3 J5：`auto_match_candidate` 的盲索引单形态漏判

`hash_for_search(phone)` 只产出**当前 salt 口径**的单一 hash ⇒ 启用外部 salt **之前**写入的
**v1 存量哈希**永远匹配不上 ⇒ 校招档案走本地补号，编号与候选人不同源。
**改动**：改双读 `encrypted_field_eq_q('phone_hash', phone)`（与主查重路径同款），
**不动** `hash_for_search` / `hash_candidates_for_search` / `Candidate.save()`。
**验收**：v1 存量行 `real_cand_001`（`phone_hash=36967844fd…`）**单读命中 0 → 双读命中 1**。

### 2.4 J4-Django：`reencrypt_pii` 遇历史明文行**在读阶段就崩**

原实现用 `model.objects.all()` 遍历待回填行 ⇒ ORM **读阶段**就触发 `from_db_value` 解密
⇒ 历史**明文**行直接抛异常 ⇒ 命令根本走不到"回填"那一步。
**改动**：
1. 改用 `values_list('pk')` + **原生 SQL**（只取主键，绕开模型读）；
2. 明文行**默认清晰报错**（不静默跳过）；
3. 新增 `--include-plaintext` 显式开关（用于收敛存量明文行）。
**配套**：`apps/common/encryption.py` 抽出单一真源 `FERNET_TOKEN_PREFIX='gAAAAA'` + `looks_like_ciphertext()`
（`decrypt_value` 复用，**行为等价**）。
**验收**：新增 2 个 pytest ⇒ `tests/test_reencrypt_pii.py` **5 passed**；
真源库 `reencrypt_pii --dry-run --model candidate.Candidate` ⇒ 11 字段无报错。

### 2.5 J8：角色/授权的两处悬空引用

| 处 | 事实 | 处置 |
|---|---|---|
| `user_roles` 孤儿绑定 1 条 | `id=125, user_id=198, role_code='HEAD_TEACHER'`，而 `core_user` 里 **id=198 完全不存在** ⇒ 按 `user_role_codes`（按 `user.pk` 查）**对所有真实用户静默失效**；若将来出现 id=198 的用户 ⇒ 它会**突然获得 `HEAD_TEACHER`** | **先备份**到 `bak_ats_decisionA_20261023_user_roles` → 精确删除（`6 → 5` 条有效绑定 · 孤儿 **0**） |
| `role_permission` 孤儿授权 5 条 | `role_code='ADMIN'`（ids 2287-2291，资源全是 `recruit:settings:dynamic_strategy:*`），而 `roles` 表里**从来没有 ADMIN** ⇒ **永不生效** ⇒ 动态策略的 5 个资源对所有非超管都不可用 | **用户 2026-10-23 拍板「改挂 manage（扩权）」** ⇒ 已改挂（原件备份在 `bak_ats_decisionA_20261023_role_permission`） |

**改挂依据**：`roles.template_code` 里 `SUPER_ADMIN` 与 **`manage`（管理员）** 都是 `TMPL_ADMIN`；
而 `TMPL_ADMIN` 模板的 `permission_codes` **含** dynamic_strategy 码 ⇒ 按 `backfill_role_permissions` 的规则，
**`manage` 本应持有这 5 个码**（实测改挂前 `manage` 59 条授权里 dynamic_strategy **0 条**）。

**改挂后实测**：ADMIN 残留 **0** · manage 的动态策略码 **5** · manage 总授权 59 → **64** · 总行数 **934 不变** · 无重复码。

**功能证明（事务内，结束必回滚）**：

| 步骤 | 结果 |
|---|---|
| 负向对照：非超管 `hm_wang`（现有绑定只有 `HRBP`），**不动任何数据** | 5 个动态策略码 **全 False** ✅ |
| 正向：事务内加绑 `manage` | 5 个码 **全 True** ✅ |
| 回滚 | 绑定行数 1 → 1（**零残留**）✅ |

> ⚠️ 验证用户**必须是非超管**：超管走 `is_super_admin` bypass，`has_perm` 恒 True ⇒ 证明不决定性。

> ⚠️ **仍存的事实**：改挂修正的是**授权模型**（manage 本就该持有这些码），
> 但 `user_roles` 里**无人持有 `manage`** ⇒ 功能当前对非超管仍不可用。
> **「谁持有 manage」属角色分配决策**，不在本次拍板范围。

## 5. J2：命题在 Django 侧**不成立** ⇒ 不改（只登记）

| 项 | 结论 |
|---|---|
| 原命题 | "指标点路径 snake/驼峰错配" —— 解析器从 **dict** 取值（`apps/metrics/…/field_resolver.py:119-124`）⇒ **命题不成立** |
| 实测 | 4 条派生指标 `base_path = candidate.workExperience` 报 `error='字段解析失败: candidate.workExperience 不存在'`、`degraded=True` —— 但 `extra` 里**也没有** `work_experience` ⇒ **本仓没有工作经历的结构化模型** ⇒ 属**产品侧决策**（建模型 / 停用这 4 条） |
| 顺带登记① | `apps/metrics/services/candidate_snapshot.py:36-62` 的 `BASIC_FIELDS` 漏 `source_channel`（模型里是 **ForeignKey**，`_entity_node` 显式跳过 FK ⇒ 需 `source_channel_id` 或关联名语义）—— **中风险**，收益仅 1 条原子指标；`demand.department/hr/sharers` 同类 |
| 顺带登记② | 另有 **49 条**指标指向动态字段，但 `dynamic_field_values` 里 `resource='Candidate'` **0 行** ⇒ 属**数据未落地**，非代码缺陷 |

> **不改的理由**：这几条都指向"产品侧尚未决定的事"（要不要建工作经历模型）——
> 凭想象补模型/停用指标，都是**把决策伪装成代码** ⇒ 只登记，不动手。
