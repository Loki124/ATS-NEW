## 1. 方案摘要

1. **零迁移**：`platform` 列已存在（`models.py:97-100`，`max_length=32, blank=True, default='', db_index=True`），模型层**无 `CheckConstraint` / 自定义 `constraints`**（已 grep 确认）→ 本次只改应用层校验，**不需要新迁移**；`db_index=True` 已存在，筛选性能零变化。
2. **改动集中在「门控」，不在「解析」**：Excel 的中文名解析 `_resolve_dict_key`（`io_rotation_resource.py:163-170`）本身**与 `resource_type` 无关**，只做「中文名或 key → 字典 key」；真正要改的是 `io_rotation_resource.py:440-454` 那层 `if resource_type == 'LIVE_ROOM' / elif platform_raw: 报错` 的分支。**中文名双路径不需要改**。
3. **后端有 4 处硬编码，交办清单只列了 3 处** —— 漏掉的是 `import_campus_data.py:188`（JSON 导入命令），且它的策略与其它三处**不一致**（静默丢弃而非报错），是最容易漏改、且漏改后**无任何报错**的一处。
4. **字典复用 `LIVE_ROOM_PLATFORM`，但其语义是直播专属**（实测字典仅 3 项：`VIDEO_ACCOUNT 视频号` / `TENCENT_MEETING 腾讯会议` / `WECHAT_WORK_LIVE 企微直播`）。建议闸口1 先按复用方案落地（改动面最小），把「客服部门是否需要独立字典」作为**显式挂起项**交给产品经理裁定 —— 这是产品语义决策，不是技术决策。
5. **下游三处口径确认零影响**（已逐处读码）：校招占用 `campus_count`（`serializers.py:117-128`）、`ResourceBuSummaryView` 分段（`views.py:1084` 只取 `id/bu_id/capacity/resource_type`）、轮岗安排 `location_type` 派生（`serializers.py:343-345` 由 `resource.resource_type` 派生）—— **三者均不读 `platform`**。
6. **闸口1 已裁决（2026-10-23）**：Q1 **三类形态均可选填**（`OTHER` 一并放开）· Q2 直播间平台在 **Excel 导入端**仍必填、表单端不强校验 · Q3 **复用** `LIVE_ROOM_PLATFORM` 字典。落地情况见 §2.3。
7. **判据自身已修正 3 条**（本轮 17:48 起，详见 §6.6）：R-12（时序假设→假绿）、R-5'/A-19（短语锁错→假阴性）、D-6（子串命中注释→假红）。**三条方向各不相同**，共同教训是「判据写了 ≠ 判据能判定」⇒ 判据必须用语义/结构判定，且必须带改前基线数字。

## 4. 对交办 5 个技术问题的直接回答

**Q1 · 是否需要数据库迁移？**
**不需要。** 依据：① `platform` 列已存在（`models.py:97-100`）；② 模型**无 `CheckConstraint` / `constraints`** → 没有任何数据库级约束与「仅直播间」绑定；③ `db_index=True` 已有 → 索引无需新增；④ 存量实测（本地 dev 库，2026-10-23 15:31）：`LIVE_ROOM` 共 1 行 / `platform` 非空 1 行，**`SERVICE_DEPT` 行数为 0** → 无存量客服部门需要回填。
**是否加约束？明确反对。** 加 `CheckConstraint(Q(resource_type='LIVE_ROOM') | Q(platform=''))` 会与本次需求**直接冲突**，且存量行无法通过迁移预检。
**存量为空是否有影响？** 无。且按当前代码的四道关卡（`serializers.py:96-99` 400 / `io:452-454` 行级错误 / `import_campus_data.py:188` 静默清空 / 前端 `:549-550` 强制 null），**存量 `SERVICE_DEPT` 行的 `platform` 必然为空**，跨环境均如此。
⚠️ 唯一例外：若 B16 改了 `help_text`，Django 会生成一条 `AlterField` 纯注释迁移 → 与「零迁移」目标冲突。**闸口1 需裁决 B16 是否同步**（建议：改，则接受一条无数据影响的注释迁移；`make doctor` 会校验一致性）。

**Q2 · 平台字典 `LIVE_ROOM_PLATFORM` 是否复用？**
- **后端确实做字典校验**，但**两条路径口径不同**：`serializers.py:100` 只按 **key** 查库（`dict_key_active` → `validators.py:58-65`，`filter(type__code, key, is_active=True).exists()`）；Excel 走 `_resolve_dict_key`（`io:163-170`），先按 key 再按 value（中文名）命中，同一个 `DictionaryItem`。
- **复用的问题（实测）**：该字典**只有 3 个种子项，全部是直播形态** —— `VIDEO_ACCOUNT 视频号` / `TENCENT_MEETING 腾讯会议` / `WECHAT_WORK_LIVE 企微直播`。客服部门填「视频号」在业务语义上不成立；客服真正需要的（呼叫中心 / 在线客服 / 工单系统）在字典里**根本不存在**。
- **技术建议**：**闸口1 先复用**（零迁移、零前端字典分支、导入导出闭环天然成立），但**必须同时明示风险**并在闸口1 记为挂起项：字典管理页的类型名仍叫「直播间平台」，运营若不知情会只加直播平台项。字典是运营可维护目录（`seeds.py:19-21` 明示该设计意图）→ 运营可自行在字典页增删客服部门适用项，**无需改代码**。
- 若选独立字典（方案 B）：成本 = 新字典类型 + 种子 + `serializers.py:100` 按类型路由字典 code + `io:224/235/371/444` 四处路由 + 前端 `:490` 按类型拉字典 + 筛选下拉联动（`:38-46`）→ 改动面约为方案 A 的 **2.5 倍**，且**仍然零迁移**（字典是数据）。

**Q3 · Excel 列级规则怎么改？中文名 vs key 两条路径都要改吗？**
- 规则改为**正交两判据**：`LIVE_ROOM` → 必填判空；**所有类型** → 非空则必须解析为启用字典项。
- **中文名路径不需要改**（关键）：`_resolve_dict_key`（`io:163-170`）**完全不感知 `resource_type`**，它只负责「中文名或 key → key」。改动仅限 `io:440-454` 的分支门控。
- 闭环验证（改后）：客服部门填「视频号」→ 解析为 `VIDEO_ACCOUNT` → 导出时 `platform_names.get('VIDEO_ACCOUNT')` → 写回中文名「视频号」→ 再导入仍解析为同一 key ⇒ **导入→导出→再导入稳定**。
- 模板文案（`io:267-268`）**必须同步**，否则运营照旧说明「客服部门请留空」，功能放开等于没放开。

**Q4 · 列表筛选语义要按类型限定吗？**
**建议不限定。** 后端 `views.py:774-776` 与前端 `:415-417` 当前都是「对全部资源按 platform 精确匹配」，放开后语义自然正确：选「视频号」应同时命中直播间的视频号与客服部门的视频号。
若改成「按类型限定」，会产生一个反直觉副作用：同时选了「资源类型 = 客服部门」+「平台 = 视频号」才有结果，而选「全部类型」+「视频号」则行为取决于是否有跨类型同值 —— 筛选组合的语义会变得不一致。**当前无类型限定是正确设计，不动。**
⚠️ 附带：筛选下拉选项来源仍是 `LIVE_ROOM_PLATFORM`（`:490`）→ Q3 选方案 B 时，此处需按类型联动，是方案 B 的主要复杂度来源。

**统一教训（适用于所有 grep 类判据）**：

1. **判据必须用「语义/结构」判定，不能用「子串出现」判定** —— 子串会同时命中 *代码* 与 *解释代码的注释*（J3），也会因*字面微调*而漏掉同义表述（J2）。
2. **期望数字不得绑定时序假设** —— 「未构建时应输出 N」这类写法在主流时序下无判别力（J1）。要判「产物是否已同步」，用**内容指纹**（正向标记 + 反向旧串 + 存在性/唯一性）。
3. **扫描面要逐项确认**：构建产物目录（`staticfiles/`/`dist/`）、历史迁移目录（`migrations/`）、注释行 —— **三处都可能产生假红/假绿**，每处都要显式排除或显式处理。
4. **每条判据必须带「改前基线数字 + 逐处位置」** —— 否则「应为 0」无法判定是「已清理」还是「没抓到」；且基线本身会在实现推进中漂移（本次 R-5 基线由 7 漂到 0，而残留仍在 ⇒ 漂移 ≠ 清理）。
