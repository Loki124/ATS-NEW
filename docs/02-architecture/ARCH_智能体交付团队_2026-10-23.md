# ARCH_智能体交付团队（minimax-bot 7 Bot + 15 Subagent）

> 日期：2026-10-23　|　状态：设计已确认，待落地　|　作者：Verifier
> 适用范围：ATS-NEW（`/Users/loki/WorkBuddy/招聘助手/ATS-NEW`）及后续同类项目

## 1. 背景与问题

minimax-bot 插件（官方 v0.7.7）已在本机安装并运行（Mini App runtime `running`，runId `1cef0754-7546-4f5a-ae11-1f854a94945d`），
团队已有 6 个 Bot、3 个群。但**落盘状态显示这套团队从未真正跑通过一条完整交付链**：

| 角色 | 总派发 | done | cancelled | failed | unknown | 成功率 |
|---|---|---|---|---|---|---|
| 精细书记员 | 6 | 2 | 2 | 1 | 1 | 33% |
| 牛逼架构师 | 5 | 3 | 1 | 1 | 0 | 60% |
| 高级CTO | 5 | 2 | 2 | 0 | 1 | 40% |
| 优秀QA | 3 | 2 | 1 | 0 | 0 | 67% |
| 专业研究员 | 2 | 0 | 1 | 1 | 0 | 0% |

三个根因（均已核实）：

1. **主 Bot 的 instructions 仍是默认模板**（245 字符，内容是「帮用户搭建 Bot 团队」），团队没有交付总控。
2. **交付链缺「定义要做什么」这一环**：历史 9 个批次的链条是 架构师→CTO→QA→书记员，没有需求定义角色。
3. **团队记忆近乎空置**：`memory/team.md` 只有一行「回复尽量简短」。

## 2. 目标与非目标

**目标**

- 建立一条「需求 → 契约 → 实现 → 独立验收 → 归档」的双轨交付流程，每一环有明确角色、明确产物、明确判据。
- 人在两个闸口介入（方案确认、合并确认），中间实现全自动。
- 任何时刻可见团队在干什么（执行中实时可见 + 3 小时态势报告）。

**非目标**

- 不追求「无人值守全自动」：实测节拍下方向错误的止损窗口是 1 个批次 ≈ 66 分钟，无人值守代价过高。
- 不追求 Bot 数量最大化：Bot 数量不改变吞吐，只增加 roster 提示长度与协调成本。
- 不改变插件自身代码；所有设定通过 minimax-bot 的 MCP 工具完成。

## 3. 关键约束（均为实测基线，不是估算）

15 个任务一批（并发 2）墙钟 ≈ 4.1 小时。

## 4. 组织方案选型

| 方案 | Bot 数 | 到闸口1 | 全流程 | 结论 |
|---|---|---|---|---|
| 一 · 职能流水线（7 Bot 串行） | 7 | 99 min | 198 min | ❌ 6 棒串行，大半时间在等 |
| **二 · 双轨制** | **7** | **66 min** | **132 min** | ✅ **采用** |
| 三 · 单主控 + 专家池 | 4 | 33 min | 99 min | ❌ 把需求定义压回 Chief，用速度换质量 |

**决策依据**：方案二与「两闸口」同构（闸口1 = 定义轨产物，闸口2 = 验收通过 + 合并决策），
主链只有 4 跳；并行集中在执行轨内部（worker subagent 文件互斥）；
且「专业角色独立」已被实测验证（架构师 60%、QA 67% 成功率最高）。

#### 6.2.1 大内总管 —— `update_bot（改人设）`

`bot_id`: bot_eb1214f30be5　`role`: 交付总控：拆解、派活、验收整合、唯一对外口径

```text
你是团队总管兼交付总控，负责把一个需求从进来带到可合并、可追溯的交付物。

工作方式：
1. 收到需求先用 1-2 句话复述目标、范围与验收标准再动手；含糊处按最小可行解释收敛，并在首轮写清你的假设。
2. 阶段固定为两轨：定义轨（产品经理 → 牛逼架构师）→ 闸口1 → 执行轨（高级CTO → 优秀QA → 精细书记员）→ 闸口2。
3. 闸口1：把《交付说明书》（产品经理的 PRD + 架构师的技术契约 + 分层验收标准）交给用户确认，未确认不得进入执行轨。闸口2：把验收报告 + 改动清单 + 合并影响预览交给用户确认，未确认不得合并。
4. 派活用 dispatch_tasks，request_id 用「<需求简名>-<阶段>-<日期>」，重试复用同一 ID；单批不超过 4 个任务。
5. 派完必须在本轮输出里写下 batch_id——后续状态查询与进度汇报都靠它。
6. 失败任务重跑必须换新 request_id（<原ID>-r2）：同 ID 同内容只会返回原来那个失败。
7. 状态 unknown 代表结果待确认，不自动重派；要重新派发用新 request_id。
8. 用 get_tasks 查进展，不逐个问 Bot 进度——问进度是派工，会拖慢交付。
9. 子产出必须由你验收，不合格就派补充任务；不要原样转贴子 Bot 的报告，用你自己的话整合。
10. 只有你向用户汇报。异常（failed / unknown / 阻塞 / 到闸口）立即通告，不要等定时报告；定时态势由精细书记员负责。
11. 跨群协作只在单聊发起（post_group 在群聊中禁用）；群里用 @名字 接力。
12. 已确认的决定写入团队记忆，过程资料留在对话里。

派活映射：
- 诉求模糊、体验类、需澄清 → 产品经理
- 外部选型、版本风险、竞品对照 → 专业研究员
- 涉及接口、数据模型、迁移 → 牛逼架构师
- 闸口1 已过 → 高级CTO
- 实现自测通过 → 优秀QA
- 闸口2 归档或不可逆决定 → 精细书记员

边界：不亲自写 PRD、契约或代码；不把内部编号暴露给用户；不给没验证过的结论背书。
```

## 9. 两闸口执行流程

```
【定义轨】串行 2 跳
  产品经理 ──PRD + 产品层验收标准──▶ 牛逼架构师 ──技术契约 + 技术层验收标准──┐
   (派 explore×3 摸底)            (派 explore+worker)                     │
                                                                            ▼
                                              ◆ 闸口1：人工确认《交付说明书》◆
                                                                            │
【执行轨】1 跳并行 + 2 跳串行                                         ▼
  高级CTO ──派 worker×5(文件互斥)+verifier×2──▶ 优秀QA ──▶ 精细书记员        │
   (实现 + 自测)                        (独立验收)      (归档)              │
                                                                            ▼
                                              ◆ 闸口2：人工确认合并 ◆
```

### 9.1 步骤与产物

| 步 | 执行者 | 动作 | 产物 | 门禁判据 |
|---|---|---|---|---|
| 0 | 用户→Chief | 一句话描述需求 | Chief 复述目标/范围/验收标准 | 含糊处写明假设 |
| 1 | Chief | 派 PM（诉求模糊/体验类/需澄清）或派架构师（需求已定但涉及契约） | 任务回执 + batch_id | batch_id 已写入输出 |
| 2 | PM → 架构师 | 定义轨串行 | PRD + 技术契约 + 分层验收标准 | 需求已明确时 PM 可只出范围确认与验收标准，不重写 PRD |
| 3 | Chief | 汇总《交付说明书》→ **闸口1** | 等待人确认 | 范围清楚 / 非目标明确 / 每条验收标准可判定 / 契约覆盖变更点 / 风险与回滚已知 |
| 4 | Chief | 派 CTO（带契约版本号 + 文件归属 + 验收标准表 + 门禁命令） | 任务回执 + batch_id | 闸口1 已确认 |
| 5 | CTO | 派 worker×5 并行实现 + verifier×2 交叉复核 | 改动清单 + 命令结果 | 文件互斥声明齐全；门禁命令实跑并贴输出 |
| 6 | Chief | 验收 CTO 产出 → 派 QA | 任务回执 | 自测证据齐（文件:行号/命令/退出码） |
| 7 | QA | 逐条核对产品层 + 技术层标准 | 验收报告 + 未验证项清单 | 区分产品缺陷 vs 工具/环境问题；[R]/[H] 项不勾选 |
| 8 | Chief | 派书记员归档 | 台账条目 + ADR | 续号追加，不覆盖他人条目 |
| 9 | Chief | 汇总 → **闸口2** | 验收结论 + 改动清单 + 合并影响预览 | 等人确认后方可合并 |

### 9.2 异常处理（贯穿全程）

| 状态 | 含义 | 处置 |
|---|---|---|
| `failed` | 任务失败 | Chief **立即**通告（并入当前回合，不等定时报告）；重派必须换新 `request_id`（`<原ID>-r2`） |
| `AGENT_UNAVAILABLE` | 宿主 agent 不可用 | 插件内置重试 8s/20s 已耗尽；等数分钟再重派，属环境问题非产品缺陷 |
| `unknown` | 结果待确认（进程中断） | **不自动重派**；闸口前由人确认结果是否已落库 |
| `waiting_for_user` | 等人回答 | 立即告知用户 |
| `cancelled` | 已取消 | 确认是否需要重派 |

## 10. 进度可见性

### 10.1 三层设计

| 层 | 场景 | 机制 | 占槽 | 新角色 |
|---|---|---|---|---|
| L1 执行中实时 | 想看现在谁在干什么 | Mini App 任务页 + 执行记录侧栏 + 消息 live 活动行 + event 事件 + 会话摘要角标 | 否 | 否 |
| L2 里程碑 | 想看到哪一步了 | Chief 在闸口1 / 闸口2 / 批次收尾时汇报一次 | 否（并入已有回合） | 否 |
| L3 定时报告 | 长任务、跨天、态势监控 | `create_schedule` | 是，1 槽/次 | 否 |

**L1/L2 是免费的**：宿主已把活干完（`setLive()` / `attachEvent()` / `broadcastSummary()` 均为回合内附带事件）。

### 10.2 L3 的归属与参数

| 报告类型 | target_bot | kind | 参数 |
|---|---|---|---|
| 团队态势 | 精细书记员 | interval | `every_minutes=180`（schema 最小 5） |
| 一次性回看 | 大内总管 | once | `in_minutes=30` |
| 每日晨报 | 精细书记员 | daily | `time=09:00` |

```
create_schedule(
  kind = "interval",
  every_minutes = 180,
  name = "团队态势报告",
  target_bot = "精细书记员",
  prompt = "按你的态势报告格式产出一份当前态势：当前阶段、在跑批次与各任务状态、台账增量、异常（failed/unknown/waiting_for_user 必须显式列出）、下一步、需要人决策的事项。状态无变化时只写一行「无变化」并简述当前阶段。只读状态，不派工、不改计划。"
)
```

**三条硬规则（写进 Chief 的定时任务 prompt）**

1. **只读状态**（`get_tasks`），**禁止**用 `message_bot` 问进度——问进度是派工，每个派工实测均耗 33 分钟且占并发槽。
2. **不改变交付流**——不派工、不改计划、不催任务，它是只读旁路。
3. **状态无变化就只回一行**「无变化」，不展开全量。

**频率依据**：3 小时 = 每天 8 次报告 = 每天 8 个槽（对比 30 分钟一次的 48 槽）。
但 3 小时 > 单次交付周期 2.2 小时，所以 L3 只做**跨需求态势**，单次交付的关键节点由 L2 闸口通告覆盖。

**生命周期**：批次开始时创建 → 批次归档后 `delete_schedule` 删除。
**硬约束**：定时任务**只在 Mini App 进程运行时触发**，Mini App 关了就断。

| 验证剧场检查 | [R]/[H] 项标注为「未验证，需运行时工具 / 需人工确认」，**无一项被勾成通过** |
| 异常可见性 | failed / unknown 在闸口2 之前被显式报告，无静默吞掉 |
| 台账纪律 | 续号追加，无覆盖他人条目，提交只 add 台账一个文件 |
| batch_id 可追溯 | Chief 派工回合输出中有 batch_id，书记员台账已登记 |
| 状态机完整 | `dispatch-probe.py` 输出的状态分布中，无「未归类失败」 |

### 13.3 数据验收基线

历史基线：21 个任务 → 9 done（43%）、7 cancelled、3 failed（全部 `AGENT_UNAVAILABLE`）、2 unknown。
剔除宿主不可用导致的 3 个批量失败后：9/18 = **50%**。

首轮交付判定标准：**done 率 ≥ 50%，且无未归类失败**；`cancelled` 属正常人工干预，不计入失败。

探针脚本：`/tmp/mavis-verify/dispatch-probe.py`（只读 `state.json`，输出状态分布/耗时/失败模式/群接力强度）。

### 13.4 落地后实测：单回合响应时长

2026-10-23 落地后对 6 个 Bot 各做一次"自我介绍"探针（`requestId: team-retrofit-check-*`），单回合一等答案耗时：

| Bot | 单回合一等答案耗时 |
|---|---|
| 精细书记员 | 10.4 s |
| 优秀QA | 24.6 s |
| 专业研究员 | 51.3 s |
| 高级CTO | 68.3 s |
| 牛逼架构师 | 99.8 s |
| **大内总管** | **400.5 s** |

两条推论：

1. **轻量任务量级远低于重交付基线**。此前 33.1 min/任务是重交付（写文档、改代码）的耗时；状态查询、简短复核、格式化类任务实测在 **10–400 秒**。因此 3 小时态势报告的频率绰绰有余（报告本身预期 10–100 秒量级）。
2. **主 Bot 比同伴慢 4–40 倍**，因其 brief 注入完整团队名册（7 Bot + 3 群）与全部工具说明。**这实测验证了「roster 膨胀拉长每个 Bot 的 prompt」**——且主 Bot 是最严重的一个。继续增加 Bot 会进一步拖慢总管，是新增 Bot 数量必须克制的直接证据。

## 14. 风险与已知边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 汇报挤占交付槽 | 每次定时报告占 1 槽（全局仅 3 槽） | 3 小时一次；禁止用派工问进度 |
| 定时任务断档 | Mini App `on-demand`，进程停则不触发 | 用前先确认 Mini App 在运行 |
| 失败重跑被幂等挡住 | 同 `request_id` 返回原 failed | 换 `<原ID>-r2` |
| `unknown` 被误当失败 | 结果待确认 ≠ 失败 | 显式列在态势报告；人工确认后处理 |
| 角色闲置 | 研究员实测 2 次派发 0 成功 | 已给出明确触发条件；连续 2 个批次未被调用即收缩该角色 |
| 团队记忆过载 | 每轮仅注入 6,000 字符 | 只放已确认决定；过程资料留各 Bot 私有 |
| 单一 API 账户 | 7 Bot 共用一个 `apiKey`，限流共享 | 避开整点并发；必要时降 effort |
| Bot 写权限无机制约束 | Bot 跑在 `mavis` 上，工具含 `write`/`edit` | 「PM/研究员不写代码」是 instructions 约束而非机制约束；由 QA 核对改动文件清单兜底 |
| 改造不可逆 | `update_bot` 覆盖后原 instructions 丢失 | 改造前快照存于 `docs/02-architecture/ARCH_智能体交付团队_回滚基线_2026-10-23.md` |
| M3 的 effort 不生效 | 运行时模型目录未为 M3 提供 `thinking.efforts` | **待复查**（非永久限制）：目录更新后改一次 `update_bot` 即可；或改用 Flash |
| 主 Bot prompt 膨胀 | 总管单回合 400.5s vs 同伴 10–100s，因 brief 注入全量名册 | 克制 Bot 数量；名册随需求增长时改用按需点名 |

## 附录 A：机制速查

| 机制 | 关键事实 |
|---|---|
| Agent vs Subagent vs Bot | Agent = 宿主角色定义（agent.md：提示词 + 工具白名单 + features）；Subagent = `task` 工具拉起的 branch session；Bot = minimax-bot 插件的人设封装，跑在 `mavis` agent 上 |
| 子代理上下文 | 无父会话历史，prompt 必须自包含 |
| 并发上限 | subagent 10/父会话；Bot 任务 2；全局槽 3 |
| `post_group` | 仅单聊发起，群聊回合禁用（含 Chief 与管理员） |
| `start_helper` | 全新隐藏会话；禁止 `ask_user`、禁止调用团队工具；产出报告交回 Bot 验收 |
| `recall` / `remember` | 先 `recall` 再带 `expected_revision` 改；冲突返回 `memory_conflict` |
| 权限 | 只有主 Bot 能 `create_bot` / `create_group`；普通 Bot 越权 `forbidden` |
