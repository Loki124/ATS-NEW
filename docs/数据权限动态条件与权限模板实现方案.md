# 数据权限动态条件 + 权限模板 实现方案

> 目标：支持「需求的所属部门 **包含** 当前用户的负责部门」这类**动态条件**，并支持在指标模板中预置权限模板、再于数据权限中引用。
> 现状基线：`apps/data_permission`（编译）+ `apps/core/scope_resolver.py`（执行）+ `apps/metrics`（指标模板）。
> 本方案在此基础上**增量扩展**，不改动现有静态多值路径。

---

## 0. 现状盘点（方案的事实依据）

### 0.1 已有能力与缺口

| 能力 | 现状 | 缺口 |
|---|---|---|
| 条件组/条件两级布尔表达式 | ✅ `expr_compiler.py` 6 条语法规则，组内 AND/组间 OR 可覆盖 | — |
| 维度 → ORM 字段映射 | ✅ `field_map.py:19` `demand.dept → department_id` | — |
| 静态多值匹配 | ✅ `dimension+operator(in)+values[{id,label}] → Q(field__in=[])` | 值必须配置时手工选死 |
| 部门树层级 | ✅ `Department.path = /root/a/b/`，`save()` 自动维护 | 未被权限计算利用 |
| 行级执行链路 | ✅ `scope_filter_q(entity=…) → role_entity_scope_q → compile_scope_q → Q` | 编译函数**拿不到 user**，无法注入动态值 |
| 指标模板 | ✅ `MetricTemplate`（指标口径模板） | **无权限模板概念** |
| 用户负责部门 | ⚠️ `User.department`（FK 单值）+ `Department.leader`（一人可管多部门） | 无统一「负责部门」解析器 |

### 0.2 关键约束（决定方案形态）

1. **`compile_scope_q(payload, entity)` 当前是无状态纯函数** —— 要注入用户上下文，必须加参数，这会影响全部调用方。
2. **`Department.leader` 的 `related_name='+'`**（`models.py:199`），没有反向属性名 → 只能 `Department.objects.filter(leader=user)` 查询，**这是「负责部门」多值的主要来源**。
3. **现有代码坚持 fail-safe / fail-closed**：`enforcement.py:162` 编译失败 `no-op`；`scope_resolver.py:43` 异常 `fail-closed 到 SELF`。动态条件**必须沿用该基调**，且动态解析失败要比静态更严格（静态失败是 no-op，动态失败必须**拒绝**）。
4. **`DataPermissionRule` 行级已统一由 `scope_resolver` 作真相源**（`enforcement.py:3-5` 注释明示），新能力必须挂在 `compile_scope_q` 这条唯一路径上，不能另起炉灶。

## 1. 数据权限规则：字段定义、包含关系、多值与动态上下文

### 1.1 条件结构扩展

现状（`api/data-permission.ts:44-63`）只有静态 `values`。新增 **`valueSource` + `dynamicKey`** 两个字段：

```ts
export type PermValueSource = 'static' | 'dynamic';
/** 动态值来源（运行时由后端注入，前端不可选具体值） */
export type DynamicSourceKey =
  | 'currentUser.departments'   // 当前用户负责的部门集合（新增）
  | 'currentUser.deptSubtree'   // 当前用户负责部门 + 其所有子部门
  | 'currentUser.id'
  | 'currentUser.bu';

export interface PermCondition {
  id: string;
  kind?: 'relationship' | 'attribute';
  // 关系维度
  dimension?: string;
  operator: string;
  values?: PermValue[];          // 保留：static 时使用
  // —— 新增 ——
  valueSource?: PermValueSource; // 缺省 = 'static'（向后兼容，旧数据零改动）
  dynamicKey?: DynamicSourceKey; // valueSource='dynamic' 时必填
  /** 动态集合与业务字段的包含关系（仅 dept 维度支持，见 1.2） */
  relation?: 'exact' | 'in_subtree' | 'contains' | 'overlap';
  // 属性条件（不变）
  field?: string;
  fieldName?: string;
  value?: unknown;
  meta?: { min?: string | number | null; max?: string | number | null };
}
```

**向后兼容保证**：`valueSource` 缺省即 `static`，`relation` 缺省即 `exact`（等价于现有 `operator='in'` 语义）。存量 `scope_payload` 无需迁移即可继续编译。

### 1.2 「包含」语义的四档定义（`relation`）

设 `U` = 当前用户负责部门集合，`D(req)` = 单条需求的所属部门（`demand.department_id`）。

| relation | 数学定义 | 业务含义 | 典型用例 |
|---|---|---|---|
| `exact` | `D(req) ∈ U` | 只看本部门 | 部门专员只看自己部门 |
| `in_subtree` | `D(req) ∈ ⋃_{u∈U} subtree(u)` | 本部门 + 所有下级 | 部门负责人看本部门全部需求 |
| **`contains`** | `∃u∈U: D(req) 是 u 的祖先` | **需求部门是负责部门的父级** | **本需求场景**：用户负责「智能BG/前端组」→ 可见归属「智能BG」的全部需求 |
| `overlap` | `exact ∨ in_subtree ∨ contains` | 双向任一成立 | 矩阵型组织 |

**为什么 `contains` 必须单独存在**：现状 `in` 只能表达 `D ∈ U`，无法表达「我负责子部门、却要看父部门的需求」这一极其常见的诉求。用 `Department.path` 前缀匹配实现：

```python
# D 是 u 的祖先  <=>  u.path 以 D.path 为前缀
contains  ⟺  D.id ∈ { d.id : ∃u∈U, u.path.startswith(d.path) }
```

### 1.3 动态上下文解析器（后端唯一真相源）

新增 `apps/data_permission/context_resolvers.py`：

```python
from apps.core.models import Department, User

class ContextResolveError(Exception):
    """动态上下文解析失败 —— 上层必须 fail-closed（拒绝），不得放行。"""

def _responsible_departments(user: User) -> list[Department]:
    """当前用户负责的部门 = 所属部门 ∪ 其作为 leader 管辖的部门。

    注意 User.department 是单值 FK，而 Department.leader 反向 related_name='+'
    （models.py:199 无名），故 leader 侧只能显式查询 —— 这正是"负责部门"天然多值的来源。
    """
    ids = set()
    if user.department_id:
        ids.add(user.department_id)
    ids.update(
        Department.objects.filter(leader=user)
        .values_list('id', flat=True)
    )
    return list(Department.objects.filter(id__in=ids))


def _subtree_ids(depts: list[Department]) -> set[str]:
    """按 Department.path 前缀展开子树（与 scope_resolver._subtree_ids_from_dept 同源语义）。"""
    if not depts:
        return set()
    out = set()
    for d in depts:
        out.add(d.id)
        out.update(Department.objects.filter(path__startswith=d.path)
                   .values_list('id', flat=True))
    return out


def resolve_dynamic(key: str, user: User) -> set[str]:
    """解析动态值来源为「部门 id 字符串集合」。失败一律抛 ContextResolveError。"""
    if key == 'currentUser.departments':
        return {d.id for d in _responsible_departments(user)}
    if key == 'currentUser.deptSubtree':
        return _subtree_ids(_responsible_departments(user))
    raise ContextResolveError(f'未注册的动态值来源: {key}')
```

> **设计要点**：解析器只产出**集合**，不做 ORM 查询拼接。包含关系的判定留在编译层，保证解析器可单测、可缓存。

### 1.4 编译层改造（`expr_compiler.py`）

新增辅助函数（放在 `expr_compiler.py` 或新文件 `dynamic_compiler.py`）：

```python
def _compile_dynamic_dept(cond: dict, field: str, dimension: str, *, user) -> Q:
    """动态部门条件 -> Q。仅 dept 维度支持（field 存在性由 field_map 保证）。

    fail-closed 约定：user 缺失 / 来源未注册 / 解析异常 / 结果为空
    一律返回 Q(pk__in=[])（拒绝一切数据），绝不退化为无约束放行。
    """
    from .context_resolvers import ContextResolveError, resolve_dynamic

    # 非部门维度暂不支持动态（避免给 user/creator 维度错误的树语义）
    if dimension != 'dept':
        return Q(pk__in=[])
    if user is None or not getattr(user, 'is_authenticated', False):
        return Q(pk__in=[])          # 匿名：无上下文 -> 拒绝

    try:
        ids = resolve_dynamic(cond.get('dynamicKey'), user)
    except ContextResolveError:
        logger.warning('[expr_compiler] 动态值来源解析失败, fail-closed: %s', cond.get('dynamicKey'))
        return Q(pk__in=[])
    except Exception:                 # noqa: BLE001 — DB 异常等同样拒绝
        logger.exception('[expr_compiler] 动态上下文解析异常, fail-closed')
        return Q(pk__in=[])

    if not ids:
        # 用户没有负责部门 -> 看不到任何数据（与 _own_dept_ids 返回 [] 时的语义一致）
        return Q(pk__in=[])

    relation = str(cond.get('relation') or 'exact')
    if relation == 'contains':
        # 需求部门是负责部门的祖先：取所有「路径前缀命中」的部门 id
        ancestor_ids = _ancestor_dept_ids(ids)
        if not ancestor_ids:
            return Q(pk__in=[])
        return Q(**{f'{field}__in': list(ancestor_ids)})
    if relation == 'in_subtree':
        ids = _subtree_ids_from_ids(ids)
        if not ids:
            return Q(pk__in=[])
        return Q(**{f'{field}__in': list(ids)})
    if relation == 'overlap':
        return (Q(**{f'{field}__in': list(ids)})
                | Q(**{f'{field}__in': list(_subtree_ids_from_ids(ids))})
                | Q(**{f'{field}__in': list(_ancestor_dept_ids(ids))}))
    # exact（默认）
    return Q(**{f'{field}__in': list(ids)})
```

## 2. 指标模板中预置权限模板

### 2.1 为什么独立建模而非塞进 MetricTemplate

现有 `MetricTemplate`（`metrics/models.py:199`）是**指标口径**模板（指标 + 运算符 + 参数域），`param_config` / `value_domain` / `calc_params` 全服务指标求值。而权限模板的生命周期（复用度、版本、被引用关系、失效传播）与指标完全不同，塞进去会让 `MetricTemplate` 承担两种语义。

**方案**：新增 `DataPermTemplate`（权限模板），`MetricTemplate` 通过一个 JSONField **预置引用清单**，满足「在指标模板中预置、再于数据权限中引用」。

### 2.2 数据模型

```python
# apps/data_permission/models.py 新增
class DataPermTemplate(UUIDModel, FullAuditModel):
    """数据权限模板 —— 可复用的条件组预设，供数据权限规则实例化引用。

    与 MetricTemplate 的区别：MetricTemplate 描述「指标口径」，本模型描述
    「可见数据范围」，二者通过 MetricTemplate.scope_template_refs 弱关联。
    """
    code = models.CharField(max_length=32, unique=True, db_index=True)  # DPT+4 位
    name = models.CharField(max_length=64)
    module_key = models.CharField(max_length=32, db_index=True)          # 适用模块
    description = models.CharField(max_length=255, blank=True, default='')

    groups = models.JSONField(default=list)
    """模板体：与 scope_payload.groups 同构的 [{expr, conditions:[...]}]。
    conditions 中占位符以 ${paramKey} 书写，实例化时替换。"""

    params = models.JSONField(default=list)
    """参数声明：[{key, label, valueType:'dept'|'user'|'text'|'number',
                    required, default, enum?}]"""

    status = models.CharField(max_length=16, choices=Status.choices, default=Status.ENABLED)
    version = models.PositiveIntegerField(default=1)
    objects = SoftDeleteManager()
    all_objects = models.Manager()
```

`MetricTemplate` 增加：


### 2.3 内置模板：部门包含规则

系统预置（seed）一个模板，直接对应本需求：

```json
{
  "code": "DPT0001",
  "name": "本部门及所辖部门",
  "moduleKey": "demand",
  "params": [
    {"key": "relation", "label": "包含关系", "valueType": "text",
     "required": true, "default": "contains",
     "enum": ["exact", "in_subtree", "contains", "overlap"]}
  ],
  "groups": [
    {
      "expr": "",
      "conditions": [
        {
          "kind": "relationship",
          "dimension": "dept",
          "valueSource": "dynamic",
          "dynamicKey": "currentUser.departments",
          "relation": "${relation}"
        }
      ]
    }
  ]
}
```

`${relation}` 是**参数占位符**，实例化时被绑定值替换。

在指标模板上预置：

```json
MetricTemplate(name="智能BG 需求口径").scope_template_refs =
  [{"templateCode": "DPT0001", "bindings": {"relation": "contains"}}]
```

### 2.4 参数化绑定规则

- 占位符语法：`${key}`，仅允许出现在 `conditions[].relation` 与 `conditions[].values[].id` 两处（**白名单**，防止注入到 `dynamicKey` / `dimension` 等控制字段）。
- 校验：实例化时逐个检查 `params` 中 `required=true` 的键是否有绑定值；缺失则报错「模板【X】缺少参数：【Y】」。
- 转义：绑定值若含 `${`，用 `\${` 转义；解析后仍做一次「占位符全消解」断言，杜绝半解析状态。

## 3. 数据权限引用模板的机制

### 3.1 存储形态：来源标记 + 内容快照

引用后**不外链**，而是把模板体**深拷贝并绑定参数**写入实际 `scope_payload`，同时打来源标记：

```json
{
  "moduleKey": "demand",
  "mode": "scope",
  "expr": "",
  "groups": [
    {
      "id": "g_1",
      "expr": "",
      "templateRef": {
        "templateCode": "DPT0001",
        "templateVersion": 1,
        "templateName": "本部门及所辖部门",
        "bindings": {"relation": "contains"}
      },
      "conditions": [
        {"kind": "relationship", "dimension": "dept",
         "valueSource": "dynamic", "dynamicKey": "currentUser.departments",
         "relation": "contains"}
      ]
    }
  ]
}
```

> **为何快照而非外链**：模板是「起草工具」，不是「运行时真相源」。若运行时实时读模板，则管理员改模板会让所有在用规则**静默语义漂移**（最危险的权限缺陷）。快照让每条规则的实际语义固化在保存那一刻。

### 3.2 实例化算法

```python
def instantiate(template: DataPermTemplate, bindings: dict) -> dict:
    """模板 -> 实际 groups（深拷贝 + 参数替换 + 完整性断言）。"""
    for p in template.params:
        if p.get('required') and not bindings.get(p['key']):
            raise TemplateBindError(f'模板【{template.name}】缺少参数：【{p["label"]}】')

    payload = json.loads(json.dumps(template.groups))   # 深拷贝
    raw = json.dumps(payload, ensure_ascii=False).replace(r'\${', '\x00')

    for p in template.params:
        val = bindings.get(p['key'], p.get('default'))
        raw = raw.replace('${%s}' % p['key'], json.dumps(val, ensure_ascii=False)[1:-1])

    if '${' in raw.replace('\x00', ''):
        raise TemplateBindError('模板存在未绑定的占位符')
    groups = json.loads(raw.replace('\x00', r'${'))

    # 绑定结果仍需通过通用校验（维度/运算符/动态来源合法性）
    reason = validate_scope_payload({'expr': '', 'groups': groups}, template.module_key)
    if reason:
        raise TemplateBindError(f'模板绑定后不合法：{reason}')
    return groups
```

### 3.3 优先级与冲突处理

沿用现有三层结构，**不引入新概念**：

| 层级 | 规则 | 现状是否已有 |
|---|---|---|
| L0 模板 vs 手写 | 同一模块内，所有条件组（模板实例化组 + 手写组）地位**完全平等**，按 `module.expr` 组合（留空则组间 OR） | ✅ `compile_scope_q` L348-350 |
| L1 多角色 | **RBAC 并集（OR）**：任一角色的该模块规则为 ALL → 全量；NONE 贡献空集；CUSTOM 各自编译后 OR | ✅ `role_entity_scope_q` L152-177 |
| L2 角色 vs 默认 scope | 有角色自定义范围 → **替换**默认 scope（不叠加）；无 → 回退 `resolve_scope` 四层堆栈 | ✅ `scope_filter_q` L495-501 |

**冲突处理三条明规则**：

1. **ALL 短路**：任一角色 ALL → `Q()`（全量），CUSTOM 规则被忽略。现状已实现。
2. **模板不提升权限**：模板只产出 `scope_payload`，最终可见范围仍由 `mode`（none/all/scope）与上述并集决定。模板无法把 `scope` 变成 `all`。
3. **动态条件不放宽**：即使同一组内 AND 了静态 `department__in=[全部部门]`，只要同时含动态条件且动态解析失败，整组仍 fail-closed（AND 语义下空集即为空集，天然满足）。

### 3.4 模板版本漂移

- 已实例化的规则固定 `templateVersion`，**不自动升级**。
- 模板 `version` 递增后，列表页对引用旧版本且 `template.status=ENABLED` 的规则展示「模板有新版本」标记，由管理员**显式**执行「升级到 v{n}」（走一次完整的 `instantiate` + 校验 + 用户确认）。
- 模板被软删：引用它的规则**继续按快照执行**（不失效、不报错），UI 标注「模板已删除」。

|---|---|---|
| 智能BG | `/智能BG/` | — |

→ 负责部门 `U = {前端组, 后端组}`
→ `contains` 取 U 的所有祖先 → `{前端组, 后端组, 智能BG}`

| 需求 | 所属部门 | 判定 | 张三可见 |
|---|---|---|---|
| REQ-001 | 智能BG | 智能BG 是 前端组 的祖先 | ✅ |

**边界行为表**

| 场景 | 期望 | 实现 |
|---|---|---|
| 用户未挂任何部门 | 看不到任何需求 | `resolve_dynamic` 返回空集 → `Q(pk__in=[])` |
| 动态来源未注册 | 拒绝全部 + 服务端告警日志 | `ContextResolveError` → fail-closed |
| 用户上下文缺失（`user=None`） | 拒绝全部 | 显式检查 `is_authenticated` |
| 数据库查询异常 | 拒绝全部 + exception 日志 | `except Exception` → fail-closed |
| 该条件与其他条件 OR | 静态分支不受影响，仍可放行 | OR 语义下空集为 no-op（见下方警示） |
| 非 dept 维度用 dynamic | 保存期即拒绝 | `validate_scope_payload` 拦截 |

> ⚠️ **必须在设计评审时确认的一条**：动态条件与其他条件 **OR** 组合时，动态解析失败会退化为 no-op（不阻断其它分支），这与「fail-closed」的直觉不同。本方案保持该行为（仅 AND 组合才强制拒绝），理由是：OR 场景下其它分支本就是独立授权，强行拒绝会误伤；若安全上要求「解析失败即整规则拒绝」，需在 `compile_scope_q` 顶层加 `has_dynamic and error → raise`，代价是任何一条动态条件故障都会让整个角色的该模块全不可见。**默认选前者（可用性优先），并在此显式记录以便审计。**

## 7. 遗留决策点（需产品/安全确认）

1. **§4.2 的 OR vs AND fail-closed 取舍** —— 默认 OR 场景下动态失败为 no-op。
2. **「负责部门」是否包含 `bu_president` 管辖的 BU** —— 当前方案不含，如需则新增 `currentUser.buDepartments` 来源。
3. **`in_subtree` 是否需要** —— 若产品只需要 `exact` + `contains`，可砍掉以缩小面。
4. **模板是否需要跨模块复用** —— 当前 `DataPermTemplate.module_key` 单值，若需「一个模板多模块」需改为多值或通配。
5. **空部门时的兜底** —— 本方案选择「拒绝全部」。若产品希望空部门时回退 SELF（只看自己创建），需改 `context_resolvers` 返回值并同步 UI 提示。
