### 2.2 需求 1-2 各个角色数据相互隔离

**方案**：补齐 G-02/G-03/G-04 三层基础设施，四角色数据范围。

**第一层 — 实体登记**（`core/entity_scope.py:23` `ENTITY_SCOPE` 补 4 项）：

```python
'campus_person':   {'entity': 'campus_control.Person', ...},
'campus_class':    {'entity': 'campus_rotation.ClassRoom', ...},
'campus_resource': {'entity': 'campus_rotation.LiveRoom', ...},
'campus_arrangement': {'entity': 'campus_rotation.RotationArrangement', ...},
```

**第二层 — 数据权限维度**：

> ⚠️ **实施修正（2026-10-19 实读代码）**：`hrbp` 维度**已存在**于 `DIMENSION_META`（`field_map.py:129-132`，用户类含 `currentUser.id` 动态源），原方案「无任何 campus 维度」的表述偏保守。真正缺的是 **`MODULE_DIMENSION_FIELDS` 的实体条目** —— 该表只登记了 candidate/demand/position/process/talent 五个实体，校招四实体全部缺席。故本层改为「补实体维度字段映射」，而非「新增维度」。

| 维度 key | 中文 | `MODULE_DIMENSION_FIELDS` 字段路径 |
|---|---|---|
| `hrbp` | HRBP | `class_room__hrbp_id`（经班级取 HRBP） |
| `head_teacher` | 班主任 | `head_teacher_id` |
| `mentor` | 带教导师 | `mentor_id` |
| `campus_class` | 班级 | `class_room_id` |

**需同步登记的 4 个 entity**（`MODULE_DIMENSION_FIELDS` 新增 key，供 `role_entity_scope_q` 消费）：

```python
'campus_person':        {'dept': None, 'creator': 'created_by_id', 'unit': True, ...},
'campus_class':         {'dept': None, 'creator': 'created_by_id', 'unit': True, ...},
'campus_resource':      {'dept': 'bu_id', 'creator': 'created_by_id', 'unit': True, ...},
'campus_arrangement':   {'dept': 'current_dept_id', 'creator': 'created_by_id', 'unit': True, ...},
```

> 🔴 **`hrbp`/`head_teacher`/`mentor` 三个维度在 `MODULE_DIMENSION_FIELDS` 中登记后，`scope_filter_q` 才会走 CUSTOM 分支实现「带教导师只看自己带的」。这是需求 1-2「角色数据隔离」的核心机制。**

**⚠️ 实施修正 2 — 隔离能力的真实边界（重要）**：

`ScopeQuerysetMixin.scope_field` **只能按部门 FK 路径过滤**，无法表达「按人际关系隔离」。核对实现后确认：

| 隔离诉求 | 机制 | 可行性 |
|---|---|---|
| HRBP 看本部门及下级 | `scope_field='class_room__hrbp_id'` + DEPT_AND_SUB | ✅ 可行 |
| 班主任看本班成员 | `scope_field='class_room_id'` | ✅ 可行 |
| **带教导师只看自己带的** | `scope_field='mentor_id'` + CUSTOM 规则「mentor 包含 currentUser.id」 | ✅ **可行**，但须管理员在数据权限规则中显式配置 CUSTOM 规则 |

结论：三种隔离均可通过 `scope_field` + `DataPermissionRule` 组合实现，**无需改造 `scope_resolver` 核心**。但「带教导师只看自己带的」依赖 CUSTOM 规则被正确配置，**不配置则回退默认 scope（DEPT/SELF）**，此为设计既有语义，非缺陷。

**第三层 — ViewSet 接入行级隔离**：四个 ViewSet 全部改继承 `ScopeQuerysetMixin`（`core/permissions_v2.py:170`），`permission_required` 改指向新实体码。

**隔离矩阵**：

| 角色 | 校招生档案 | 班级 | 轮岗资源 | 轮岗安排 |
|---|---|---|---|---|

### 6.7 需求 5-7 性别均衡算法

**方案**：新增 `apps/campus_rotation/services/gender_balance.py`

```python
def allocate_by_gender(persons, resources, ratio=MALE_RATIO_TOLERANCE):
    """按性别比例分配校招生到轮岗资源。

    目标比例来自配置（如男:女 = 6:4），允许偏差 tolerance。
    算法：贪心 + 代价函数
      1. 按 BU 维度统计各资源当前男/女占用
      2. 每轮选取「性别比偏离目标最大」的资源，分配当前待分配中占比更高的性别
      3. 并列时按「剩余容量最大」平手，再并列按资源 id 稳定排序（保证结果可复现）
    """
```

**⚠️ 需求已给出兜底**：「短期内若算法难以实现绝对公平，可由 BP 手动调整」→ 算法作为**建议**输出，`suggest_mentor` 式提供「一键应用建议」与「手动调整」双入口，不强制。

**单元测试要求**（`MEMORY.md` 纪律：纯函数不 mount）：
- 男女各 10 人分 2 资源 → 断言偏差 ≤ tolerance
- 单一性别输入（全男） → 不崩溃，偏差超限标记 `imbalanced=True`
- 容量为 0 的资源被跳过
- 同一输入两次调用结果一致（可复现性）

### 6.9 需求 5-9 超 15 天必须输出考核，不足 15 天免考

**规则引擎**：

```
actual_end - actual_start >= 15 天 → assessment_status = 'REQUIRED'（必须考核）
                          <  15 天  → assessment_status = 'WAIVED'（免考）
阶段置 DONE 时，若 REQUIRED 且无 assessment_result → 拒绝流转，返回 400
```

**边界口径**：`>= 15` 计入考核（`timedelta(days=15)`），`actual_end` 为空时用 `planned_end`；两者皆空则 `assessment_status='PENDING'` 不阻断，由定时任务兜底提醒。**「15 天是否含首尾」需你确认**（见 §7）。

**实现位置**：`RotationStage` 的 `clean()` + `RotationArrangementSerializer` 的阶段流转校验，Celery 定时任务 `rotation_assessment_reminder` 每日扫 `REQUIRED` 且临近未考核记录。
