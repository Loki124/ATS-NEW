## 3. 真实数据导入口径

导入命令：`manage.py import_campus_lifecycle_data`（支持 `--dry-run` / `--limit` / `--only` / `--skip-users` / `--skip-schools`）。
数据文件：`apps/django/apps/campus_control/management/commands/data/campus_lifecycle_seed.json`（1.49 MB，仓库内可追溯，由目标站前端产物逆向抽取）。

### 3.1 导入映射与「不编造」决策

| 源 | 目标 | 口径 |
|---|---|---|
| 878 校招生 | `campus_control.Person` | 编号 `CS`+8 位（**不复用候选人 C 序列**）；工号 `25`+6 位补 8 位；院校标签只保留 `985/211/双一流`，其余归 `其他`；专业名称存 `major_name`，标签按关键词判 `工学/其他`；`batch` 原样（7 个真实批次号） |
| 10 + 177 + 8 名册 | `core.User` + `user_roles` | 密码**不可用**（不给默认可登录口令）；班主任→`HEAD_TEACHER`、导师→`CAMPUS_MENTOR`、HRBP→`HRBP` |
| 1026 院校 | `library.School` | 按校名幂等；存量院校**只补省份**，不混写标签词汇 |
| 49 条异常 | `campus_assessment.FeedbackRecord` | 报告人/问题/处理方式/处理人/证据一一对应；有处理日期 → 状态「已闭环」 |
| 125 待分配 | `campus_placement.PositionDemand` + `PositionApplication` | 按意向部门去重成岗位需求；每人生成第一志愿（状态「已填报」） |
| 116 直播间台账 | `campus_rotation.RotationResource` | 平台/地点原样；`capacity=7`（单间均值上限口径）；**社招/校招逐间不分摊**（部门级数字属编造）→ 写入 remark |

### 3.2 **未**导入项（如实登记，避免"看起来导全了"）

| 项 | 条数 | 原因 |
|---|---|---|
| 轮岗经历 | 778 | 源为学生内嵌数组，本仓 `RotationArrangement` 是带审批状态机的独立模型，字段口径差异大，强行映射会产生假状态 |
| 轮岗计划 / 定岗计划 | 2 / 30 | 源表含分组表头行，无稳定业务键 |
| 直播间盘点明细 | 133 | 部门级聚合；逐间分摊属编造 → 只按 BU 口径写入资源 remark 与导入摘要 |
| BG·BU 计划 / 院校 offer 统计 | 23 / 296 | 统计接口实时聚合，不落库（避免与实时数双源） |

## 4. 影响面（如实告知）

### 4.1 人员主数据从 56 → 934

导入 878 名历史校招生后，`campus_control.Person` 由 56 条增至 934 条。

**连带影响**：本仓 **28 条全局管控规则**（`ControlRule.bu` 为空 = 适用全部部门）的样本量随之从 56 变为 934，
性别/院校/专业比例类规则的**结论会变化**。这是「导入全部真实校招生主数据」这一决策的必然结果，
不是缺陷；如需保持管控结论不变，应对导入数据设置 `counted=False`（不计入核算）——
**本次未擅自设置**（导入的是真实在职人员，`counted=True` 更贴近事实），是否调整由业务侧决定。

### 4.2 部门枚举扩容

`campus_control.constants.DEPTS` 由 4 档扩为 7 档（补 `能人BG` / `能智BG` / `能本BG`）。
依据：源数据 878 人中 139 人落在这三个真实存在的 BG；归入「综合BG」= 事实错误。
既有 4 档顺序**未变**，既有管控规则的目标 BU **不受影响**；新增 BG 暂无专属规则。

### 4.3 新增 195 个不可登录账号

名册导入创建的 `core.User` 密码不可用 —— 只用于「人 - 档案」关联与数据隔离，不构成可登录账号。
