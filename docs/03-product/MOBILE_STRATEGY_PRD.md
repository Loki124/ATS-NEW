# 移动端双端战略与 PRD（P0 方案）

> 状态：待评审 ｜ 版本：v0.1 ｜ 日期：2026-08-25
> 决策来源：用户确认「内部同事 + 外部候选人 分开两个移动端」

## 0. 决策记录

| 项 | 结论 |
|---|---|
| 整体方向 | 内部同事端、外部候选人端 **两套独立移动端** |
| 内部端形态 | **企业微信 H5 微应用**（现有 Vue SPA 套企微壳） |
| 外部端技术 | **微信小程序（uni-app）**（独立代码库） |
| 下一步 | 先出本架构 + PRD 方案文档，评审后再落地 |

---

## 1. 战略定位：为什么必须分开

| 维度 | 内部同事端 | 外部候选人端 |
|---|---|---|
| 受众 | HR / 面试官（企业员工） | 投简历的陌生人 |
| 核心目标 | 招聘提效（审批、填评价、看进度） | 用户触达与转化（投递、查进度、确认） |
| 入口 | 企业微信工作台 | 微信「搜一搜 / 扫码 / 会话卡片」 |
| 鉴权 | 企微免登 → 内部 JWT | 微信 openid/unionid OAuth |
| 权限模型 | 现有字段级 ACL（内部角色） | candidate 自服务（**只看自己**） |
| 合规 | 企业内部数据 | 候选人个人信息 PIPL、微信平台规则 |

> 两套受众、入口、鉴权、合规完全不同。硬塞一套会两头不讨好：内部嫌重、外部嫌门槛高。

## 2. 总体架构

```mermaid
flowchart TB
  subgraph Internal["内部端 · 企业微信 H5 微应用"]
    I1[企微工作台入口]
    I2[现有 Vue3 SPA\n(响应式补强+底部Tab)]
    I3[企微 JS-SDK 免登]
  end
  subgraph External["外部端 · 微信小程序 uni-app"]
    E1[微信扫码/搜一搜]
    E2[uni-app 小程序\n(独立代码库)]
    E3[微信 OAuth openid]
  end
  subgraph Backend["共享后端 · Django + DRF"]
    B1[/api/v1/* 内部域\nJWT 鉴权/字段级ACL/]
    B2[/api/v1/candidate/* 外部域\n微信OAuth/强隔离/]
    B3[(MySQL)]
  end

  I1 --> I2 --> I3 --> B1
  E1 --> E2 --> E3 --> B2
  B1 --> B3
  B2 --> B3
```

**关键分叉点**：前端两套、后端共享但 **API 域与鉴权分叉**。后端是唯一真相源，两端口都不直连 DB。

### 技术栈矩阵

| 层 | 内部端 | 外部端 | 共享 |
|---|---|---|---|
| 前端框架 | Vue3 + Naive UI + UnoCSS（现有） | uni-app（Vue 语法） | — |
| 运行容器 | 企微 H5 微应用 WebView | 微信小程序运行时 | — |
| 登录 | 企微 JS-SDK 免登 → JWT | 微信 `wx.login` → openid → token | — |
| 后端 | Django + DRF | Django + DRF | 同一服务 |
| API 域 | `/api/v1/*` | `/api/v1/candidate/*` | 同一网关 |
| 存储 | MySQL | MySQL | 同一库（表按域隔离） |

## 3. 内部端：企业微信 H5 微应用

### 3.1 形态与入口
- 在**企业微信工作台**挂一个「招聘助手」微应用，URL 指向现有 Web SPA。
- 同事点开即免登（企微 JS-SDK 拿 corpid/userid，后端换 JWT），**零安装**。
- 复用现有 90% 页面逻辑，仅做移动化改造。

### 3.2 功能范围（P1 MVP）
1. 候选人列表 / 详情（手机可读）
2. 面试安排确认、评价填写
3. 校招管控关键看板（只读）
4. 企微消息卡片 → 跳转审批

### 3.3 改造清单（基于现状审计）
| 改造项 | 现状 | 目标 |
|---|---|---|
| 响应式覆盖率 | 19/66 页（29%） | **100%** 页面窄屏可⽤ |
| 导航 | 桌面侧栏（≤768 已转抽屉） | 加**底部 Tab** 主导航 |
| 触控目标 | 未系统优化 | 点击区 ≥ 44×44px |
| 企微接入 | 无 | 接 JS-SDK 免登 + 工作台消息 |
| 断点标准 | 各页不统一 | 收敛到统一断点 token |

> 现有 `Layout.vue` 已有 `isMobile≤768 → 侧栏转 n-drawer` 的骨架，可在此基础上扩展，不必重做。

---

## 4. 外部端：微信小程序（uni-app）

### 4.1 形态与入口
- 独立 uni-app 项目，编译为微信小程序。
- 入口：微信内扫码 / 搜一搜 / HR 会话卡片转发。
- 候选人**无需下载 App**，微信里即用。

### 4.2 功能范围
- **P2 MVP**：简历投递（绑定 JD）、投递进度查询。
- **P3 扩面**：面试时间安排与确认、offer 确认、补充材料上传。

### 4.3 独立代码库结构（建议）
```
apps/wechat-mp/                # uni-app 小程序
  src/
    pages/apply/               # 投递
    pages/status/              # 进度
    pages/interview/           # 面试确认
    pages/offer/               # offer 确认
    api/                       # 仅调用 /api/v1/candidate/*
    store/ utils/
```
> 与内部 SPA **不共享代码**（uni-app 编译目标不同），但可沉淀纯逻辑工具（校验、格式化）为共享 npm 包。

### 4.4 后端依赖（开工前置）
- 微信公众平台/开放平台 **appid + secret**（需企业主体资质）。
- 小程序**回调域名、业务域名**配置（ICP 备案域名）。
- 微信登录 `code2Session` 换取 openid 的服务端实现。

## 5. 后端改造（最关键，两端口共用）

### 5.1 鉴权分叉
| 端 | 流程 | Token |
|---|---|---|
| 内部 | 企微免登 userid → 后端映射员工 → JWT | 现有 JWT |
| 外部 | `wx.login` code → `code2Session` openid → candidate 账号 → token | 新增 candidate token |

### 5.2 新增外部 API 域 `/api/v1/candidate/`
- 仅暴露候选人自服务接口：`投递 / 我的投递 / 我的面试 / 我的 offer`。
- **强隔离**：所有查询带 `candidate_id = 当前微信用户`，禁止越权看他人。
- 限流 + 风控：外部端面向公网，必须加频率限制与防刷。

### 5.3 数据模型影响
- 现有 `Person`（内部候选人档案）vs **外部投递人**：需明确映射关系。
  - 方案 A：外部投递先落 `CandidateApplication`，入职后转 `Person`。
  - 方案 B：外部 openid 直接关联 `Person.external_openid`。
- 待定，需在 P0 评审中明确（建议 A，解耦内外数据生命周期）。

### 5.4 安全红线
- 外部域**绝不**暴露内部字段级 ACL 接口。
- 候选人 PII 加密存储、最小必要字段、符合 PIPL。
- 微信 secret 走环境变量，不入库、不进前端包。

## 6. 分期路线与里程碑

| 阶段 | 范围 | 主要产出 | 验收 |
|---|---|---|---|
| **P0** | 本方案评审 | 架构图 + PRD + 后端影响清单 | 用户/研发评审通过 |
| **P1** | 内部端 | 响应式 100% + 底部 Tab + 企微免登 + 消息卡片 | 企微内全流程跑通 |
| **P2** | 外部 MVP | uni-app 小程序 + `/candidate` 域 + 微信登录 | 「投递→查进度」闭环 |
| **P3** | 外部扩面 | 面试确认 + offer 确认 + 补材料 | 候选人端完整体验 |

> 后端 `/candidate` 域与微信登录可在 **P1 并行启动**（不阻塞内部端），建议 P1 同期立项。

## 7. 风险与待确认

1. **微信资质**：外部端需企业主体小程序 appid，若主体/外包未就绪则 P2 阻塞——**需提前确认主体归属**。
2. **合规**：候选人 PII 处理需过隐私合规评审（PIPL）。
3. **uni-app 学习成本**：团队若未用过 uni-app，P2 前需技术摸底。
4. **响应式补强工作量**：47 个未适配页面（66−19）需逐页补 `@media`，建议沉淀统一断点 mixin 降低重复。
5. **数据模型映射**：`Person` vs 外部投递人关系（5.3）需架构评审定案。

---

## 8. 下一步建议
1. 评审本方案（架构、选型、分期）。
2. 确认两个待定项：**微信主体归属**、**Person/外部投递人映射方案**。
3. 评审通过后，先落 P1（内部端），并同期立项后端 `/candidate` 域 + 微信登录（P2 前置）。
