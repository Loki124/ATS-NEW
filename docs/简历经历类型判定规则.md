# 简历经历类型判定规则设计（实习 / 项目 / 工作）

> 适用范围：ATS-NEW 候选人简历解析（`apps/django/apps/add_candidate/services/resume_parser.py`）
> 目标：针对来源多样（校招/社招、国内/海外、中英模板、格式千差万别）的简历，可靠判定每段经历属于「实习 / 项目 / 工作」。
> 状态：当前 `Experience` 模型无类型字段，所有经历被归为 `work_experiences` 一类，本规则为待落地设计。

---

## 1. 为什么不能靠单一信号

不同简历把经历混排的方式完全不同，单看一个维度就会误判：

- **校招简历**：实习经历常混在「工作经历」段里，项目经历可能在独立「项目经验」段，也可能塞进工作段描述。
- **社招简历**：「项目」往往是某段正式工作内的子项目，不应算独立项目经历。
- **海外简历**：英文 `Intern` / `Co-op` / `Part-time` 语义清晰，但模板无中文「实习」字样。
- **在读生**：经历时间与学业重叠，是实习的强信号，但正式兼职也可能重叠。
- **自由职业 / 个人项目**：company 字段为空或填的是项目名而非雇主。

结论：**必须多信号加权 + 优先级裁决**，单信号不可靠。

---

## 2. 判定信号分层（按可靠性从高到低）

### 信号 ① 区块归属（Section Signal）—— 最强
简历若分「实习经历 / 项目经验 / 工作经历」独立区块，区块标题即答案。
- 解析器（如 Affinda）若返回 `section` 元数据 → 直接采用。
- 若解析器未返回 section，需从原始文本按标题分段（可在解析层或后处理补）。

### 信号 ② 职位标题硬关键词（Title Signal）
- **实习**：`实习` / `实习生` / `Intern` / `Internship` / `Co-op` / `暑期实习` / `寒假实习` / `日常实习`
- **项目**（作为职位时较弱，需配合其他信号）：`项目` / `Project`（注意：社招里"项目负责人"是工作内的角色，不等于独立项目经历）
- **工作**：正式职位词（工程师 / 经理 / 专员 / 分析师 / 设计师 / 运营 …）

### 信号 ③ 时间-学业重叠（Temporal Signal）
- 经历时间段落在某段学历 `start~end` 区间内 → **实习强信号**（v2 修正：须先过豁免检查，见 §10.2）。
- 起始时间晚于最后一段学历 `end` → **工作**（已毕业）。
- ~~持续时间 ≤ 6 个月 → 实习倾向~~（v2 废弃：短期正式工作常见，时长不作判定依据）

### 信号 ④ 组织 / 载体（Org Signal）
- 项目经历：`company` 常为项目名称、为空、或"个人/校内"，而非真实雇主法人名。
- 实习 / 工作：`company` 为真实公司名（大厂实习岗尤常见）。

### 信号 ⑤ 描述文本（Content Signal）—— 最弱，仅作软信号
- **实习**：`协助` / `参与` / `配合` / `在…指导下` / `学习`
- **项目**：技术栈罗列（`React`/`Spring`/`PyTorch`）、`负责 X 模块` / `使用 X 实现` / `Git/文档链接`
- **工作**：业绩指标、团队规模、业务结果（`KPI` / `营收` / `用户增长`）

## 3. 裁决优先级（决策树）

```
判定 exp 类型:
  if section 明确(项目/实习/工作):          返回 section 类型        # 信号①（v2 修正：title 实习硬关键词可覆盖 section，见 §10.3）
  if title 含实习硬关键词:                   返回 internship          # 信号②
  if 时间段 ⊂ 在读区间 且 非毕业后:           返回 internship          # 信号③
  if (org 为空 或 像项目名) 且 描述含技术栈:  返回 project             # 信号④+⑤
  if 有真实雇主 且 正式 title:               返回 work                # 默认
  else:                                      返回 unknown             # 无法判定，交人工
```

**默认兜底为 `unknown`，不要硬猜**——错误归类比不归类危害更大（会污染校招筛选标签）。

---

## 4. 冲突消解规则

| 冲突 | 处理 |
|------|------|
| 实习 ∩ 项目（一段经历既像实习又像项目） | 以 section 为准；无 section 时，title 含"实习"→实习，否则看 org 是否真实雇主（项目常填项目名）→项目 |
| 工作 ∩ 项目（社招常见：工作内的项目） | 有真实雇主 + 正式 title → 工作；独立「项目经验」段且无雇主 → 项目 |
| 海外 Intern/Co-op/Part-time | 归入实习（Part-time 若无学业重叠且长期，可标 unknown 交人工） |
| 多段重叠（如读研期间同时有实习+项目） | 逐段独立判定，不互相影响 |

---

## 5. 置信度与人工兜底

- 每条经历返回类型 + `confidence`（高/中/低）。
- 高：section 或硬关键词命中；中：时间/组织信号命中；低：仅文本软信号。
- `confidence=低` 或 `type=unknown` → 前端在简历预览页高亮，提示 HR / 候选人手动修正并落库。
- 校招场景：实习 / 项目是筛选核心标签，必须可修正，不可静默默认。

## 6. 针对现有代码的落地改造建议

### 6.1 数据模型
```python
from enum import Enum

class ExpType(str, Enum):
    INTERNSHIP = 'internship'
    PROJECT = 'project'
    WORK = 'work'
    UNKNOWN = 'unknown'

@dataclass
class Experience:
    period: str
    company: str
    position: str
    summary: str
    exp_type: str = ExpType.UNKNOWN.value   # 新增
    exp_confidence: str = 'low'             # 新增：high/medium/low
```

### 6.2 分类函数（插入 resume_parser.py）
```python
INTERN_TITLE_RE = re.compile(r'实习|intern|internship|co-?op|暑期|寒假|日常实习', re.I)

def _classify_exp(exp: dict, educations: List[Education]) -> tuple[str, str]:
    """返回 (exp_type, confidence)"""
    title = (exp.get('job_title') or '').lower()
    org = exp.get('organization') or ''
    desc = exp.get('job_description') or ''
    section = (exp.get('section') or '').lower()

    # ① 显式 section
    if '项目' in section or 'project' in section:
        return ('project', 'high')
    if '实习' in section or 'intern' in section:
        return ('internship', 'high')
    # ② 标题硬关键词
    if INTERN_TITLE_RE.search(title):
        return ('internship', 'high')
    # ③ 时间-学业重叠
    if _overlaps_study(exp, educations) and not _is_after_graduation(exp, educations):
        return ('internship', 'medium')
    # ④+⑤ 项目软信号
    if (not org or _looks_like_project_name(org)) and _has_tech_stack(desc):
        return ('project', 'medium')
    # 默认工作 / 未知
    if org:
        return ('work', 'medium')
    return ('unknown', 'low')
```

### 6.3 解析层接入
- `_parse_response` 中 `experiences = [_parse_exp(e) for e in ...]` 改为先收集 educations 时间轴，再对每段 exp 调用 `_classify_exp(exp, educations)` 填充 `exp_type` / `exp_confidence`。
- Affinda 若返回独立的 `projects` section → 直接映射 `project` 类型（优先级高于 heuristic）。
- 前端 `store` schema 与简历预览卡片需同步新增 `exp_type` 字段与可编辑修正入口。

## 7. 校招场景特殊考量（腾讯校招）

- 校招筛选高度依赖「实习公司 / 实习时长 / 项目技术栈」，类型判定错误会直接导致人才漏筛或错筛。
- 建议在「人才库 / 校招管控」标签体系里，把 `exp_type` 作为一级可筛选维度，且 `unknown` 必须可批量修正。
- 实习时长（从 period 推算月数）应单独存储，用于校招「实习时长 ≥ N 月」类规则。

## 10. v2 修订（2026-08-26 下午）：法律锚点、四类体系与豁免逻辑

### 10.1 分类体系：三类 → 四主类 + 子类型

| 主类 | 子类型 | 判定本质 |
|------|--------|----------|
| work | 正式 / 自由职业 / 外包派遣 | 正式劳动关系 |
| internship | 日常实习 / 暑期实习 / Co-op | 在读、无劳动关系 |
| project | 校内（毕设/课程/实验室）/ 个人（开源/side project）/ 竞赛 | 非雇佣的能力证明 |
| other | 军旅 / 志愿 / 支教 / 间隔年 | 兜底，不硬塞前三类 |

`unknown` 仅作低置信产物（待人工修正），不是第五分类。

### 10.2 核心锚点（法律事实）与三项豁免

**全日制在校生依法不能建立劳动关系 → 在读期间的企业经历默认 internship。** 该锚点可钉死约八成 case。三项豁免（命中任一 → work）：

- **E1 提前入职转正**：经历结束时间 ≥ 毕业后 3 个月，或描述含「转正 / 三方 / 正式员工」。
- **E2 在职学历**：时间重叠的学历为非全日制 / 在职（MBA、非全工程硕士等）→ 该期间全职经历判 work。
- **E3 先工作后读书**：经历开始时间早于该学历入学（须对**每一段**学历分别对齐，不能只看最高学历）。

### 10.3 信号优先级修正：一致性融合替代「section 一票定案」

| 组合 | 判定 | 置信度 |
|------|------|--------|
| title 实习词 + section 一致 | internship | 高 |
| title 实习词 + section=工作段 | internship | 中高（section 乱用普遍，title 是候选人身份声明） |
| title 无实习词 + section=实习段 | internship | 中（大厂实习 title 常不带「实习」字样） |
| 毕业后 + 真实雇主 | work | 高 |
| 在读 + 企业主体 + 无豁免 | internship | 高（法律锚点） |
| 在读 + 命中豁免 | work | 中高 |

时间线作第三方验证：与上述结论冲突时降一档并留痕。

### 10.4 项目去重（防工作年限虚增）

项目时间完全嵌套于某段实习/工作且主体相同 → `linked_exp_id` 关联为该段经历的 detail，不独立计数；无法关联（时间/主体对不上）→ 独立 project。

### 10.6 落地架构：LLM 判类 + 规则校验混合

- LLM few-shot 判类（语义任务 LLM 更强）；规则引擎做一致性校验：豁免 E1-E3 为硬约束（命中强制 work）、法律锚点强制兜底、结论冲突降置信。
- 输出结构在 `exp_type` / `exp_confidence` 之外增加 `exp_signals`（命中规则留痕，可解释可调试）与 `linked_exp_id`（去重关联）。

### 10.7 前置依赖（地基）

时间线信号可用性 = 教育经历解析质量：各学历入学/毕业/预计毕业（在读生 expected graduation）、全日制属性、休学 gap。教育时间线解析错，§10.2 / §10.3 全部失效。
