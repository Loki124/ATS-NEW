# 资源出入规则（Resource In/Out Rules）

> 状态：**现行规范（2026-10-19 兵哥立项复盘）**
> 配套代码：`apps/core/models_permission_v2.py`、`apps/core/permissions_v2.py`、
> `apps/core/permission_check.py`、`apps/core/management/commands/seed_v2_init.py`、
> `apps/core/migrations/0033_mark_disabled_resources.py`、
> `apps/core/management/commands/verify_resource_status.py`
> 编码规范真源：`docs/DESIGN_资源编码规范.md`
> 护栏：`apps/core/tests/test_resource_code_convention.py`

---

## 0. 为什么要有出入规则（复盘）

2026-10-19 对资源管理链路做一次完整复盘，暴露了三类真实问题，本规则即为对它们的制度性收口：

| 问题 | 现象 | 根因 | 处置 |
|---|---|---|---|
| **A. 停用资源仍可访问**（误导性遗留状态） | 0026/0029 已停用的功能（旧内外部用户列表、Offer 两级审批、字段权限收敛后的孤儿码等），在 `role_permission` 仍残存授权行；`has_perm` 不查 `status`，凭残留授权照样放行 | 授权引擎与资源 `status` 脱钩 | `has_perm` 新增「禁用码缓存」短路：status=0 永拒授权（`permission_check.py`） |
| **B. 停用无可见标记** | 测试 `test_r9` 注释称「0030 迁移打 `[已停用]` 前缀」，但 0030 实为校招码拆分，前缀迁移**从未存在**；后端 grep `[已停用]` 零命中，CI 因测试库空而假绿 | 迁移职责被改作他用，前缀逻辑丢失 | 新建 `0033` 迁移，给所有 status=0 补 `[已停用] ` 前缀（幂等） |
| **C. 种子复活风险** | `seed_v2_init` 对 RESOURCES 内每条码无条件 `update_or_create(status=1)`，一旦停用码被误写回 seed，下次跑种子即被强制启用 | seed 是新增资源唯一真源，却无条件覆盖 status | 护栏 `test_r11` 断言 seed 不得含已知停用码；`verify_resource_status` 巡检复活风险 |

**核心结论**：资源不是「写进 `permission_resources` 就完了」——它还要过**授权生效**、**展示标记**、**下线可逆**三道关。以下规则把这三道关固化到「新增 / 变更 / 停用」三个场景。

---

## 1. 资源模型与生命周期

`PermissionResource`（`permission_resources` 表）是资源的唯一注册表，字段：

| 字段 | 含义 | 约束 |
|---|---|---|
| `resource_code` | 资源编码（唯一键） | 见 §2 编码结构 |
| `resource_name` | 资源名称 | 停用资源由 `0033` 自动加 `[已停用] ` 前缀 |
| `resource_type` | `MENU` / `BUTTON` / `FIELD` / `API` | 与编码种类段一致（R1） |
| `module` | 模块 | **必须 == 编码第 2 段**（R2） |
| `status` | `1` 启用 / `0` 禁用 | **禁用只允许置 0，绝不允许物理删除**（见 §5） |

相邻三张表共同决定「资源能否真正生效」：

- `role_permission`（角色-资源关联，存 `resource_code` 字面量）—— 授权生效面。
- `permission_templates.permission_codes`（JSON 数组，存码字面量）—— 角色授权模板。
- `PermissionResource.status` —— 授权引擎据此拒绝停用码（**2026-10-19 新增**）。

> 🔴 **铁律**：资源码是字符串，跨 `permission_resources` / `role_permission` / `permission_templates.permission_codes` / 前端 `permissionMenu.ts` / 各 `views.py` 的 `permission_required` **五处共存**。任何资源码变更必须同步这五处，漏一处即「静默失权」或「幽灵功能」。

## 2. 统一创建规则（入库前必过）

新增资源**必须先满足以下规则 + 通过 §3 校验**，方可建立。规则真源 `docs/DESIGN_资源编码规范.md`，此处只做汇总与新增项。

### 2.1 编码结构

```
{system_code}:{module}[:{sub_module}...]:{kind}:{action}
```

- 第 1 段 = `recruit`（系统编码）。
- 第 2 段 = `module`，**必须 == `module` 字段**（R2）。
- 中间段 = 子模块层级（0~2 段，按模块实际嵌套深度）。
- 倒数第 2 段 = 种类：`menu` 必须与 `resource_type=MENU` 同现（R1）。
- 最后 1 段 = 动作，必须落在受控词表（`list/create/edit/delete/export/view/approve/assign/publish/close/schedule/feedback/advance/reject/start/stop/approve_l1/approve_l2/confirm/evaluate`…）（R3）。

### 2.2 段数按层级定，不强行拉平

`3 段`（业务域，无子页）/ `4 段`（标准页）/ `5 段`（settings 子页）/ `6 段`（权限下二级子页）并存是**自然结果，不是缺陷**。新资源按所属模块的既有层级定段数。

### 2.3 命名与占位约束

- 分段只允许 **snake_case**（小写 + 下划线，禁连字符/大写，R7）—— `company-brand` 与 `company_brand` 并存是「同名不同码」，最难的静默失权。
- `resource_name` 不得预置 `[已停用] ` 前缀（R10，前缀只来自 `0033` 迁移）。

### 2.4 2026-10-19 新增规则

- **R11（种子禁令）**：`seed_v2_init.RESOURCES` **不得含任何已知停用码**。seed 无条件 `status=1`，含停用码 = 复活。
- **R12（授权生效前提）**：资源建立后，**必须**在授权链路至少有一处可达 —— 要么授予某 `permission_templates`（经 seed 重算 `TMPL_ADMIN` 覆盖全部启用码），要么经 `role_permission` 显式授权；且 `PermissionResource.status` 必须为 `1`。status=0 的资源即使被授权也**永不可访问**（见 §5）。

## 3. 校验条件（入库闸门）

新增 / 变更资源**必须**通过 `apps/core/tests/test_resource_code_convention.py`：

| 校验 | 范围 | 说明 |
|---|---|---|
| `test_seed_not_empty` / `test_no_duplicate_codes` | seed | 非空、无重复码 |
| `test_r4` / `test_r1` / `test_r2` / `test_r3` / `test_r5` / `test_r7` | seed + 库内 | 编码结构合规 |
| `test_r8` | 前端 `permissionMenu.ts` | 一码一独立入口（禁多路径共享） |
| `test_r6` | 模板 | 模板里每个码都能在资源表找到（防悬空码） |
| `test_r9` | 库内 | 停用资源必带 `[已停用] ` 前缀 |
| `test_r10` | seed | seed 名不含停用前缀 |
| `test_r11` | seed | **seed 不得含已知停用码（防复活）** |
| `TestDisabledResourceAuthorization` | 授权引擎 | **停用码即使用户持有授权也拒绝访问** |

> 🔴 护栏只拦「新增违规」，不对存量报警（存量债务已于 2026-10-18 清零）。但 `test_r9` 对库内**全量**停用资源生效——这是停用在库内的真实落地保障。

## 4. 场景一：新增资源（Entry）

**标准流程**：

1. 在 `seed_v2_init.py` 的 `RESOURCES` 追加元组（命令幂等，`update_or_create`）：
   ```python
   ('recruit:{module}:{kind}:{action}', '中文名', 'TYPE', 'module')
   ```
2. 跑护栏：
   ```bash
   cd apps/django && .venv/bin/python -m pytest apps/core/tests/test_resource_code_convention.py -q
   ```
3. 落库 + 播种：
   ```bash
   .venv/bin/python manage.py migrate
   .venv/bin/python manage.py seed_v2_init
   ```
   seed 会自动：① 用 `status=1` 建/更新资源；② 把 `TMPL_ADMIN` 重算为「全部启用码」；③ 失效权限码缓存。
4. **同步五处**（P0，漏一处即静默失权）：
   - `RESOURCES`（已做） + `permission_templates.permission_codes`（由 seed 自动覆盖 `TMPL_ADMIN`；自定义模板须手动含新码）；
   - 前端 `web/app/src/utils/permissionMenu.ts` 追加菜单映射（若该资源是 MENU）；
   - 前端 `web/app/src/utils/permissionModules.ts` 的 `RESOURCE_MODULE_LABELS` **必须覆盖新资源的 `module`**（否则资源管理台显示 `—`）；
   - 后端对应 `views.py` 声明 `permission_required` / `permission_required_map`。
5. **授权生效验证**（穿透真实链路，禁手搓 dict 绕过解析器）：确认该资源对目标角色「可授权、可访问、停用即拒绝」。

> 🔴 **模块映射同步是高频漏点**：`permissionModules.ts` 只收录 seed 的 module 子集。新增带新 `module` 的资源时，必须同步该表，并建议补一条前端 CI 断言（`RESOURCE_MODULE_LABELS` 覆盖 seed 全部 module）—— 详见 §6 待办。

## 5. 场景二：停用资源（Exit / 下线）

**标准流程**（对应问题 A/B，2026-10-19 收口）：

1. **只置 `status=0`，绝不物理删除**（铁律）。
   - 资源码被 `role_permission` 引用，物理删除 = 留孤儿授权 + 丢历史可追溯性。
   - 停用后默认查询面 `status=1`（见 `PermissionResourceViewSet.get_queryset`）自动过滤，退出权限勾选候选；资源管理台用 `?status=all` 仍可审计。
2. **加 `[已停用] ` 前缀**（`0033` 迁移按库内 status=0 动态打，幂等）。使管理员在权限配置 / 资源管理界面一眼区分「在用 / 已停用」。前缀**只来自迁移，不来自 seed**。
3. **授权引擎自动拒绝**：`permission_check.has_perm` 经「禁用码缓存」短路，status=0 资源即使用户角色仍持有授权行也一律拒绝（修复问题 A 的根因）。
4. **保留 `role_permission` 残留授权行**：它们是惰性 + 已明确标记的，既消除误导性，又保留可追溯性，且可逆。如需彻底清除，运行 `verify_resource_status --purge-orphan-grants`（默认关闭，不可逆，需显式确认）。
5. **决策留痕**：在迁移/PR 说明里写明下线铁证（git 提交 / 功能合并），如 `0026`/`0029` 那样。禁用 ≠ 删除，但禁用必须有据。
6. **反向可逆**：`0033` 的 `backward` 剥离前缀并把已知停用码恢复 `status=1`；复活某功能须单独正向处置（重新授权 + 必要的前端映射）。

**巡检工具**：
```bash
# 报告三类问题
.venv/bin/python manage.py verify_resource_status
# 自动补缺失前缀
.venv/bin/python manage.py verify_resource_status --fix
# 含删除孤儿授权（不可逆，谨慎）
.venv/bin/python manage.py verify_resource_status --fix --purge-orphan-grants
```

> 🔴 **禁止在 seed 里「复活」停用码**：seed 无条件 `status=1`，若把停用码写回 `RESOURCES`，下次跑种子即推翻 `0026`/`0029`。`test_r11` 已在 CI 拦截。

## 6. 场景三：变更资源（Change）

资源码**一旦建立即被五处引用**，变更必须同步五处（对应 `DESIGN_资源编码规范.md` §6.1），禁止只改资源表：

| 变更类型 | 唯一做法 | 同步清单 |
|---|---|---|
| **改名**（`resource_name`） | 数据迁移 `Replace` 子串（参照 `0031_rename_campus_control_headcount`） | 仅资源表；若名被前端/模板引用需同步 |
| **改段 / 改 module** | 数据迁移逐条 `update` 资源码 + 同步三处存储（参照 `0028` / `0027`） | ① `permission_resources.resource_code` ② `role_permission.resource_code`（冲突合并去重）③ `permission_templates.permission_codes`（解析 JSON 改写）④ 前端 `permissionMenu.ts` ⑤ 各 `views.py` 的 `permission_required` |
| **改 `module` 字段** | 必须与编码第 2 段一致（R2），迁移修正（参照 `0027_fix_module_field`） | 资源表；前端 `permissionModules.ts` 的模块中文名 |

> 🔴 **改名 / 改段的「离线同步点」**（前端映射 + 后端 `permission_required`）**不进库**，必须脚本按映射表全量改写并验证零残留，否则留下「同名不同码」分叉（最难排查的静默失权）。
