# 功能资源码全面启用 · 上线手册（G1–G4）

> 日期：2026-10-11
> 范围：身份管理（功能权限）从「配置了但不生效」改为「前后端真正生效」
> 风险等级：**中高** —— 端点接入资源码校验后，未配置过权限的角色会被 403，**必须按本文顺序执行**

## 1. 背景

改造前，功能权限只落地在 `role_permission` 表，后端仅约 38 个视图校验资源码，其余端点用
`IsAuthenticated` / `IsHROrAbove` / `HasProcessPermission` 放行；前端菜单静态、路由守卫只看角色名，
全站仅 1 处按钮消费了资源码。结果是「在身份管理里配了权限，基本没生效」。

本次改造：端点全部接入 `V2Permission` + 显式读码/写码映射，前端菜单与路由按资源码显隐。

## 2. 上线前置：**seed 从不写 role_permission**

`seed_v2_init` 只写 `PermissionResource` + `PermissionTemplate`，**不写 `role_permission`**；
`init_demo_v2` 建角色时也只写 `template_code`。因此未执行过「身份管理 → 功能权限 → 保存」的
角色在 `role_permission` 里是 0 行，`/api/v1/auth/me/` 返回的 `permissions` 为空数组，
`has_perm()` 一律 False。

**端点一旦接入资源码校验，这些角色会全线 403。** 开发库实测：`HR` 角色挂着 **78 个真实用户**、
授权行数为 0 —— 这是本次最高优先级的风险点。

## 3. 上线步骤（顺序不可颠倒）

推荐直接用脚本（环境无关，含体检 / 预演 / 回填 / 复检 / 回滚指引）：

```bash
# ① 先体检：只读，不改数据。发现「有用户但零授权」会 exit 1
DJANGO_SETTINGS=config.settings.prod scripts/deploy_resource_permissions.sh --check

# ② 预演：看会回填哪些角色、写多少码，仍不写库
DJANGO_SETTINGS=config.settings.prod scripts/deploy_resource_permissions.sh --dry-run

# ③ 正式执行（seed + 回填 + 复检），无人值守加 --yes
DJANGO_SETTINGS=config.settings.prod scripts/deploy_resource_permissions.sh --yes
```

脚本做的事（等价于下列手工步骤）：

```bash
cd apps/django

# ① 补齐资源码与模板（幂等；新增 33 个码，并给 DIRECTOR/SPECIALIST 补配置类码）
python manage.py seed_v2_init

# ② 回填角色权限（先预演）
python manage.py backfill_role_permissions --dry-run
python manage.py backfill_role_permissions

# ③ 校验：抽样真实用户
python manage.py shell -c "
from django.contrib.auth import get_user_model
from apps.core.models_permission_v2 import UserRoleV2
from apps.core.permission_check import has_perm
uid = list(UserRoleV2.objects.filter(role_code='HR').values_list('user_id', flat=True))[0]
u = get_user_model().objects.get(pk=uid)
print(u.username, has_perm(u, 'recruit:settings:dictionary:list'))"
```

开发库实测（第 ④ 步输出）：

```
角色总数 9 / 已回填 6 个，写入 576 行 / 已配置跳过 3 / 无可用权限码跳过 0
HR → TMPL_SPECIALIST 115 码 · INTERVIEWER → TMPL_INTERVIEWER 7 码（按标准角色推断）
```

> 脚本的体检只看 `status=1` 的角色（停用角色不影响访问）。若某角色当前停用、后续要启用，
> 需在启用前再跑一次 `--check`，否则启用后该角色仍是零授权。

`--role <CODE>` 可单独回填某个角色；`--grant-all` 用于无模板的自定义角色（谨慎，会给全部码）。

## 4. 前端 fail-open 语义（重要）

前端菜单/路由过滤**不是**按「permissions 为空 = 无权限」处理，而是：

- `permissions` 为空数组 = 该角色**从未配置过功能权限** → **一律可见**，交由后端 403 兜底；
- `permissions` 非空 → 必须命中对应资源码才可见；
- 超管恒可见；
- 未在 `utils/permissionMenu.ts` 登记的路径视为公共入口，恒可见。

这样即使漏跑回填步骤，前端也不会出现空菜单锁死用户的情况（后端会返回 403，属于可诊断的正常行为）。

## 5. 本次变更清单

**后端**
- `V2Permission` 新增：纯 `APIView`（无 DRF action）支持 `permission_required_map` 按 **HTTP method** 匹配，
  POST-only 视图可声明精确码（`:create` / `:export`），不再退化成派生 `:edit`。
- 20 个文件、80+ 端点接入 `V2Permission`：校招管控、字典、动态字段、查重规则、标准简历、公告、
  品牌、外部集成、需求配置、候选人标签与批量操作、简历解析上传、面试评价、抢单池、数据看板与导出任务、
  渠道成本、通知模板、背调订单、MOU、流程/阶段/轮次/规则/时限/自动化/准入条件、指标与规则引擎。
- `RecruitmentProcessViewSet` 类级从 `HasProcessPermission` 改为 `V2Permission`（此前其 map 是死配置）。
- 只读视图补读码：KPI、公司库、码表库、流程模板、自动化日志；
  `/permissions/`、`/permissions/resources/`、`/permissions/templates/`、`/data/export/` **保持全员可读**
  （是 `/me` 权限面板的数据源，收紧会反噬前端）。
- 新增管理命令 `backfill_role_permissions`；seed 新增 33 个资源码，修掉 `recruit:channel:list`、
  `recruit:user_app_data_scope:list` 两个「声明了但从未定义」导致非超管恒 403 的隐性锁死。

**add_candidate 建档管线（2026-10-12 补齐）**

`b07f99dc` 的清单里列了「简历解析上传」，但该模块的 `views.py` 被陈旧工作区副本覆盖回
`IsHROrAbove`，实际未接入资源码。现按同一口径补齐，9 个视图的码映射如下：

| 端点 | 码 | 说明 |
|---|---|---|
| `upload-and-parse` / `manual-create` / `bulk-create` | `recruit:candidate:create` | 建档三入口 |
| `replace-file` | `recruit:candidate:edit` | 换附件重解析 |
| `scoring/start` | `recruit:candidate:edit` | 评分改写候选人字段 |
| `parse-status` / `duplicate-check` | `recruit:candidate:list` | 查重是 POST 但语义为读，显式给 method 键，避免被派生为 `:edit` |
| `scoring/stream` | `recruit:candidate:list` | SSE 只读 |
| `resume-parser-config` GET | `recruit:settings:standard-resume:menu:view` | |
| `resume-parser-config` POST/PUT | `recruit:settings:standard-resume:edit` | 属「标准简历设置」，候选人码不能越权切换解析引擎 |

角色口径未收窄：旧的 `IsHROrAbove` 允许 `SUPER_ADMIN/HRBP/HR`，回填映射里 `HRBP`/`HR`
都落在含 `create`/`edit` 的 `TMPL_SPECIALIST`；超管走 `is_super_admin` bypass。
`tests/test_v2_permission_wiring_add_candidate.py` 有一条守卫断言
`HR_TIER` 的模板映射不含 `candidate:create` 时必须变红 —— 若将来有人把 `HRBP`
误映射到只读的 `TMPL_DIRECTOR`，全公司 HRBP 会在上传简历时集体 403。

**前端**
- `usePermission` 新增 `isPermissionConfigured` / `canAccess`（fail-open）。
- 新增 `utils/permissionMenu.ts`：40+ 条「前端路径 → 资源码」映射（最长前缀优先）+ 递归菜单裁剪。
- 主导航、设置菜单按配置过滤；路由守卫新增资源码校验（支持 `meta.permission`）。

## 6. 行为变化（需要业务确认）

1. **配置类页面收紧**：字典、动态字段、码表库、招聘流程配置、校招管控、指标、规则引擎等此前对任意
   登录用户开放，现在需要对应资源码。为不让 HR/HRBP 突然失去这些页面，已把配置类码补进
   `TMPL_DIRECTOR`(113) 与 `TMPL_SPECIALIST`(115)，更细粒度由管理员在「身份管理 → 功能权限」自行勾选。
2. **审批码真正生效**：只勾「审批Offer / 审批需求」不再能审批（此前只要 `:edit` 就能过）。
   有 `:edit` 无审批码的身份将失去审批能力 —— 这是审批码的本意，HRBP 模板已含 `offer:approve` / `demand:approve`。
3. **导出单独授权**：候选人批量导出改为要求 `recruit:candidate:export`（此前只要 `:edit`）。
4. **建档管线按资源码收紧**：简历上传 / 手动建档 / 批量建档需 `recruit:candidate:create`，
   换附件与启动评分需 `:edit`。前端上传按钮**尚未**按资源码隐藏，权限不足时表现为
   「点了必 403」而非按钮消失 —— 与第 2 条同理，属前端按钮级消费待补的部分。
5. **解析引擎切换跨资源授权**：`resume-parser-config` 的写操作校验
   `recruit:settings:standard-resume:edit`，持候选人资源码的身份不再能切换解析后端。

## 7. 回滚

- 前端菜单/路由过滤：回滚前端即可（fail-open，不会造成用户可见故障）。
- 端点校验：回滚后端代码。已写入的 `role_permission` 行**无需清理** —— 它是「身份管理」的正常数据，
  保留后重新上线仍然生效。
- 若只想临时放开写操作：`V2_STRICT_WRITE_GUARD=False` 仅对**未声明权限码**的视图生效，
  对本次已显式声明的视图无效，因此不能用它回滚本次改造。
