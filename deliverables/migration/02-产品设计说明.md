## 0. 设计立场（一句话）

**校招生管理助手不是一个"新模块"，而是 ATS 校园招聘域的一组"业务工作台"。** 凡是与「人 / 部门 / 字典」有关的配置，一律并入 ATS 既有配置页、不新增入口；凡是"对这批校招生做动作"的作业流，才新建页面。判据只有一条：**新增页面的用户是在"做事"，还是在"改配置"。**

### 1.3 「校招专属」→ 「校园招聘」改名决策

**结论：改名。**

| 维度 | 保留「校招专属」 | 改为「校园招聘」 ✅ |
|---|---|---|
| 语义准确度 | 「专属」= 附加的、附带的。现分组同时承载 4 个**主作业页** + 2 个配置页，「专属」已不成立 | 直接命名业务域，与 `systemStore.isCampus` 的语义对齐 |
| 用户预期 | 用户会以为点进去只有"配置类"功能，作业页放这里显得错位 | 打开就知道这是校招业务的全貌 |
| 与 ATS 命名惯例 | 其他分组都是名词短语（需求与职位 / 候选人 / 面试管理），「校招专属」是唯一的形容词短语 | 恢复一致 |
| 显隐控制 | 「专属」二字重复表达了"仅校招系统可见"，而这已由 `isCampus` 代码控制，文案冗余 | 同左，去掉冗余 |

改名成本：`Layout.vue` 一处 label + i18n 一处；`permissionMenu.ts` **零改动**（按 path 匹配，与 label 无关）。

**D. 用户想找导师的完整路径**：
`主菜单 校园招聘 → 人员管理`（看这批校招生各自的导师）→ 行内「编辑」→ 轮岗信息 → 带教导师（**这是业务视角**：给某个校招生派导师）。
`设置 → 用户管理 → 工具栏「校招身份」= 带教导师`（这是**名册视角**：管理导师这个池子）。两者定位不同，都保留。

**E. 删除原导师库的影响**：原导师库可新建"张三"（无工号、无部门、无账号）。迁移后导师**必须**是 ATS 真实用户（`user_id` FK）。**这是有意的收紧**：原名单里的幽灵数据无法被分配、无法被通知、无法统计带教饱和度。

## 4. 「直属上级」字段的交互设计（要求 5 的前端落点）

### 4.1 选择器形态决策

**决策：远程搜索下拉（`PersonPicker` 单选），不复用 `n-tree-select` 树选择器。**

| 判据 | 部门树选择器 | 远程搜索下拉 ✅ |
|---|---|---|
| 候选规模 | ATS 部门数十~数百 | 内部员工**数千~数万** |
| 组织语义 | 有天然层级（parent/path），树是正确表达 | 人**没有层级语义**，`direct_manager` 是单跳关系，多跳靠 `subordinates` 反查 —— 树会误导用户以为要选"上级部门的人" |
| 渲染 | 树 DOM 全量渲染，数千节点卡顿 | 虚拟滚动，只渲染可视 10 行 |
| 已用先例 | 部门选择器全站统一 `n-tree-select`（`UserDirectory`） | `ApplyPositionSelector` / `PositionChips` 等已是远程检索范式 |

**形态规格**（`PersonPicker`，新增组件）：

```
┌────────────────────────────────────────────────────────────┐
│ 直属上级  [ 🔍 搜索姓名 / 花名 / 工号                    ▾] │  ← n-select filterable remote
├────────────────────────────────────────────────────────────┤
│ 王五 · 技术中心/前端组                        [不可选 · 你的下级] │
│ ──────────────────────────────────────────────────────────── │
│ 张伟 · 技术中心/前端组 · 20260312                            │
│ 刘洋 · 微信支付/微信基础                                    │
└────────────────────────────────────────────────────────────┘
```

| 属性 | 规格 |
|---|---|
| 组件 | `n-select` + `filterable` + `:remote="true"` + `:loading` + `clearable` |
| option label | `姓名 · 部门末级/末级（工号）`；多字同名时补花名 |
| option 禁用 | ① 自己（`option.value === 编辑中的 userId`）② **自己的所有下级**（含间接）③ 状态非 ACTIVE 的用户 |
| 禁用项呈现 | **保留在列表里**（而非隐藏）→ 让用户理解"存在但不能选"；label 后追加灰色原因后缀；`n-tooltip` 说明 |

### 4.4 循环与自选规则（UI 表达）

| 规则 | 判定 | UI 表达 |
|---|---|---|
| **不可自选** | `option.value === editingUserId` | 选项**显示但 disabled**，label 后缀 `不可选 · 这是你自己`；tooltip「不能把自己设为自己的直属上级」 |
| **不可选下级** | `candidate ∈ descendants(editingUser)`（含**间接**下级，通过 `subordinates` 递归闭包判定） | 选项显示但 disabled，后缀 `不可选 · TA 是你的下级`；tooltip 展示路径「TA 是你的下级，选了会形成环形上级关系」 |
| **不可形成环（A 选 B、B 选 A）** | 提交时后端做可达性校验；前端**乐观预检** | 前端在 `onUpdate:value` 时同步算一遍 `wouldCreateCycle`：若 `editingUser ∈ descendants(selected)` → **不清空已选值**，就地 `n-form-item-feedback status="error"`：「选了 王五 就形成环了：王五 的直属上级是你。」+ [换一个] |
| **批量场景** | 用户管理目前**无批量改上级**入口（不新增） | — |
| **存量环**（历史脏数据） | 加载编辑弹窗时若发现 `editingUser ∈ descendants(currentManager)` | 该字段 `n-select` 显示 `⚠ 存在环形上级` `n-tag type=warning`，tooltip 给出环路径（如 `A → B → C → A`）+ [去修复]；不阻止打开弹窗，但保存时**必须先解环** |

### 4.5 「不可自选、不可选下级」的可见性原则

遵守 **R-211「颜色 + 图标 + 文字两种以上」**：

| 表达通道 | 具体做法 |
|---|---|
| 颜色 | disabled 项文字 `--ink-faint`（不用 `disabled` 的纯灰，避免读不清，R-210 对比度） |
| 图标 | 每条 disabled 原因前加 ⚠ 图标（`AlertCircleOutline`，R-216 统一 ionicons5） |
| 文字 | 明确的 `不可选 · <原因>` 后缀（不只靠颜色，色盲用户可读） |
| 交互 | 仍可 hover 出 `n-tooltip` 解释原因 —— 让用户"能选但被告知为什么不行"，优于直接消失 |
