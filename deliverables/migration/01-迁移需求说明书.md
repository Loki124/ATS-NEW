## 1. 迁移目标与成功判据

### 1.1 迁移目标

把「校招生管理助手」的**轮岗全生命周期管理能力**，作为 ATS「校园招聘」体系下的一个业务模块落地，同时完成三件结构性收敛：

1. **入口收敛**：原项目 6 大模块的菜单统一归入 ATS「校园招聘」分组，不再自建一级菜单。
2. **主数据收敛**：原项目自建的 5 类基础库（轮岗部门/导师/班主任/直属上级/平台），全部改为复用 ATS 既有主数据能力（部门表、用户表 + 身份体系、数据字典），消除"两套部门""两套人员"的分裂。
3. **原型转生产**：从内存态原型升级为有持久化、有权限、有审计的服务端系统。

### 1.2 迁移成功判据（可判定）

以下 8 条全部满足，才可判定迁移成功。任一条不满足即视为未完成。

| # | 判据 | 判定方式 | 证据形式 |
| --- | --- | --- | --- |
| **G-1** | **菜单归属**：ATS 中存在且仅存在一个「校园招聘」分组，校招生管理助手的全部页面都在该分组下，无任何独立于 ATS 菜单体系的入口 | 1) 检查主菜单树，不存在第二个承载校招生助手的分组；2) 直接访问任一模块 URL，未授权用户菜单不可见但接口返回 403（不能出现"菜单藏了但数据能拉到"） | 截图 + 越权接口响应码 |
| **G-2** | **基础库去重**：系统中不存在任何独立的「轮岗部门」「导师」「班主任」「平台」主数据表或本地常量源 | 1) 数据库中不存在以轮岗部门/导师/班主任/平台为名的独立表；2) 全前端代码中不存在源项目 `ROT_DEPTS` / `ROT_MENTORS` / `ROT_MONITORS` / `ROT_PLATFORMS` / `ROT_LOCS` 的硬编码副本 | 代码检索结果 + 表清单 |
| **G-3** | **部门单一事实源**：所有轮岗相关场景中出现的部门，全部来自 ATS 部门表，且与用户在用户管理中看到的部门是同一个实体 | 1) 修改某个 ATS 部门名称后，轮岗安排/轮岗资源页面的对应展示同步变化（无需二次配置）；2) 数据库中轮岗记录的部门字段指向 ATS 部门表主键，不存在部门名称字符串副本 | 修改验证记录 |
| **G-4** | **身份合并**：导师/班主任是用户身份（角色）而非独立实体；同一用户可同时持有导师与班主任两种身份，且在用户管理中可见、可检索、可筛选 | 1) 用户管理列表可按"身份=导师"筛出所有导师；2) 将 A 用户同时授予导师与班主任身份后，该用户在两种筛选下均出现，且无任何数据冲突或报错 | 筛选截图 + 授权记录 |
| **G-5** | **直属上级闭环**：直属上级字段在用户管理中可选择、可在列表展示、可作为筛选条件，且筛选结果正确 | 1) 用户列表新增"直属上级"列并显示姓名；2) `?direct_manager=<id>` 筛选只返回该上级的直接下属（不含二级及以下）；3) 越权用户不代填上级字段 | 接口响应 + 列表截图 |
| **G-6** | **配置归并**：不存在独立的「系统管理」入口；原 5 类基础库维护能力全部收敛到 ATS 现有配置项中 | 1) 菜单树中无「系统管理」独立入口；2) 平台选项在数据字典管理页可增删改，且直播间平台下拉实时反映字典变化 | 字典页截图 + 下拉联动验证 |
| **G-7** | **权限生效**：校招生模块的每个页面/操作都有对应资源码，无"未受权限管辖的裸接口" | 1) 遍历校招生模块全部写接口，每个都有显式权限声明；2) 使用无权限账号调用写接口一律 403，且返回体含明确中文提示 | 权限矩阵表 + 403 响应记录 |
| **G-8** | **数据可追溯**：所有轮岗业务数据由服务端持久化，重启服务/刷新浏览器不丢失；历史操作有审计记录 | 1) 修改数据后重启后端服务并刷新页面，数据仍在；2) 任一条轮岗记录可查到创建人与最后修改人 | 重启前后对比截图 + 审计记录 |

### 1.3 明确不作为成功判据的项

- 不以"页面像素级还原源原型"为判据。源项目是独立设计语言（浅色毛玻璃玻璃拟态），ATS 有自己的设计语言与 AGENTS.md R-101~R-111 强制规范，**迁移后以 ATS 规范为准**。
- 不以"源项目全部功能都搬过来"为判据。详见第 4 章范围裁剪。
- 不以"示例数据在生产库里建出来"为判据。示例数据仅用于开发/测试环境演示。

## 2. 角色与权限需求

### 2.1 源项目角色（PRD 第 3 章）

| 源角色 | 关注模块 | 核心诉求（PRD 原意） | 迁移后是否保留 |
| --- | --- | --- | --- |
| 校招管理部运营 | 轮岗安排、轮岗资源、系统管理 | 分派名额、盘点容量、配置基础库 | ✅ 保留，是主要使用者 |
| HRBP | 人员管理、班级管理 | 查看花名册、人员档案、班级归属 | ✅ 保留 |
| 班主任 | 班级管理、人员管理 | 维护班级与备注、查看所带学生分布 | ⚠️ 身份保留（见要求 4），操作权限收敛 |
| 导师 | 人员管理 | 查看所带校招生档案与阶段 | ⚠️ 身份保留（见要求 4），操作权限收敛 |
| 直属上级 | 轮岗安排（轮岗中） | 查看名下校招生轮岗进展 | ⚠️ 从"基础库字符串"变为"用户属性"，权限继承用户本人 |

**重要变化**：源项目中"班主任""导师""直属上级"既是基础库里的字符串，也是隐含的角色。迁移后这四者统一由 ATS 用户体系承载（见 2.3）。

### 2.2 ATS 既有角色体系

ATS 使用 `RoleV2`（`system_code` + `role_code` + `role_name`，唯一约束 system_code+role_code），`UserRoleV2`（user + role_code + system_code，唯一约束 user+role_code），配合 `RolePermissionV2` + `PermissionResource` 做功能授权。已存在的模板角色至少含 `SUPER_ADMIN`（全量资源）。菜单可见性由 `permissionMenu.ts` 的 `MENU_PERMISSION_RULES` 按**路径最长前缀**匹配资源码，fail-open 语义（未登记路径恒可见）。

**这条 fail-open 是本模块最大的权限风险点** —— 新页面若未登记映射表，菜单对所有人可见。因此本次迁移要求：**校招生模块所有新路径必须 100% 登记进 `MENU_PERMISSION_RULES`**，不允许依赖 fail-open 兜底。

### 2.3 迁移后角色映射

| 源角色 | 迁移后承载方式 | 可做什么 | 看不到什么 |
| --- | --- | --- | --- |
| 校招管理部运营 | ATS 角色（建议 `CAMPUS_OPS`） | 轮岗安排全部写操作（分配/批量调整/终止/审批流转）、轮岗资源增删改、班级增删改、人员基础信息编辑 | —（全模块可见） |
| HRBP | ATS 角色（建议 `CAMPUS_HRPB`） | 人员管理花名册只读 + 人员档案只读；按其负责 BU 范围过滤 | 轮岗安排写操作、轮岗资源写操作、系统配置 |
| 班主任 | **用户身份（角色码）** `CAMPUS_MONITOR` | 班级管理中仅限"我所带班级"的行可见可编辑；人员管理中仅限"我带的校招生"可见 | 他人班级、他人的校招生、轮岗资源、全部配置项 |
| 导师 | **用户身份（角色码）** `CAMPUS_MENTOR` | 人员管理中仅限"我带的校招生"的档案只读 | 班级管理、轮岗资源、全部配置项 |
| 直属上级 | **不新增身份**，用用户表既有 `direct_manager` 关系表达 | 在轮岗安排「轮岗中」页签中，以只读方式看到 `direct_manager = 我` 的校招生 | 他人下属；一切写操作 |
| 校招生本人 | 建议**不做独立 ATS 账号**（见 OQ-3），但须在需求上保留"未来查看本人轮岗档案"的能力位 | 仅读本人档案 | 其他一切 |

### 2.4 需要新增的权限点（语义需求，命名由架构师定）

按"资源语义"分类，共需 **6 类**。架构师需按 ATS 既有 `recruit:{module}:{action}` 风格命名并登记到 `PermissionResource` 与 `MENU_PERMISSION_RULES`。

| 编号 | 权限点语义 | 覆盖范围 | 谁需要 |
| --- | --- | --- | --- |
| **P-1** | **校招生助手菜单可见** | 整个模块的菜单入口（1 个资源码，供 `MENU_PERMISSION_RULES` 匹配） | 所有能进入本模块的角色 |
| **P-2** | **轮岗安排读取** | 三阶段列表 + 筛选 + 详情 | 运营、HRBP、直属上级 |
| **P-3** | **轮岗安排写入** | 编辑分配、批量调整、保存并分配、审批通过、终止轮岗 | 仅运营 |
| **P-4** | **轮岗资源读取 / 写入** | BU 汇总、直播间明细、编辑/停用/删除、CSV 导入导出、测算参数调整 | 读写可分开授权；写入仅运营 |
| **P-5** | **班级管理读取 / 写入** | 班级列表、编辑班主任/班长/备注 | 班主任（仅本人班级）、运营（全量） |
| **P-6** | **人员管理读取 / 写入** | 花名册、档案查看 | 读取：HRBP/导师/班主任/运营；写入（班级/班长/HRBP/批次）：仅运营与 HRBP |

**明确不需要新增权限点的项**（收敛点）：
- 「导师库增删改」「班主任库增删改」→ **不需要**。因为它们已变为身份，身份授予走 ATS 既有"用户授权/角色分配"能力。
- 「平台库增删改」→ **不需要**。走既有数据字典管理页权限。
- 「轮岗部门库增删改」→ **不需要**。走既有部门管理页权限。

这是本模块权限设计的核心收敛成果：**新权限点从源项目的 5 类基础库增删改 + 业务增删改（约 20+ 个）压缩到 6 类共约 10 个码**。

### 2.5 数据可见性（行级）要求

菜单/接口级权限解决"能不能进"，还需定义"进去后能看到谁"：

| 角色 | 行级可见范围 |
| --- | --- |
| 运营 | 全部 |
| HRBP | 其负责 BU（部门树第二级）下的全部轮岗记录 |
| 班主任 | `班主任 = 我` 的轮岗记录；`班级.班主任 = 我` 的班级行 |
| 导师 | `带教导师 = 我` 的轮岗记录 |
| 直属上级 | `直属上级 = 我` 的轮岗记录 |

**要求**：行级过滤必须在**服务端**生效（Queryset 级过滤），不得仅靠前端传筛选参数实现。

## 3. 六条硬性要求的逐条需求拆解

---

### 要求 1：菜单统一归入 ATS「校园招聘」模块

#### 用户意图
源项目自带一套独立菜单（人员管理 / 轮岗安排 / 轮岗资源 / 班级管理 / 系统管理，胶囊式 5 模块）。迁入 ATS 后，这套菜单会与 ATS 现有的「校招专属」分组并列甚至打架，用户会困惑"到底哪个是校招"。用户要求收拢到 ATS 既有的校园招聘体系下，形成单一入口。

#### 功能需求

| 编号 | 需求 |
| --- | --- |
| **F1-1** | 在 ATS 主菜单树中，「校招专属」分组（`systemStore.isCampus` 为真时出现，现含 `/settings/campus-ambassador`、`/settings/campus-session`）扩展为承载校招生管理助手的全部子项 |
| **F1-2** | 校招生管理助手的每个页面在 ATS 中必须归属下列四者之一，不得出现分组外入口：<br>① 校园招聘**分组**（业务操作类页面：轮岗安排、轮岗资源、班级管理、人员管理）；<br>② ATS **系统设置**的既有配置页（配置类能力，见要求 2/3/4/6）；<br>③ ATS **用户管理**页（导师/班主任维护，见要求 4）；<br>④ 无入口（纯被其他页面内联调用的能力） |
| **F1-3** | 分组名称与图标沿用 ATS 现有范式，不引入源项目的胶囊式设计 |
| **F1-4** | `isCampus` 为假（社会招聘部署）时，校招生助手入口**全部不可见**（包括菜单项与路由），且直接访问 URL 返回 403 |
| **F1-5** | 每个新增路径必须在 `permissionMenu.ts` 的 `MENU_PERMISSION_RULES` 中登记，不允许依赖 fail-open |

#### 验收标准

| # | Given | When | Then |
| --- | --- | --- | --- |
| AC1-1 | 以校招租户登录 | 打开主菜单 | 「校招专属」分组存在，其子项含校招生助手的业务页面；不存在名为「校招生管理助手」的独立一级菜单或分组 |
| AC1-2 | 以社会招聘租户登录 | 打开主菜单 | 无任何校招生助手入口 |
| AC1-3 | 以社会招聘租户登录 | 直接访问轮岗安排页 URL | HTTP 403，且响应体有中文错误提示；页面不渲染任何业务数据 |
| AC1-4 | 任意角色 | 检索前端路由表 | 校招生模块 100% 路径在 `MENU_PERMISSION_RULES` 中有登记项（脚本可校验：模块路径集合 ⊆ 登记前缀集合） |
| AC1-5 | 无 P-1 权限的用户 | 打开主菜单 | 校招专属分组因无子项而整体消失，不留空壳标题 |

#### 边界与异常

| 场景 | 期望行为 |
| --- | --- |
| 用户只有轮岗安排权限、无班级权限 | 分组保留，但仅显示轮岗安排子项（部分保留语义） |
| 用户所有校招子项权限全无 | 整个分组消失（不允许出现空分组） |
| 直接输入校招 URL 但无菜单权限 | 403 + 友好提示，不跳 404 |
| 同一页面被两个分组引用 | 不允许；F1-2 的四类归属互斥 |

### 要求 2：移除独立设置入口，功能并入 ATS 现有系统设置配置项

#### 用户意图
源项目有一个独立的「系统管理」顶层模块，用 5 个子页签维护 5 类基础库。这个入口的**问题不是功能本身**，而是**它自己维护了一套主数据**（本地部门、本地导师名单……），与 ATS 的部门管理、用户管理、数据字典形成三套平行真相。用户要的是：取消这个入口，把每一类配置能力**归位到 ATS 已有的对应配置页**。

#### 功能需求

| 编号 | 需求 | 归位目标（ATS 既有位置） |
| --- | --- | --- |
| **F2-1** | 取消「系统管理」菜单入口与对应路由。ATS 中不存在任何名为「系统管理」的独立页面 | — |
| **F2-2** | 轮岗部门的维护能力 → 由**部门管理页**（`/settings/department`）提供。轮岗相关页面只消费部门数据，不提供维护入口 | 部门管理 `DepartmentManagement` |
| **F2-3** | 导师 / 班主任的维护能力 → 由**用户管理页**（`/settings/users/*`）承担，通过身份授予/撤销完成（详见要求 4） | 用户管理 `UserDirectory` |
| **F2-4** | 平台（视频号/腾讯会议/企微直播）的维护能力 → 由**数据字典管理页**（`/settings/dictionary`）提供 | 数据字典 |
| **F2-5** | 源项目系统管理中「配置校招批次与每页条数」这类页面级配置 → 并入 ATS **租户配置**（`TenantConfig`，system_code + config_key + config_value），不新建表 | 租户配置 / 系统设置 |
| **F2-6** | 每一项归位后的配置项，必须在其所在页面内有**明确的归属标识**，使用户能发现"我以前在系统管理里配的东西去哪了" | 全部归位页 |

### 要求 3：轮岗部门删除本地数据源，改为复用 ATS 已有部门信息

#### 用户意图
> **事实核查（2026-10-16 复核，含精确行号与计数）**：源项目**确实存在两套互不相同的部门数据**，这是硬事实，不是笔误。已用脚本逐行解析 `data.js` 确认：
>
> | 事实 | 出处 | 计数 |
> | --- | --- | --- |
> | 轮岗部门库：8 项**平铺**字符串，无层级 | `data.js:13-16` `ROT_DEPTS` | 8 |
> | 内置组织树：**5 个一级事业群 → 12 个二级 BU → 28 个三级叶子**，合计 45 个具名节点 | `data.js:207-270` `DEPT_TREE` | 45 |
> | 组织树扁平化清单 + BU 查表 + 派生函数 | `data.js:273-302` `MIN_DEPTS` / `DEPT_BU_MAP` / `DEPT_BY_NAME` / `DEPT_BY_CODE` / `resolveBu()` | — |
> | 直播间归属 BU **由 `MIN_DEPTS` 派生**，即轮岗资源完全依赖 `DEPT_TREE` | `data.js:316`、`:325-326` | — |
>
> `index.html` 是 `data.js` 的**内联打包产物**（`bundle.py` 明确 `SRC=index.src.html` → `OUT=index.html`，把 data.js/app.js/styles.css 内联），故三处出现同一份 `DEPT_TREE` 属正常，不是三份数据。
>
> 两套数据的**名称重叠但不一致**（脚本逐项比对结果）：
>
> | ROT_DEPTS 项 | 在 DEPT_TREE 中的归属 |
> | --- | --- |
> | 微信事业群 | 一级（精确同名） |
> | 腾讯云 | **二级**（BU 层，非一级） |
> | 互动娱乐 / 平台与内容 / 技术工程 | 一级的**前缀截断**（DEPT_TREE 中为「互动娱乐事业群」「平台与内容事业群」「技术工程事业群」） |
> | 企业发展 / 广告营销 / 金融科技 | **完全不存在**于 DEPT_TREE |
>
> **结论**：ROT_DEPTS 是**一级/二级混合粒度**（微信事业群是一级、腾讯云是二级），且与 DEPT_TREE 存在前缀截断与缺失，无法通过简单名称映射对齐。`data.js:310` 的 `DEPT_TREE.find(l1 => l1.name === r.intentDept)` 对 8 项中 7 项返回 `undefined`（仅「微信事业群」命中）。这是原型期的真实数据缺陷，进了 ATS 必须收敛为唯一部门源，否则部门改名要改两处、BU 派生口径与轮岗安排口径对不上。

### 要求 4：导师库 / 班主任库合并到 ATS「用户管理」，作为身份类型区分

#### 用户意图

### 要求 5：用户管理新增「直属上级」字段 —— 支持选择、列表展示与查询筛选

#### 用户意图
源项目把"直属上级"当成一个 5 人字符串库，但它在轮岗业务里是**只能读、不能改**的（PRD §5.1.5 硬约束：来自核心人事系统）。用户在 ATS 中提出的诉求是把这个字段做进**用户管理**，成为一个真正可维护的用户属性。这实际上是 ATS 侧的加强：ATS 作为人事数据的中枢，直属上级理应在这里维护一次，全局复用。

**关键事实**：`User.direct_manager`（FK 自引用，related_name='subordinates'，verbose_name='直接上级'）**在 ATS 中已经存在**；`UserSerializer.fields` 已包含 `direct_manager`；`UserViewSet.queryset` 已 `select_related('direct_manager')`。但：
- `filterset_fields = ['department', 'level', 'is_active']` **缺 `direct_manager`**
- 全前端**无任何 `direct_manager` 使用**（无展示、无选择、无筛选）

**所以本条要求的本质是：把一个"后端已存在但前端完全没用"的字段，补齐为「可选、可看、可筛」的完整闭环。**

#### 功能需求

| 编号 | 需求 |
| --- | --- |
| **F5-1** | **可选择**：用户新建/编辑表单中提供「直属上级」选择控件，候选项为系统内其他在职用户；复用 ATS 现有用户选择器范式（支持按姓名/工号搜索），选择后展示为姓名 |
| **F5-2** | **自引用保护**：<br>① 不允许选自己为直属上级；<br>② 不允许选择自己的下级为直属上级（防止成环 A→B→A）；<br>③ 校验在**服务端**生效 |

### 4.3 「重建」而非「搬运」的清单

源项目是**零后端的单文件原型**。以下每一项都是**从零实现**，不存在"搬运"成分：

| 项 | 现状 | 迁移后 |
| --- | --- | --- |
| 数据持久化 | 内存数组 + localStorage | 数据库模型 + ORM + 迁移脚本 |
| 主键 | 姓名（字符串） | UUID / 员工 ID |
| 权限 | 无 | 服务端权限装饰 + 行级过滤 |
| 并发控制 | 无（单用户内存态） | 需明确策略（见 6 章 EX-6） |
| 审计 | 无 | ATS 审计字段体系（创建人/修改人/时间） |
| 软删除 | 无（数组 splice） | `deleted_at` |
| 分页/筛选 | 前端内存切片 | 服务端分页 + filterset |
| 唯一性校验 | 前端遍历比对 | 数据库唯一约束 |
| 参照完整性 | 无（删部门不影响业务） | 外键约束 + 删除保护 |
| 校验时机 | 前端即时 | 前端提示 + **服务端强校验** |
| 公式测算（BU 汇总） | JS 函数、一次性算完 | 服务端计算 + 结果可重算（需考虑数据变更后的重算时机） |
| CSV 导入导出 | 前端 Blob | 服务端生成 + 编码/BOM 处理 |

**结论**：本次迁移的工作量主体是**服务端重建**，不是代码搬迁。任何按"迁移 = 搬文件"估算的排期都会严重低估。

| **人员姓名（324 个枚举生成的 mock 名）** | **不迁移** | 纯占位数据 |

### 5.3 生产环境历史数据处理

**前提**：源项目是纯前端原型，**没有服务端数据库**，因此严格意义上**没有"历史业务数据"可迁移**。但需明确三种情况：

| 情况 | 处理方式 |
| --- | --- |
| **情况 A（当前实际）**：源项目从未作为生产系统使用，数据全在个人浏览器内存/localStorage | 无历史数据需迁移。迁移完成 = 直接切换到 ATS |
| **情况 B**：源项目已被部分运营在浏览器中使用并依赖其 localStorage 中的自定义容量等数据 | 需提供**一次性导入**能力：<br>① 提供与源项目 CSV **同格式**的导入入口（源项目已有 CSV 导出，可直接导出后导入）；<br>② 导入前做**干跑（dry-run）**：解析全部行并输出「可导入 X 条 / 部门列匹配不到 Y 条 / 编号重复 Z 条」的报告，用户确认后才真正写入；<br>③ 导入按**直播间编号**判重：编号已存在则更新、不存在则新增（源项目语义一致）；<br>④ 导入幂等：同一文件重复导入结果一致 |
| **情况 C**：未来若源项目接了真实后端并产生了数据 | 按情况 B 的机制执行 + 补充映射表（源 ID → ATS ID） |

#### 幂等与重复检测要求（无论 A/B/C）

| 要求 | 判定 |
| --- | --- |
| 字典种子重复执行不产生重复项 | 执行 2 次，字典项总数不变 |
| 身份授予幂等 | 同一人同一身份授予两次，`UserRoleV2` 中只有一条记录 |
| CSV 导入幂等 | 同一文件导入两次，直播间总数不变、字段值一致 |
| 直播间编号唯一 | 同表内编号唯一；导入遇重复编号走更新而非新增（并明确报告哪些是"新增"哪些是"更新"） |
| 部门列匹配失败不静默 | 匹配不到部门的行**跳过并计入报告**，不创建部门、不静默丢弃 |
| 人员批量导入（如有）以工号/员工 ID 判重，不以姓名判重 | 重名两人必须被识别为两条不同记录 |

### OQ-1 ⭐ 本次迁移的业务模块范围

**问题**：源项目有 6 大模块，本次是一次性全量迁移，还是先迁一部分？

- 选项 A：全量迁移 5 大业务模块（轮岗安排/轮岗资源/班级管理/人员管理）+ 基础库收敛
- 选项 B（**推荐**）：**分两期**。一期只做「基础库收敛 + 菜单归属 + 权限骨架」（即 6 条硬性要求的全部落地），业务模块暂以「ATS 内跳转/占位页」或不做；二期再做四大业务模块
- 选项 C：一期做「基础库收敛 + 轮岗安排一个模块」试点

**推荐 B（二期）**，理由：
1. 本次是**结构性收敛项目**而非功能迁移项目。6 条硬性要求的价值 90% 在"去重两套主数据"，这部分本身就能独立产生价值（消除数据分裂），且是后续所有业务模块的**前置依赖**。
2. 四大业务模块的服务端重建工作量极大（4.2 已说明全是"重建"），一次性全上风险不可控，且**主数据一旦收敛，原型的算法口径需要重新验证**（原型依赖本地部门树和本地导师库的口径全部失效）。
3. 二期可以带着一期收敛后的真实 ATS 部门/用户数据来做算法验证，比用 mock 数据验证更可靠。
4. 若兵哥坚持要一次全上，则选 A，但必须配套拆分上线（基础库先上、业务模块后上），而不是一个大版本。

### OQ-2 ⭐ 轮岗部门、导师、班主任这三类"人/部门"到底要不要预置

**问题**：源项目有 8 个轮岗部门、8 位导师、5 位班主任。迁移时这些数据怎么处理？

- 选项 A（**推荐**）：**完全不预置**。全部由业务方在 ATS 中自行创建/确认后授予身份。迁移交付的是"能力"，不是"数据"。迁移前由业务方准备一份确认清单（8 个部门在 ATS 中是否已有对应项、13 位人员对应哪些 ATS 用户）
- 选项 B：预置全部（部门建 8 个、用户建 13 个并授予身份）
- 选项 C：折中——部门不预置（因 ATS 部门是全公司主数据，轮岗模块不该反向创建一级部门），但导师/班主任预置

**推荐 A**，理由：
1. **ATS 部门是全公司主数据，轮岗只是它的消费方**。轮岗模块没有资格反向决定全公司的一级组织架构。要求 3 的方向是"复用 ATS 已有部门"，不是"轮岗模块自己造一套一级部门"。
2. **这 8 项是腾讯真实的组织架构名称**（微信事业群、腾讯云、互动娱乐、平台与内容、技术工程、企业发展、广告营销、金融科技）。把示例数据里的真实事业群名预置进生产库的组织树，一旦与 HR 实际架构不符，就是污染且需要人工清理 —— 而 ATS 部门被大量业务模块引用，清理成本极高。
3. **粒度确实不齐，但不是主因**：`ROT_DEPTS` 是平铺列表，其中「腾讯云」在源项目自己的 `DEPT_TREE` 里其实是二级 BU（不是一级），另有 3 项是 `DEPT_TREE` 一级的前缀截断（互动娱乐 → 互动娱乐事业群），3 项（企业发展/广告营销/金融科技）在 `DEPT_TREE` 中完全不存在。**8 项里只有 1 项能与 `DEPT_TREE` 精确对齐**。因此「按源项目原样预置」连自洽都做不到。
4. **13 位人员是真实人名**（非示例数据），系统不应替业务方创建真实用户 —— 用户创建涉及工号、部门、账号等真实身份信息，自动创建风险高且可能建错。
5. 这 13 人**极可能就是示例数据**（与 324 个枚举生成的 mock 姓名并列存在），但需求侧无法确定。若是真实人，由业务方建更靠谱；若是示例数据，就不该进生产。

### OQ-3 ⭐ 校招生本人是否要在 ATS 中有账号

**问题**：源项目中校招生是数据条目（花名册行），不是登录用户。迁移后呢？

- 选项 A（**推荐**）：本期**不给校招生建账号**。校招生作为轮岗记录的业务主体存在（可关联到 ATS 用户，也可不关联 —— 例如实习/待入职尚未入职者）。"查看本人轮岗档案"留作二期
- 选项 B：校招生建 ATS 用户（`user_type=EXTERNAL`），可自助登录查看本人档案
- 选项 C：校招生不建账号，但预留"学员门户"接入位

**推荐 A**，理由：
1. 校招生的真实身份是"候选人"，而 ATS 中候选人是一等公民（`Candidate`），不是 `User`。把校招生建成 `User` 会污染用户体系并触发一堆权限/部门/上级的数据要求（他的部门是谁？工号是什么？）。

### OQ-7 ⭐ 「推荐算法」（建议部门/建议导师/自动分班）本次做不做

**问题**：源 PRD §5.1.3 定义了三个初始化推荐算法。其中「并列最低导师随机分配」是刻意的随机行为。

- 选项 A（**推荐**）：**本期不做自动推荐**。轮岗安排提供手工分配 + "手动触发推荐"（点击才跑算法，结果落库、可解释、可手工修正）。随机项改为**确定性 tie-break**（如按带教人数、再按姓名/工号排序）
- 选项 B：完全按源 PRD 实现（初始化时自动计算、并列最低随机）
- 选项 C：本期只做"建议部门"（最简单的一条），不做建议导师与自动分班

**推荐 A**，理由：
1. **生产系统不能让用户面对不可解释的结果**。"每次刷新人不一样"在多人协作场景下会造成对账困难与信任问题。随机性应被消除。
2. 初始化时自动计算在真实系统里也不合适 —— 人员、部门、导师数据会持续变化，初始化那刻算出的"建议"很快就过期，且用户不知道它是何时算的。
3. 改成"手动触发 + 结果落库 + 可解释（显示推荐理由）"是保留算法价值的同时消除随机性和时效性的最小代价改法。
4. 如果兵哥坚持保留随机（如为模拟演练），应限定为**仅开发/演示环境**。

### OQ-13 ⭐⭐ 「BU」这个业务概念在 ATS 中如何表达（产品设计师已提出阻塞项）

**问题**：轮岗资源**不是**只用轮岗部门库，而是**强依赖** `DEPT_TREE` 派生的 BU 口径 —— 这是比"两套部门数据冲突"更深的一层依赖：

```
data.js:315-318  LIVE_ROOMS[i].dept = MIN_DEPTS[i % ...].name   ← 取「最小部门/叶子」
                 LIVE_ROOMS[i].bu   = ...bu（由 resolveBu() 派生）
data.js:300-302  resolveBu(minDept) { return DEPT_BU_MAP[minDept] || "" }   ← 取「二级部门」
```

即：**直播间必须选到叶子部门，BU 才能从它身上派生出来**。BU 汇总（`data.js:367` `allBus = [...new Set(MIN_DEPTS.map(d => d.bu))]`）的全部口径都建立在这条派生链上。

**迁入 ATS 后的语义断裂点**：源项目把"BU"硬编码为"**恰好是第 2 层**"，因为 `DEPT_TREE` 恰好是三级且写死。而 ATS `Department` 是**任意深度**的树 —— 核对模型字段（`apps/core/models.py` `class Department`）确认：

| 字段 | 含义 | 能否表达 BU 语义 |
| --- | --- | --- |
| `parent` | 上级部门（自引用） | 只能表达层级，不能表达"这一层是 BU" |
| `path` | 路径，形如 `/root/dept1/dept2/` | 可**推导深度**，但不含层级角色 |
| `name` / `code` / `sort_order` | 名称 / 编码 / 排序 | 否 |
| `leader` / `manager_2` / `manager_3` / `hrbp` | 各层负责人 | 是"人"的字段，**不是"层级角色"标记** |
| `is_active` | 启用 | 否 |

**结论**：ATS `Department` **没有任何字段能标注"本节点是 BU"**。所以"BU = 第 2 层"在 ATS 中只能是**一条约定**，而约定在以下情形会静默失效：某 BU 下被增删了中间层、某 BU 只有一个子部门、某事业群被拍平成一级。

**选项**：

- 选项 A（**推荐**）：**约定 + 显式配置兜底**。默认按"距根第 2 层"推导（继承 OQ-4），但允许业务方在**系统设置中显式指定哪些部门是 BU**（一份 `TenantConfig` 列表）。推导失败或与显式配置冲突时，以显式配置为准并在 UI 上明示来源。
- 选项 B：**只按约定**（BU 恒为距根第 2 层），不加任何配置。实现最简单，但 ATS 部门被其他业务模块调整层级时，BU 汇总口径会**静默错位**且无人察觉。
- 选项 C：给 `Department` 增加"层级角色"字段（如 `level_role` ∈ {事业群, BU, 部门}）。语义最显式，但**改的是 ATS 全局主数据模型，影响所有既有业务模块**，需架构师与主理人评估爆炸半径。
- 选项 D：在轮岗资源侧派生冗余字段（直播间表上冗余一个 `bu_department_id`）。绕过语义问题，但**要求 3 禁止冗余部门副本**（见 F3-2 与 AC3-2「无 dept_name 之类冗余字符串列」），且部门调整后冗余值会过期。

**推荐 A**，理由：
1. **不碰全局模型**。选项 C 改 `Department` 会波及 ATS 所有引用部门的模块（用户、权限、招聘需求…），爆炸半径远超本项目，不该由一个校招子模块单方面推动。
2. **选项 B 的风险是"静默错位"**。BU 汇总口径错了不会报错，只会让承载率/剩余容量算错 —— 这正是源项目遗留问题 3（承载率口径存疑）已经踩过的坑，不该在收敛时重蹈。
3. **选项 D 直接违反要求 3**，已排除。
4. 选项 A 的成本仅是一份租户级配置 + 推导兜底，收益是：约定成立时零配置、口径漂移时有人工干预点，且**不需要改任何全局模型**。与 OQ-10 的"模块开关放 `TenantConfig`"是同一套机制，工程上可复用。
